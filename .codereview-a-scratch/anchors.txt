=== Issue #4390 (verbatim) ===

## Context

`execution_artifacts`'s `collect_amcache` (`agents/plugins/execution_artifacts/src/execution_artifacts_win.cpp:301-336`, `TempHiveCleanup`) deletes its temp AmCache hive copy (and `.LOG1`/`.LOG2` sidecars, up to 256 MiB total) via an RAII destructor that fires on every normal return path, including exceptions caught by the entry point's `try/catch(...)`. That destructor never runs on a process kill, crash, or power loss — there is no other cleanup mechanism, and no startup sweep exists anywhere in `agents/core` or this plugin to reclaim orphaned copies.

## Acceptance criteria

- A startup-time (or periodic) sweep in the plugin's `init()` or agent-core boot path reclaims stale temp hives — e.g. delete files/directories whose owning PID is no longer running, or (simpler, sufficient) older than a bounded age.
- A regression test (or documented manual verification) confirms repeated kill-during-copy cycles don't leave the directory growing unboundedly across agent restarts.
- No change to the hive-copy or cleanup logic during normal operation — this is additive-only (a reclaim pass), not a rework of `TempHiveCleanup`.

=== Issue #4392 (verbatim) ===

## Context

`execution_artifacts`'s `collect_amcache` calls `RegQueryValueExW`/`CreateFileW`/`RegLoadAppKeyW`/`RegEnumKeyExW` directly, with no injectable reader/OS-call seam. This means several correctness-relevant paths have no unit coverage today and structurally can't be covered without a refactor:
- `TempHiveCleanup`'s deletion-failure branch (the `g_temp_cleanup_failed_total` counter and `note|temp_cleanup_failed` output row)
- the `subkey_cap` accumulator branch (`kAmcacheMaxSubkeys` = 20000)
- the mid-walk `enum_<code>`/`subkey_open_failed`/`value_enum_incomplete`/`value_read_failed` accumulator branches
- the Prefetch `file_cap`/`byte_cap` truncation branches

Blast radius is bounded: read-only forensic collection, gated Forensics/AdminOrApproval, every path already falls back to a named constrained/note token rather than failing silently or throwing across the plugin ABI.

## Acceptance criteria

- Design and introduce an injectable seam for the registry/file-system calls `collect_amcache`/`collect_prefetch` make (parameterized reader/runner, following this repo's existing pattern for other Windows-leg plugins if one exists), OR document a specific alternative if a seam refactor isn't the right fit.
- Unit tests locking: `TempHiveCleanup` deletion-failure path, `subkey_cap` truncation, at least one `enum_*`/`value_read_failed` accumulator branch, and Prefetch `file_cap`/`byte_cap` truncation.
- No behavior change to the production collection paths — this is test-infrastructure-only work.
