# ADR-0022 Execution Plan — Program Ladder + Vulnerability-Management Module Scoping

This document is the execution plan for [ADR-0022](adr/0022-headless-platform-use-case-engines.md) (PR #1918): headless platform, use-case engines, agentic-first as a core principle. It is **not** an ADR — it does not make new binding architectural decisions; it sequences ADR-0022's decisions into a phased program and works out the detailed scoping of the first use-case engine (UCE) module, vulnerability management, which re-homes the shipped server-side NVD sync + CVE matching (ADR-0022 grandfathered surface #2 — as extended 2026-07-07/08 to absorb the in-server vuln stack: the ADR-0023 correlation engine and the ADR-4001 dashboard lens; see "Relationship to ADR-0023 and ADR-4001" under Module scoping).

Two items below are flagged as candidates for their own future ADRs rather than settled here: the UCE host stack/runtime choice (deferred pending a requirements doc) and the auth-architecture delegation follow-up (ADR-0022's own named prerequisite).

**Assumption:** this plan assumes ADR-0022 is accepted (independent review + tracking issue + status flip, handled separately).

**Numbering note:** "Decision N" (bare) below refers to this plan's own 14-item decision log; "ADR-0022 Decision N" refers to ADR-0022's 7 decisions. The two number lines are independent and collide (e.g., this plan's Decision 5 is the catalogue-grain join; ADR-0022's Decision 5 is delegation) — always read the prefix.

## Decision log

These decisions resolve open scoping questions ADR-0022 deliberately left to "first module scoping" (ADR-0022 Decision 6) and the execution sequencing it leaves to a follow-up program. None override or amend ADR-0022 itself.

1. **v1 vuln module is read-only against the server.** Write-back/orchestration (result-set materialization by the engine, remediation dispatch) waits for ADR-0022 Decision 5 delegation to ship. This constraint is enforced structurally, not just by omission: Phase 6 (module cutover to engine-principal auth) and Phase 7 (NVD removal) are both scoped and gated without requiring delegation — see Program ladder.
2. **Hand-off seam included, mechanism pinned.** The module's findings page hands off a device cohort as a **server-side object created via the server's public API, under the operator's own session** (e.g. a result set). The write must originate from **the operator's own browser, calling the Yuzu server's own origin using the operator's existing Yuzu session** — never a credential or token the UCE backend holds or forwards on the operator's behalf. This is what keeps decision 1's read-only property real: if the UCE backend ever held or proxied a write-capable credential, it would be performing the write, not the operator, regardless of whose session initiated it.
3. **Consumer model.** Agentic workers and orchestrators (e.g. a ServiceNow-style integration) consume the **Yuzu server directly** over REST/MCP and compose their own interpretation from server primitives. **No machine consumer of the UCE exists in this scoping** — the UCE's only external interface is its human UI. The UCE-host UI ↔ UCE-host backend seam is private (one product); ADR-0022's parity/discoverability obligations discharge at the *server* surface, not inside the UCE. **This exemption is scoped to parity/discoverability only. It does not extend to ADR-0017 management-group confinement, which is a separate requirement — see Decision 14.**
4. **Scale target:** build for 2,000 devices, **design for up to 500,000**.
5. **Catalogue-grain join; no fleet-inventory replica in the engine.** The module never syncs a copy of per-device installed-software inventory. Cycle: sync CVE feeds → match feed data against the server's `software_catalog` rollup (distinct name/version pairs — on the order of 10–50k entries even at 500k devices, an estimate not yet empirically validated) → expand only the *matched* entries to affected devices via `query_software(name)` → persist **findings only**. This keeps egress at O(catalogue) + O(hits) instead of O(fleet), and removes bulk changed-since delta sync from this module's critical path. **Caveat:** the 10–50k estimate assumes bounded version-string cardinality; long-tail per-build or portable-app version strings could push distinct-pair counts materially higher. M2's acceptance criterion (below) includes a cardinality check against the 500k design ceiling before this assumption is load-bearing for a real deployment.
6. **The UCE host owns one shared fleet-data access layer**, used by every module (vulnerability management now; software asset management and others later) — API-backed reads, cached, request-paced against a single shared budget toward the server. Modules store only their own derived domain state (findings, license positions, etc.), never a fleet copy. The interface is designed so a synced replica could be introduced behind it later; the trigger for that is a module demonstrating a genuine need for device-grain data residency, not module count. **A likely candidate for that trigger is the second module itself:** software asset management's per-device license attribution may need device-grain data from day one. That module's own scoping must re-examine device-grain residency as an explicit first step, not assume this layer suffices by inheritance from the vuln module.
7. **NVD re-home is a strangler migration, not a code move.** The UCE module builds and proves its own feed-ingest + matcher first; a parity gate (module output == existing `POST /api/nvd/match` output on a reference inventory) precedes any server-side deletion — see the strengthened acceptance criterion on M3 below, and Phase 7. **No `/api/v1/nvd/*` twin is built** on the server — the existing capability has no REST-versioned or MCP twin today, and building one would freeze the interpretation logic into the platform contract at the exact moment it's being extracted. The gap closes by removing the capability, not by twinning it. (2026-07-08: this refusal covers **legacy** capability being extracted; it is not contradicted by ADR-4001's `/api/v1/vuln/*` + MCP twins, which ADR-0022 Decision 4 *mandates* for new work — those ship with the versioned-surface deprecation rider and their read-contract carries forward as the module's own spec; see "Relationship to ADR-0023 and ADR-4001".)
8. **Agent-side `vuln_scan` plugin:** the `inventory` collection action and the generic rule-evaluation / content-delivery plumbing stay core (mechanism, per ADR-0022 Decision 2). The plugin's embedded static `cve_rules.hpp` CVE list and its use as an authoritative `cve_scan` finding source are **frozen (no further rule updates) and marked deprecated**. The long-term replacement is engine-published content delivered through the existing content-distribution plane — the ruleset becomes engine-authored content evaluated by the agent's existing generic engine, which is cleanly mechanism-side.
9. **Postgres migration interplay and the audit-attribution window.** Two audit needs have different timelines and are treated separately:
   - **Actor attribution (`principal_class`: human / agent / engine) is needed the moment Phase 4 makes engine principals live**, independent of delegation. This is a small, additive field — it does not need to wait for a Postgres migration and is **pulled into Phase 4 directly** (see Phase 4, and Phase 3a below) so that no engine-principal action is ever audited without knowing what kind of actor performed it. Revoked engine-principal rows are soft-retained (never hard-deleted) so this attribution stays resolvable after a credential is revoked.
   - **The full delegation audit shape** (engine principal id, `is_delegated`, delegated operator identity, delegation artifact id, `delegation_verification_status`) lands with `AuditStore`'s Postgres migration (ladder Wave 1, already a mandatory-backfill item) — nothing can populate these fields correctly before Phase 5 ships, so there is no benefit to an earlier throwaway SQLite schema change. If Wave 1 slips past Phase 5's need for it, an additive SQLite column is the fallback for this delegation-specific shape only (not for `principal_class`, which ships earlier regardless — see Phase 3a/3b split below).
   - The engine-principal class does **not** wait for `RbacStore`'s later Postgres migration wave — adding an `engine` value to `principal_type` is additive on either substrate. **`ApiTokenStore`'s Postgres migration is pulled forward** to precede the engine-principal work, since it is already marked unblocked-to-migrate and engine credentials are semantically new rows worth being born on Postgres rather than migrated later. `ApiToken` rows carry an explicit, persisted principal-kind field set at creation time; session synthesis branches on that stored field, never on inference over the `principal_id` string shape — this is what keeps a legacy human-attributed token and a new engine-attributed token unambiguous during the live Phase 4 cutover.
10. **The API versioning/deprecation policy is written early — folded into Phase 0, not a separate parallel track.** ADR-0021 is landing new API surface now that needs a published compatibility posture regardless of delegation's timeline; there is no reason to wait. MCP tool versioning follows the same posture as REST: additive-only evolution, with a versioned tool name (e.g. `query_software_v2`) only on a breaking change — no per-tool semver scheme.
11. **UCE host stack is deferred** until a committed requirements document exists; the runtime/language choice is then made via its own review (ADR-worthy: hard to reverse, a real trade-off, and will surprise a future reader without the context). What is decided now: the UCE host's data layer is **its own Postgres database**, never the server's connection pool (ADR-0022 Decision 3 — no new private seam, no shared database access). Location is **inside the Yuzu repository**, under `engines/` (`engines/host`, `engines/modules/vuln`), shipped as a separate deployable artifact from `yuzu-server`, with CI enforcing that nothing under `engines/` includes or links against `server/` code.
12. **Naming:** "UCE" is adopted **by this plan** as shorthand for ADR-0022's "use-case engine" / "use-case engine host" — ADR-0022 itself does not abbreviate. The source directory stays the plain-English `engines/`.
13. **Deferred out of this scoping** (tracked, not lost):
    - Everything delegation-dependent: engine-initiated write-back, result-set materialization by the engine itself, remediation dispatch, quota mechanisms beyond the minimum interlock.
    - Streaming/durable event-subscription egress — evaluated against the batch-join alternative per ADR-0022 Decision 6's mandate, and deferred in favor of batch-join (see Module scoping, egress decision, below).
    - Bulk changed-since delta sync (`/changes`-style endpoint) — removed from this module's critical path by the catalogue-grain join (Decision 5); revisited only if a future module proves a device-grain residency need.
    - The vulnerability graph differentiator (topology, trust zones, attack-path scoring) — its own future scoping, with its own core-vs-engine boundary analysis. (2026-07-08: ADR-4001/4002 began that scoping; 4001's surface is absorbed as grandfathered — see "Relationship to ADR-0023 and ADR-4001" — while the boundary analysis for 4002's scoring substrate remains owed at its own merge.)
    - Agent-side KEV pre-filter as engine-published content — waits on the module producing an authoritative ruleset.
    - SBOM ingest (roadmap 18.5) and compliance-framework report bundles (roadmap 18.2) as separate future modules.
    - Scope-aware `software_catalog` rollup — stays on its existing tracked issue; not a blocker for this module, since the module computes its own rollups from synced findings.
    - Server-only topology support-matrix implications, BYO-engine conformance/assurance package, published SLO numbers, dashboard-migration sequencing — placeholder tracking only, per ADR-0022's explicit "no migration scheduled" stance.
    - The UCE host's own data-processor/retention posture for its Postgres-resident derived state (beyond the v1 findings-store commitment in Phase 2c below) is a Phase 8 pre-GA item, not a v1 blocker.
    - A customer-facing v1 "what's in / what's out" pilot-readiness note (read-only scope; no cross-group visibility guarantee until Decision 14 ships; what a pilot customer should and shouldn't expect against the `vuln-scan-engine-design.md` north-star) — distinct from this internal engineering decision log, and not produced by it. Owned by SOC 2 Workstream G (Customer Assurance), authored once a pilot is scheduled. Distinct from and additional to it (2026-07-07): a disclosure for any customer piloting **today's in-server vuln capability** (ADR-0023 M1a/M1b, absorbed as grandfathered — and, per the 2026-07-08 extension, explicitly including the **ADR-4001 `/vuln` dashboard lens**, where the interim status is far more customer-visible than a background scanner) — that it is interim, honestly scale-ceilinged, and scheduled for re-homing — owed by Workstream G **now**, independent of module-pilot scheduling, not deferred to Phase 7's deprecation cycle, and in place before any ADR-4001 implementation PR merges (enforced alongside the item-(xi) sequencing gate).
    - The UCE host's new deployment topology and data flows (a separately-deployed component holding customer-derived findings data, per Decision 11) require an update to the security whitepaper / shared-responsibility-matrix — also owned by Workstream G, tracked alongside the BYO-engine assurance package above.
    - **Tripwire:** if any future module version syncs per-user or behavioral data, ADR-0022 Decision 5's bulk-PII security-guardian review triggers at that point. The v1 dataset (installed-software inventory, and the CVE findings derived from it) is machine-scope only and does not trigger that specific review — but see Decision 14 for the confinement requirement that applies regardless of PII class.
    - Recorded here for symmetry with ADR-0022's own exception-ledger convention: Decision 3 ("no machine consumer of the UCE") is a scoping choice made by this plan, not a grandfathered-surface exception under ADR-0022 itself, and does not need an entry in that ADR's ledger.
14. **Findings-viewing must enforce ADR-0017 management-group confinement, keyed to the viewing operator.** The module's own reads (Decision 5's catalogue-grain join, M2/M3) are necessarily fleet-wide — that is what makes the egress footprint tractable. But nothing about that read scope should leak into what an individual operator sees in the findings UI afterward. Decision 3's exemption of the UCE UI↔backend seam from ADR-0022 parity/discoverability obligations does **not** extend to this: confinement is a distinct requirement, and this plan already enforces it for Phase 5's delegated reads via the existing `authorize_list_read` chokepoint. **The mechanism for the module's own findings-viewing enforcement is not yet designed here, only required:** the UCE is a separate deployable with no Yuzu server session of its own (Decision 11), so it cannot literally call the same server-side chokepoint at view time. How it binds a viewing operator to their Yuzu management-group scope — a per-operator scoped read-through at view time, a session-exchange/identity-assertion mechanism, or a confinement predicate synced alongside findings and re-validated on a short TTL (never a stale cached snapshot, given Decision 6's shared access layer is explicitly a cache) — is an open design question. It is a **required, named deliverable of Phase 2c's requirements doc**, not something the citation above already solves. Whatever mechanism 2c selects, the outcome must match: a group-confined operator's findings page shows the same device set for a given CVE that `/devices` would show that operator for the same scope — never more. **This is a hard interlock, not a v2 nice-to-have, and it is unconditional: it gates M3's acceptance and Phase 6 the moment the mechanism must exist, not only once a multi-group or MSP-style customer happens to be onboarded** — mirroring the Phase 1/Interim-rules pattern already used for engine principals and quotas, but stronger: Phase 6 cuts the module over to fleet-wide-reading engine-principal credentials regardless of which customer is live at the time, so the gate fires on the mechanism's own live-and-verified state (M3's condition (d)), never on customer topology (see Program ladder and Phase 6). A multi-group/MSP pilot is simply the scenario where an unmet gate would be most visibly harmful — it does not define when the gate fires. One additional constraint sits on top of the gate without being its trigger: between M2 (module reading fleet-wide) and M3(d) verifying, the findings UI must not be exposed to a multi-group or MSP-style pilot customer — the phase gate prevents *cutover* with confinement unbuilt, and this clause closes the residual pre-cutover window where an in-development findings view could show a pilot operator unconfined cross-group data (the Workstream G pilot-readiness note in Decision 13 discloses this same boundary customer-side).

## Program ladder

Critical path: **auth-architecture follow-up design → engine-principal class → module cutover**. Delegation (full write-back) is **not** on this critical path, since v1 ships read-only and autonomous per Decision 1 — it runs in parallel and gates only the later write-back phase.

```
P0 (docs: governance wiring + doc fan-out + versioning policy) ──► P1 (interim interlocks)
   │
   ├──► 2b auth follow-up design ──► P4 engine principals ──► P6 module → engine auth ──► P7 NVD strangler removal
   ├──► 2c UCE requirements + stack ADR (confinement-mechanism design only) ─────────────► feeds 2d
   ├──► 2e keyset pagination on query_software (#1634, independent of auth) ──────────────► gates M3(a2)
   └──► 2d module domain half (M1–M4; M3 = parity + confinement gate, needs 2e) ─────────► P7
             └─ M3(d) confinement mechanism live + verified ──────────────────────────► gates P6 directly
        P3a audit principal_class (pulled forward, cheap) ──► gates P4
        P3b full delegation audit fields (PG Wave 1) ─────────────────────► P5 delegation
                                                                             (write-back only — off the P6/P7 critical path)
```

2e is deliberately pulled out of Phase 6: it is an ordinary authenticated-read improvement with no dependency on engine-principal auth, so gating it behind Phase 4/6 would have transitively delayed M3's parity gate behind the entire auth chain despite 2d being described as this program's most independent track. Likewise, Phase 6 depends on M3's condition (d) specifically — the confinement mechanism landing and being verified — not on M3's other four conditions (a/a2/b/c, the matching-parity and shadow-match work), which gate Phase 7 only; 2c is a design input consumed by 2d, not itself the thing Phase 6 waits on.

- **PR 0.3 — API versioning/deprecation policy.** Promote the existing REST-only versioning statement into a formal cross-surface policy: versioning mechanics, additive-preferred posture, deprecation cycle length, and MCP tool versioning per Decision 10. (2026-07-08 addition: the policy must also define **cross-deployable succession** — see "Relationship to ADR-0023 and ADR-4001" item (viii); if the Phase 0.3 doc has already shipped without it, this lands as an amendment before Phase-7 planning consumes it.) Folded into Phase 0 (not a later parallel track) because ADR-0021 is landing new surface now that needs this regardless of the auth follow-up's timeline; this also gates external engine credential issuance (Phase 8) and is cited by the NVD deprecation cycle (Phase 7).

### Phase 1 — Interim interlocks (2 small code PRs + 1 tracking issue)

- **PR 1.1 — reject on-behalf-of assertions on every ingress surface.** Define the reserved header/field names and reject (not silently ignore) any such assertion at the single pre-routing chokepoint in `server/core/src/server.cpp`, returning the A4 error envelope and citing ADR-0022. Covers REST and MCP, since both pass through the same chokepoint (confirmed: MCP registers on the same web-server instance as REST), **and the agent-facing gRPC channel**, via a single gRPC server interceptor at agent-service ingress — not a per-RPC-method check, since a guard duplicated across `Register`/`Heartbeat`/`ReportInventory`/command-result handlers is exactly the shape a future new RPC method could be added without, silently reopening the gap this PR closes; the interceptor is what gives the gRPC guard the same "no new route can bypass it by construction" property the HTTP chokepoint already has. ADR-0022's rejection rule binds on **any surface**, not HTTP alone (ADR-0022's Interim rules, first bullet — currently `docs/adr/0022-headless-platform-use-case-engines.md:95`), and this plan is not chartered to narrow that. The gRPC guard is a defensive no-op today — no engine-principal traffic crosses the agent gRPC channel under Decision 3's no-machine-consumer scoping — but it ships now, not when a machine consumer first appears, since the ADR's rule binds from acceptance, not from when current traffic happens to need it.
- **PR 1.2 — `principal_class` metric label** (`human` / `agent` / `none` today, `engine` reserved) on the HTTP request-count metric. As shipped, this is a **presentation-level classification resolved at the metrics site**, not an authoritative class stashed during pre-routing — `none` covers unauthenticated requests (probes, login, static assets), which the original two-value set had no honest label for. The authoritative, persisted principal-kind field remains Decision 9 / Phase 4 work; this label must never be consumed for authorization.
- **Issue 1.3 — per-principal quota interlock tracker.** ADR-0022's interim rules block any engine principal from production until a minimum per-principal concurrency/quota cap exists; today's rate limiter is per-IP only. This issue is the tracked blocker for that gap; it closes when Phase 4's minimum cap ships.

### Phase 2 — Parallel tracks

- **2b — auth-architecture follow-up design.** Delegation token-exchange mechanics, principal granularity (per-module vs. per-host), credential lifetime/rotation ceilings, the change to token-session attribution needed for engine principals (today a service token's session is attributed to its human creator), the self-target-guard extension, and MCP tier applicability to engine principals. This is the program's critical-path deliverable.
- **2c — UCE host requirements doc**, capturing Decisions 2–6, 11–12, and 14 as functional/non-functional requirements, plus two items that are not deferred and need a commitment before M1 lands: (i) an explicit data-inventory entry for the module's own findings store (classification, retention default, deletion path) — the findings store is arguably more sensitive than the asset inventory it derives from; (ii) the concrete **confinement-enforcement mechanism** for Decision 14 (findings-viewing must match `authorize_list_read`'s outcome without a server session to call it directly — see Decision 14 for the candidate approaches this doc must choose between). A stack ADR follows as its own PR once the requirements doc is settled.
- **2e — keyset pagination on `query_software`** (closes the existing tracked gap, #1634): the fleet-wide software query is hard-capped at 1,000 rows with no offset today. This is an ordinary `Inventory:Read`-gated improvement with no dependency on engine-principal auth — it is deliberately kept out of Phase 6 (see Program ladder note) so it can land whenever it's ready and simply be available when M3 needs it, rather than transitively gating the module's parity milestone behind the entire auth chain.
- **2d — vuln module domain-logic half** (the module's longest-running, most independent track — buildable now per ADR-0022 Decision 6's "domain-logic half can start immediately" carve-out): see Module scoping below for the milestone breakdown (M1–M4). **The team executing this track is responsible for tracking amendments to this plan doc as governance findings are folded in** — do not fork a static backlog from an early version of this document.

### Phase 3 — Audit substrate, split by urgency

- **3a — `principal_class` field, pulled forward.** An additive field on `AuditStore` recording actor class (human / agent / engine) for every audited action, landing **before or alongside Phase 4** (not gated on a Postgres migration) — this closes the audit-attribution gap that would otherwise open the moment engine principals can act. Cheap, additive, no delegation semantics required.
- **3b — full delegation audit shape via PG Wave 1.** `AuditStore`'s Postgres migration (mandatory backfill) carries the remaining Decision 9 fields (engine principal id, `is_delegated`, delegated operator identity, delegation artifact id, `delegation_verification_status`) into the target schema, with defaults only until Phase 5 ships producers. Gates Phase 5, not Phase 4.

### Phase 4 — Engine principal class

Gated on Phase 2b's design being accepted **and Phase 3a** (actor-class attribution must exist before engine principals can act).

- **PR 4.1** — `ApiTokenStore` migrates to Postgres (pulled forward per Decision 9), with the persisted principal-kind field from Decision 9 included at creation.
- **PR 4.2** — introduce the `engine` RBAC principal type and a machine principal class on `Session`; engine token sessions attribute to the engine principal itself, not the creating human, branching on the persisted principal-kind field (never inferred).
- **PR 4.3** — engine-principal lifecycle surface (create/rotate/revoke, named responsible human owner, grant justification captured at creation, folded into the existing periodic access-review cadence) on both REST and MCP, plus an admin-console page composing that API. Least-privilege is enforced, not merely asserted: the grant model is default-deny per securable, with no "all permissions" toggle available to an engine principal — recreating the ServiceNow-integration's admin-token pattern must not be possible through this surface, not just discouraged by it. **How an issued credential is classified internal (first-party module, e.g. Phase 6's own credential) vs. external (third-party/BYO) is not yet designed here — it is a required, named deliverable of this PR.** Decision 9's persisted principal-kind field distinguishes human/agent/engine only; Phase 8's external-issuance gate (versioning policy, quota cap) has nothing to key off without a further internal/external attribute (or an equivalent operational convention) on that same field. **Whatever mechanism this PR selects, an unclassified or ambiguously-classified credential must default to external** (the stricter, gated treatment) — never to internal — so a classification bug or a not-yet-wired write path fails toward re-checking the Phase 8 interlocks, not toward silently skipping them.
- **PR 4.4** — minimum per-principal concurrency/quota cap, closing Issue 1.3, with a quota-exhaustion counter emitted so the server side can independently observe a UCE module approaching its budget (not reliant on the module self-reporting).
- **PR 4.5** — `principal_class=engine` becomes a live metric value.

### Phase 5 — Delegation (write-back only, off the P6/P7 critical path)

Gated on Phase 3b (full audit shape) and Phase 4 (principals exist). Server-issued delegation artifact and verification (an engine-*asserted* delegation is rejected permanently, at every point in this program); effective authority computed as permissions ∩ scope through the existing ADR-0017 list-read chokepoint; self-target destruction guards re-keyed on the effective delegated identity; audit producers begin emitting the full Decision 9 fields, with pre-enforcement rows carrying `delegation_verification_status=unverified` per ADR-0022's incremental-shipping rule. This phase unlocks write-back/orchestration (Decision 13) — it is not required for the module's v1 read-only operation, autonomous sync, or the NVD strangler removal.

### Phase 6 — Module moves to engine auth

Gated on **Phase 4 and M3's condition (d)** — the Decision 14 confinement mechanism, designed in 2c and built as part of 2d, live and verified per M3(d) — independent of M3's other four conditions (a/a2/b/c), which gate Phase 7 instead (not Phase 5 — v1 remains autonomous and read-only per Decision 1). The vuln module switches from a plain API token to engine-principal credentials with least-privilege grants (explicitly not the union-of-permissions pattern of the existing ServiceNow integration). This phase changes only which credential the module authenticates with — the device-expansion cap fix (2e) is independent and may already be in place by the time this phase runs. **M3(d) must be live and verified before this phase runs, full stop — not merely before a multi-group customer is onboarded, and not merely once 2c's design doc is accepted.** The module's own reads are fleet-wide from M2 onward (Decision 5), so an unconfined findings-viewing path is already exposed the moment credentials switch, regardless of which customer happens to be looking; gating this only on customer topology, or on design-doc acceptance rather than the built-and-verified mechanism, would let cutover proceed with the confinement gap still open.

### Phase 7 — NVD re-home surgery (server-side strangler)

- **PR A** — extract the pure `compare_versions()` helper out of the NVD store into a standalone core utility (it has two existing internal consumers and is mechanism, not interpretation — it stays in the server permanently).
- **PR B** — deprecation marks on the three legacy `/api/nvd/*` routes, plus a settings-fragment banner and a capability-map note, following the Phase 0.3 policy's announced cycle. ### Module milestones (Phase 2d's longest track)

- **M1** — UCE host skeleton (server-API client with a min/max supported server-API version handshake, a sync scheduler, the shared fleet-data access layer from Decision 6, a UI shell) plus NVD 2.0 feed sync with a watermark, landing in the module's own Postgres. *Acceptance: CVE count and watermark match a server-side sync over the same window; the host itself exposes a readiness probe and a metrics surface matching `docs/observability-conventions.md` before this milestone is considered done — a CVE-matching module that silently stops syncing must be observable to an operator, not just to the server.*
- **M2** — catalogue-grain inventory join per Decision 5: read the fleet-wide software catalogue plus per-name device expansion, over a plain API token, autonomous reads only, request-paced. *Acceptance: the module's catalogue snapshot matches server reads for a pilot fleet, AND a synthetic high-cardinality version-string seed is used to measure sync/egress against the 500k design ceiling (validating or correcting the 10–50k catalogue-size estimate in Decision 5), AND the device-expansion read is exercised specifically for correctness (not just the catalogue read) given the 1000-row cap tracked at #1634.*
- **M3** — matcher parity, a findings store with a triage lifecycle (new / triaged / accepted-risk / remediated / reopened), findings UI, and the operator hand-off seam from Decision 2. *Acceptance, strengthened — this is the gate that authorizes Phase 7's irreversible deletion, so it carries five conditions across two axes (matching-logic parity and device-expansion completeness are different checks, since `/api/nvd/match` itself has no device-count dimension — it takes a `{name,version}` inventory and returns CVE matches, nothing more):*
  - *(a) Matching-logic parity: given the identical `{name,version}` inventory input, the module's matcher returns the identical set of CVE findings as the existing `/api/nvd/match` route.*
  - *(a2) Device-expansion completeness (depends on 2e): for a software title seeded via a controlled synthetic fixture (not discovered through the same `query_software` path under test, to avoid a circular check) to be installed on more than 1,000 devices, the module's own device-expansion enumeration (via the keyset-paginated `query_software` from 2e) returns the complete device list with no cap-related truncation — verified against the fixture's known device count, not against `/api/nvd/match`, which was never involved in device counting.*
  - *(b) A production-scale shadow-match run against the live fleet during the deprecation window, comparing the **per-device set of CVE ids**, not just aggregate finding counts — a compensating false-positive/false-negative pair must not pass this check by netting out to the same total.*
  - *(c) Sign-off from someone other than the engineer who built the matcher and the reference corpus, since a milestone that grades its own homework is not an independent gate for an irreversible deletion.*
  - *(d) Decision 14's findings-viewing confinement is live and verified — a group-confined operator's findings view matches what `/devices` would show them for the same scope.*
  - *Phase 7's own implementation should additionally exercise synthetic adversarial version-string edge cases (epoch prefixes, backport/distro suffixes, wildcard CPEs) as part of its test design — this milestone's acceptance criteria establish the gate's structure, not an exhaustive input corpus.*
- **M4** — surpass parity: real package/version identity matching, version-range evaluation, additional feed sources for reduced false positives. *Acceptance: a fully-patched reference OS image reports zero package-level CVEs.*

### Egress-primitive decision

ADR-0022 Decision 6 requires evaluating at least two consumer archetypes even if only one ships.

- **Batch-join** (changed-since reads over the catalogue rollup plus per-name device expansion): matches the module's actual data cadence — CVE feeds update on an hourly-to-daily cycle, and per-agent inventory changes at most once a day. At the 500,000-device design ceiling, catalogue-grain access keeps this to tens of thousands of rows per cycle (pending the M2 cardinality validation above), not a fleet-wide scan.
- **Streaming** (a durable, replayable event subscription on inventory or catalogue mutations): evaluated and **not selected for v1** — it would add a new durable-log/retention/backpressure subsystem for data that does not benefit from sub-daily latency in this module, and would reintroduce gap-detection/replay-horizon complexity that batch-join avoids by construction.

Decision: **batch-join ships**; streaming is deferred, not rejected, and nothing in this plan precludes adding it later behind the same shared fleet-data access layer (Decision 6) if a future module demonstrates a genuine latency need.

## Verification

- **Phase 0:** a governance dry run on a synthetic capability-adding diff confirms the standing review question fires in Gate 3/4 output; Phase 1's own code PRs are the first real capability-adding diffs and are what actually exercises this wiring end to end.
- **Phase 1:** a request carrying a reserved on-behalf-of header receives the A4 rejection envelope on both REST and MCP — with one recorded exception: the four liveness/readiness probe paths (`/livez`, `/readyz`, `/health`, `/api/health`) are exempt, so a mesh/SSO proxy that stamps a reserved header on every request cannot 403 the probes and crash-loop the pod (governance Gate 5 CH-3/UP-5; recorded in ADR-0022's exception ledger — a probe performs no identity-bearing action and nothing consumes the header on that path). An equivalent assertion sent over the agent-facing gRPC channel is rejected at the gRPC interceptor (no current traffic exercises this path, per Decision 3, but the rejection is live — verified manually via `grpcurl`; the in-process HTTP/gRPC test harness that would automate this check, and pin the probe exemption alongside it, is a tracked follow-up). The HTTP request metric shows the correct `principal_class` value for a browser session vs. a bearer-token (agent) call.
- **Phase 3a/3b:** an audited action performed by an engine principal carries a `principal_class=engine` field from the moment Phase 4 ships (3a), independent of whether delegation-specific fields (3b) have landed yet.
- **Phase 2e:** `query_software` returns a stable, complete, keyset-paginated device enumeration for a title exceeding 1,000 installs, with no duplicate or dropped rows across pages.
- **Phase 2d milestones:** acceptance criteria as stated above (M1 host observability + watermark parity, M2 catalogue parity + cardinality validation + expansion-read correctness, M3's five-part matching-parity + expansion-completeness + per-device shadow-match + independent-signoff + confinement gate).
- **Phase 4/5:** an engine token's session attributes to the engine principal (not its creator) in audit rows; attempting to issue an **external** engine credential via the admin console with either of the two Phase 8 interlocks (versioning policy published, quota cap live) deliberately unmet is refused with an audited denial, not merely a UI warning — Phase 6's own module credential is exempt from this check because it is **internal** (first-party, not the external/BYO case this gate targets); its read-only scope (Decision 1) is a separate property and is not itself what exempts it, so a future read-only *external* credential must still pass this gate. (The internal/external classification mechanism itself is PR 4.3's open deliverable — see Phase 4.) A delegated read on behalf of a group-confined operator returns only that operator's groups; the self-target guard blocks an engine from acting against its own delegated operator's account.
- **Phase 6:** a group-confined operator's findings-page device **set** for a given CVE matches what `/devices` would show them for the same scope — a count-only comparison is insufficient here for the same reason M3(b) rejects it for the shadow-match: a compensating over-inclusion/under-inclusion pair must not pass by netting out to the same total.
- **Phase 7 PR E:** full server test suite passes; the server boots and reaches a healthy `/readyz` with no NVD flags set and no UCE reachable. For the original NVD store this is a pre-existing exclusion (it was never wired into the readiness conjunction), so that half of the check is a clean boot after route and dead-seam removal. The ADR-0023 `VulnFindingStore`, however, **is** wired into the `/readyz` `stores_ok` conjunction (ADR-0023 Decision 8), so for the absorbed stack PR E **is** a readiness-wiring change: deletion must unwire the findings store from the conjunction, and this bullet's boot-to-ready check explicitly covers the server reaching healthy with that store absent.
- **Phase 8:** the two external-credential interlocks ADR-0022 actually names — versioning policy published, quota cap live — are each independently checkable, and external credential issuance is blocked when either is unmet. Delegation status is not an issuance gate; it governs audit-row labeling (`delegation_verification_status`) on credentials that will perform delegated writes, and is checked separately at Phase 5.
- Every server-side code change in this program runs the full governance pipeline per repository policy; no push or PR proceeds without explicit confirmation.
