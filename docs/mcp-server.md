# MCP (Model Context Protocol) Server

Yuzu embeds an MCP server at `POST /mcp/v1/` using JSON-RPC 2.0 transport. This allows AI models (e.g., Claude Desktop) to securely query fleet status, check compliance, investigate agents, and — with appropriate authorization — execute instructions on endpoints.

CLAUDE.md keeps only the load-bearing invariants (embed point, tier-before-RBAC ordering, kill switches, audit pattern). This document is the full architecture and tool reference.

## Architecture

- **Embedded in existing server** — MCP runs inside the same cpp-httplib server as the REST API and dashboard. It reuses auth middleware, RBAC, rate limiting, CORS, and audit logging with zero duplication.
- **Module:** `server/core/src/mcp_server.hpp` / `mcp_server.cpp` — mirrors `RestApiV1` pattern (injected store pointers, same callback signatures).
- **JSON-RPC helpers:** `mcp_jsonrpc.hpp` (header-only) — parse/build JSON-RPC 2.0 envelopes.
- **Tier policy:** `mcp_policy.hpp` (header-only) — static allow-lists per tier, checked before RBAC.
- **Output serialization:** Uses local `JObj`/`JArr` string builders (same pattern as `rest_api_v1.cpp`) to avoid the 56GB nlohmann template bloat. `nlohmann::json` is used for parsing only.

## Security Model

- **Three authorization tiers** enforced *before* RBAC: `readonly` (read only), `operator` (+ tag writes, auto-approved executions), `supervised` (all ops via approval workflow).
- **MCP tokens** use the existing API token system (`api_token_store`) with a new `mcp_tier` column. MCP tokens require mandatory expiration (max 90 days).
- **Approval workflow** — Operations that `requires_approval(tier, type, op)` returns true for are routed to the `ApprovalManager`. Admins approve/reject via Settings UI or REST API. All admins see all pending approvals (both AI-initiated and human-initiated).
- **Kill switch:** `--mcp-disable` rejects all `/mcp/v1/` requests with `kMcpDisabled` JSON-RPC error. `--mcp-read-only` blocks non-read tools.
- **Boot-time registration validator (#2383):** `McpServer`'s constructor throws (fatal — the server refuses to boot, `Fatal exception: MCP tool security registration invalid ...` naming every offender, sorted) unless the served `kTools[]` names, the `kToolSecurity` registrations, and the `kWriteTools` read-only-guard set agree exactly (both directions, duplicates rejected), and every registered (securable, operation) pair is inside the closed RBAC catalogues mirrored from `rbac_store.cpp`'s seed (binding test: `test_rbac_store.cpp` "seeded catalogues match the MCP C8 validator mirrors"). Dispatch carries a defense-in-depth pre-gate: a served-but-unregistered tool is denied `kInternalError` (-32603, "tool security registration missing — denied fail-closed"; audit reason `tool security registration missing correlation_id=<cid>` — SIEM rules should prefix-match, the correlation id also appears in the `spdlog::error` line and the A4 envelope — plus the `yuzu_mcp_tool_security_misconfig_total` counter) rather than silently skipping the tier/approval gate; an unknown tool name still returns `kMethodNotFound` untouched, even if a stray registration row exists for it. Note: with `--mcp-disable` the constructor never runs, so a misregistered build boots and only fails when MCP is re-enabled (accepted residual — CI trips the same validator in every test fixture). Runbook: `docs/ops-runbooks/mcp-tool-registration-recovery.md`.
- **Pre-approval input-schema validation (#2405):** inside the C8 approval block, tool arguments are validated against the tool's served `inputSchema` **before** an approval ticket is minted and **before** a recall consumes one — a schema-invalid supervised call can no longer waste an admin's approval or burn a one-time ticket (one check above the mint/recall fork, so the two paths cannot diverge; the degraded no-`ApprovalManager` deny still answers first, and C7/tier denials still precede validation so an unauthorized caller learns nothing about argument validity). The denial is `kInvalidParams` (-32602) with an A4 envelope whose audit row and `error.data` carry the **same** correlation id, plus the `yuzu_mcp_tool_args_invalid_total{tool}` counter (label bounded — only approval-gated tools reach the gate; `server.cpp` pre-seeds exactly that set via `approval_gated_tool_names()`). Validation exists ONLY on the approval-gated path — a deliberate consequence: the same argument shape can be stricter on the supervised tier than on operator (e.g. a typed `params` value is `-32602` supervised, while operator-tier keeps the pre-existing handler coercion via `dump()`); strict typing on the maker-checker path is the product decision, not an accident. Enforcement is the `mcp_input_schema` **subset compiler** (`server/core/src/mcp_input_schema.{hpp,cpp}`): a CLOSED keyword catalogue — `type`/`properties`/`required`/`enum`/`minimum`/`maximum`/`maxLength`/`pattern` (RE2, JSON-Schema search semantics)/`items`/`minItems`/`maxItems`/`additionalProperties` (schema-form or `false`)/`anyOf`-of-required-alternatives, with `description`/`default` ignored — deliberately **not** a conforming JSON-Schema validator; do not claim conformance. Yuzu deviations: `integer` is STRICT (`1.0` rejected — `param_int` only honors integer-typed JSON, so accepting an integral float would validate an argument the handler then silently defaults; out-of-int64 integers rejected for the same reason) and `maxLength` counts **bytes**. Violation paths never carry caller-derived text — a map key validated via `additionalProperties` is reported as the wildcard `*`, so audit rows and envelopes stay free of untrusted argument content. `approval_id` is control-plane, not tool input: a present non-string one is rejected at `/approval_id`; a string one passes every gated schema (declared on `delete_tag`/`quarantine_device`, tolerated as an undeclared property on the rest). Handler-side validation stays as defense in depth. A pre-existing approved-but-unconsumed ticket whose arguments a later-tightened schema rejects becomes unrecallable **fail-closed** (never consumed); approval tickets also lazily expire after 7 days (pending, and approved-unconsumed post-review — PR #1796), so such a stray ticket ages out.
- **Server-side input bounds on `execute_instruction` (#2437):** the `maxLength`/`maxItems` in this tool's served schema are enforced **on every path** by the handler before dispatch, not only on the approval-gated path where the C8 gate validates them. That distinction mattered: the **operator** tier executes with *no* approval, so it had neither the schema check nor a handler check — the tier that needs no human in the loop was the unbounded one. Each rejection is `kInvalidParams` (-32602), an audit row (`result=denied`, `detail` = `input bound exceeded: <reason>`), and `yuzu_mcp_tool_args_too_large_total{tool,reason}` over a closed `reason` set. Bounds are byte counts (matching the compiler's `maxLength`-counts-bytes deviation): `plugin`/`action`/each `agent_ids` entry ≤ 128 B, `scope` ≤ 8192 B, each `params` value ≤ 64 KiB, `agent_ids` ≤ 10000 entries — plus two the closed subset **cannot** express: `params` ≤ 32 keys and each `params` key ≤ 256 B.
  - Those bounds borrow `kMaxParamCountPerStep`/`kMaxParamKeyLen`/`kMaxParamValueLen` from `bundle_service.hpp`, so the two execute surfaces agree on what a param may be — **shape and value size**. They used to disagree 8× on value size (8 KiB here, 64 KiB for a bundle step); that was not a decision, it was an accident of which constant was reached for, and it was documented as deliberate before anyone checked why. The smaller figure was also never *enforced* on the operator tier, so keeping it would have broken content-carrying plugin actions (a `filesystem` write, a script body) that worked in practice.
  - **The cost of that alignment, stated rather than dropped:** a bundle's per-step value cap was sized knowing it is amplified ×N by fan-out, and `execute_instruction` fans out too. Raising the per-call params ceiling from 256 KiB to 2 MiB multiplies what a `scope:"__all__"` dispatch copies per agent by 8×, and `agent_registry`'s gateway path queues a full `CommandRequest` copy per routed agent. That queue is unbounded independently of this change and is tracked separately; MCP nonetheless remains the *tighter* path, because the REST twins accept the same `params` with no bound at all.

  - **Not published, but NOT a ticket burn.** The closed subset has no `maxProperties`/`propertyNames`, so C8 cannot derive these two from the schema — instead `check_exec_instruction_shape` is called explicitly inside the C8 block, above the mint/recall fork, so a 33-param supervised call is denied `-32602` before a ticket is minted or consumed. What remains open is *discoverability*: the two bounds are absent from `tools/list`, so a client learns them only by being refused. Publishing them needs the catalogue extended (#2444).
  - **REST twin asymmetry, recorded here so it is findable:** `POST /api/command` and `POST /api/instructions/{id}/execute` accept the same `{plugin, action, params, scope, agent_ids}` shape under the same `Execution:Execute` and apply **no** bounds at all. #2437 closes this class on the MCP surface only; the REST twins are tracked as a follow-up.
  - **Targeting is type-checked and an empty target set is refused.** A non-string `agent_ids` entry or `scope`, a supplied-but-empty `agent_ids` (published as `minItems: 1`) or empty `scope`, are all rejected rather than dropped — because a target set that empties out falls into the "nothing specified" default, which means the entire fleet, and the caller is told it succeeded. The supervised tier was protected by C8's `items.type=string`; the **operator** tier, which executes with no human in the loop, was not. Every rule the schema *cannot* express lives in one pure function (`check_exec_instruction_shape`) called from BOTH the C8 gate (before a ticket is minted or consumed) and the handler (for the ungated tiers, which never reach C8) — adding a rule at only one of those sites reintroduced a ticket burn twice during review.
  - The schema literals in `kTools[]` and the constants in `mcp_input_bounds.hpp` are **one contract in two places**, and a test reads the served schema back and asserts each literal equals its twin — so bumping one without the other fails a test rather than silently reopening the gap. The charset is deliberately *not* narrowed to `execute_bundle`'s `[a-z0-9_]` identifier rule: dotted server actions are live shipped content (`content/definitions/workflow_management.yaml` ships `plugin: server`, `action: workflow.list`), so importing that rule would reject working calls.

- **Adding a tool (checklist):** a new tool must land in **all** of: `kTools[]` (schema — which must compile under the `mcp_input_schema` closed keyword catalogue above, with every `required` name declared in `properties`; an unsupported keyword or malformed operand is a **boot failure** through the #2383 validator's 4th raw sequence, so the C8 gate can never meet a schema it only partially enforces; an approval-gated tool's schema must NOT set `additionalProperties:false` unless it also declares `approval_id` — otherwise its own recall argument would fail validation and every ticket it mints would be unrecallable; the boot validator enforces this rule, not just this checklist), `kToolAnnotation` (served hints), `kToolSecurity` (securable/operation drawn from the seeded RBAC catalogues), `kWriteTools` **iff** its operation is non-Read, plus its dispatch branch and per-handler `perm_fn`. A missing table entry is a boot failure (and a mass `[mcp]` test failure), by design. Any future per-tool metadata table must be folded into `validate_tool_security_registration` — never a second validator.
- **Reserved on-behalf-of headers rejected (ADR-1005):** MCP registers on the same httplib instance as REST, so the pre-routing chokepoint rejects any `/mcp/v1/` request carrying a reserved on-behalf-of header with `403` before the JSON-RPC layer runs — see `docs/auth-architecture.md` ("On-behalf-of assertions rejected") for the reserved-name list.
- **Transport request-body bound (#2437):** every path under the `/mcp/` prefix (so `/mcp/v1/`, `/mcp/v1`, and a future `/mcp/v2/` by default — the cap matches the scope the auth chokepoint admits) admits only request bodies it can size in advance, enforced in the pre-routing chokepoint — which httplib runs **before it reads the body**, so a rejection costs a header parse rather than megabytes of buffering. Two rejections, both counted by `yuzu_mcp_body_too_large_total{reason}` and logged (throttled, sanitized) since there is no principal to audit pre-auth:
  - **`413`, `reason=over_cap`** — a declared `Content-Length` above **4 MiB**.
  - **`411`, `reason=unmeasurable`** — a request carrying framing or encoding this server is not the sole interpreter of: **any** `Transfer-Encoding` (any value, any method), **any** `Content-Encoding` other than `identity`, or a POST/PUT/PATCH with no `Content-Length`. The rule is deliberately broader than "reject chunked", because matching httplib's parsing by hand is what failed the first time: it tested `Transfer-Encoding` with a case-sensitive substring while httplib compares case-insensitively, so `Transfer-Encoding: Chunked` was admitted as a measurable body and then read as chunked under the 100 MB default — one capital letter defeating the cap. Encodings matter for a second reason: this build compiles `CPPHTTPLIB_BROTLI_SUPPORT`, httplib decompresses transparently and bounds only the **decompressed** size against its global limit, so `Content-Length` on a `Content-Encoding: br` body measures the compressed bytes and is no bound at all on what gets buffered. JSON-RPC clients send an identity-encoded body with a `Content-Length` and are unaffected; a proxy or streaming stack that re-frames requests will be refused, which is a deliberate trade.
  - This is a **per-path** bound, deliberately *not* the server-global `set_payload_max_length`, which would also cap the multipart certificate upload and content distribution on the same httplib instance. Those keep the 100 MB default.
  - **4 MiB is a deliberate clamp, not a ceiling derived from every tool.** It sits above a maximal `execute_instruction` — **~3.27 MiB decoded, about 18% headroom**, down from 62% before the `params` value cap was aligned with `execute_bundle`'s 64 KiB. Read that 18% before widening any `execute_instruction` field bound again: the remaining room is real but no longer generous, and the sizing `static_assert` in `mcp_input_bounds.hpp` fails the build rather than letting a maximal legitimate call start 413-ing. It stays **deliberately below what `execute_bundle`'s own validator accepts**: `validate_bundle_steps` permits 32 steps × 32 params × 64 KiB ≈ 64 MiB, and one saturated step is already ~2 MiB, so a **2-step saturated bundle (~4.02 MiB) is refused before its validator runs.** That product bound was a per-step memory guard for the agent fan-out, never an advertised aggregate — but the asymmetry is real, is **not** shared by the REST twin `POST /api/v1/bundles`, and is pinned by a test. For multi-MiB bundle params, use the REST twin or raise the cap deliberately.
  - **Encoding caveat:** the per-field `execute_instruction` argument caps bound *decoded* bytes while this bounds the *raw* body, and legal `\uXXXX` escaping can inflate a payload several-fold. The tolerance is **1.22×** raw-to-decoded (it was 2.63× before the `params` widening — quantified here rather than described, because the adjective outlived the number it was calibrated to). Plain ASCII and base64 (1.00×), Windows paths at ~8% backslashes (1.08×), JSON-in-a-string at ~12% quotes (1.12×) and text with 3% newlines (1.03×) all fit. An all-quote payload (2×) or raw control bytes (6×) do not, and a simultaneously-saturated maximal call built from them is refused with a `413` telling the caller to reduce the arguments. So: the headroom absorbs realistic escaping of a maximal `execute_instruction`; it is **not** a proof against a maximally-escaped one.
  - **What "maximal" bounds:** the ~3.27 MiB figure covers the *declared* fields. `execute_instruction`'s root schema does not set `additionalProperties: false` and undeclared properties are deliberately tolerated, so a schema-valid call can legitimately exceed it, up to the 4 MiB transport cap. The figure answers "does a legitimate maximal call fit", not "is 3.27 MiB the largest accepted body".
  - **JSON nesting is bounded at 32 levels**, rejected as a `-32700` parse error before the document is built. `nlohmann`'s `dump()` is recursive (its parser and destructor are not), so a ~0.95 MiB body of nested arrays — a quarter of the cap, comfortably admitted by it — segfaults the process, and callers `dump()` caller-supplied values. Guarding an individual `dump()` would miss every other recursive traversal, so the tree is never constructed. The deepest legitimate MCP request is `execute_bundle` at about seven levels.
  - **Deployment caveat:** a rejected body is never read off the socket. httplib stamps `Connection: close` on any status ≥ 400 so a conforming client closes, but if a **reverse proxy is ever placed in front of Yuzu**, an unread `Content-Length` body is a textbook request-smuggling primitive between proxy and origin. The shipped rigs expose the server directly; front it with care.
- **Audit:** Every MCP tool call logged with `action: "mcp.<tool_name>"` and `mcp_tool` field on `AuditEvent`.
- **Response-collection scope (`query_responses`) — #1634, PARTIAL.** A per-agent `check_scoped_permission` filter is applied to the returned rows, **but it is INERT under the current global `Response:Read` gate** — a holder of global `Response:Read` (the only principal that passes the gate) admits every agent, so no rows are dropped and a caller currently **does** see other operators' execution rows by id; a management-group-confined operator is 403'd at the gate before the filter runs. So this does **not** yet provide cross-operator isolation; its only active effect today is failing **closed** (zero rows) on a corrupt/load-failed `rbac.db`. Effective isolation needs the admit-then-filter gate change tracked in #1634. When a row IS dropped (the corrupt-store path), `query_responses` emits a **second** audit row `result=denied` (`detail` carries the distinct dropped-agent count) **in addition to** the `result=success` row — a SIEM rule must treat the two as a pair for one call (informational access-boundary evidence for CC6.1, not a failed call); under normal operation this `denied` row does not fire. RBAC-off → no filter (legacy-open). The result object carries `audit_persisted:false` if any of that call's audit rows could not persist, and `result_truncated_by_cap:true` if the raw query hit the row cap before filtering (incomplete page). *(The same inert per-agent filter + corrupt-store fail-closed now also covers `aggregate_responses`, REST `/executions/{id}/visualization` + `/api/responses/*`; the dashboard `/fragments/results` family and workflow execution-detail reader remain flat-`Response:Read` and **fail OPEN on a corrupt `rbac.db`** — all tracked in #1634.)*

## Error envelope

JSON-RPC error responses from the denial paths (read-only mode, tier policy, approval-required, the #2383 missing-security-registration misconfig deny, and the #2405 pre-approval input-schema deny) carry a structured `error.data` field (A4, per `docs/agentic-first-principle.md`):

```json
{ "correlation_id": "req-<hex-ms>-<hex-seq>", "retry_after_ms": null, "remediation": "use a higher-tier MCP token, or the REST API / dashboard" }
```

> **Supervised-tier / approval-gated operations — ticket-then-recall (#289).**
> An operation for which `requires_approval(tier, type, op)` is true is answered
> with `kApprovalRequired` (-32006). Its `error.data` extends the A4 envelope
> with two extra fields:
>
> ```json
> { "correlation_id": "req-<hex-ms>-<hex-seq>", "retry_after_ms": null,
>   "remediation": "an admin must approve this approval_id (see status_url), then re-call this tool with the approval_id argument to execute",
>   "approval_id": "<32-hex>", "status_url": "/api/v1/approvals/<32-hex>" }
> ```
>
> Before ANY of the below — mint, dedup, recall lookup, consume — the
> arguments must pass the #2405 input-schema validation (Security Model
> above); a schema-invalid call answers `kInvalidParams` (-32602) with
> nothing minted and nothing consumed.
> The **first** call mints an `ApprovalManager` approval (`definition_id =
> "mcp.<tool>"`, `submitted_by` = the caller, `scope_expression` = the
> canonical JSON of the tool arguments) and returns the envelope above. An admin
> approves it (Settings UI / REST `POST /api/approvals/{id}/approve`; reviewer ≠
> submitter is store-enforced, so self-approval is impossible). The caller then
> **re-calls the same tool** passing the returned `approval_id` as an argument;
> the server verifies the approval is (a) approved, (b) for this exact tool
> (`definition_id`), (c) for these exact arguments (canonical-args match,
> `approval_id` excluded from the comparison), and (d) not yet consumed, then
> **atomically consumes it** (one-time; a replay of a consumed ticket, or a
> concurrent second recall, is rejected — the mutating op runs at most once) and
> lets the call through to the handler. A recall against a still-**pending**
> ticket returns the same `kApprovalRequired` envelope (keep polling
> `status_url`); a rejected/expired/mismatched/consumed ticket returns
> `kPermissionDenied` (-32003). This generic gate governs every approval-gated
> tool — the supervised tier's `execute_instruction` / `revoke_certificate` /
> `execute_bundle`, plus `delete_tag` (operator + supervised) and
> `quarantine_device` (supervised). **Degraded path:** if the server has no
> `ApprovalManager` (a stripped deploy / test harness), it cannot mint a pollable
> ticket, so it falls back to a `kTierDenied` (-32004) with no `approval_id`.
> **Note:** the per-tool RBAC check (`perm_fn`) runs on the *recall*, after the
> ticket is consumed, so a token that passes the MCP tier check but fails RBAC
> can mint→approve→then 403 (burning the ticket) — a rare consequence of the
> deliberate tier-then-RBAC two-gate split.

`correlation_id` is a per-error token (`req-<hex-ms>-<hex-seq>`, the same format as the REST `X-Correlation-Id` header) returned to the caller in the error body, so a client can cite a stable handle when reporting a failure. **It is not persisted to the audit log today** — the audit row for a denied call (`mcp.<tool>`) is written separately and does not carry the token — so server-side correlation relies on any `spdlog` line the handler emits at that moment, not on `audit.db`. Two exceptions stamp the SAME token into the audit detail (one-cid pattern): the #2383 misconfig deny (`... correlation_id=<cid>`) and the #2405 input-schema deny (`arguments do not match the tool input schema at '<path>' correlation_id=<cid>`). `retry_after_ms` is `null` on tier/approval-denial errors (the denial is not retryable as-is); `remediation` carries an actionable hint — escalate to a higher-tier token, or use the REST API / dashboard. Per-tool validation errors (e.g. the dex-perf tools) populate `correlation_id`, a `null` `retry_after_ms`, and a field-specific `remediation`. Parse `error.code` for the error class and `error.data.correlation_id` for client-side traceability.

## Phase 1 (Implemented)

- Read-only tools (the **authoritative, complete table** is `docs/user-manual/mcp.md` — this list is illustrative, not a count): `list_agents`, `get_agent_details`, `query_audit_log`, `list_definitions`, `get_definition`, `query_responses`, `aggregate_responses`, `query_inventory`, `list_inventory_tables`, `get_agent_inventory`, `query_installed_software`, `get_tags`, `search_agents_by_tag`, `list_policies`, `get_compliance_summary`, `get_fleet_compliance`, `list_management_groups`, `get_execution_status`, `list_executions`, `list_schedules`, `validate_scope`, `preview_scope_targets`, `list_pending_approvals`, `get_guardian_schemas`, `list_dex_signals`, `get_dex_signal_scope`, `get_dex_signal_detail`, the DEX-perf + network tools, and `list_issued_certs`
  - **`query_installed_software`** is the typed daily-sync software-inventory read (ADR-0016), gated on `Inventory:Read` (with a per-agent management-group drop filter that is **not yet verified effective under the global gate — see ADR-0017 / #1716**) — distinct from the generic `query_inventory`/`get_agent_inventory` (generic blob store, `Infrastructure:Read`).
  - **DEX read tools (`list_dex_signals` / `get_dex_signal_scope` / `get_dex_signal_detail`)** are the MCP parity for the `/api/v1/dex/*` REST surface — same `GuaranteedStateStore` aggregations, gated on `GuaranteedState:Read`, with a `window` of `24h`/`7d`/`30d`/`all` and an optional `os` filter (`all`/`windows`/`linux`/`macos`) on `list_dex_signals` + `get_dex_signal_detail` that scopes the rollup / drill-down lists to one OS (the drill-down echoes the applied `os` and keeps `by_os` cross-OS), matching the dashboard and REST twins. The audit boundary mirrors REST: the rollup and per-OS scope are fleet aggregates (only the generic `mcp.<tool>` tool-call audit), while `get_dex_signal_detail` returns a most-affected **devices** list (behavioral) and additionally emits a **`dex.signal.view`** audit (`target_type=ObsType`) so one SIEM filter catches the dashboard, REST and MCP behavioral-access surfaces alike. `obs_type` is validated against `[A-Za-z0-9._-]{1,64}` (malformed → `kInvalidParams`). When the `dex.signal.view` audit row cannot persist, `get_dex_signal_detail` **set-and-proceeds** and carries `audit_persisted:false` in the result (absent on success — consumers key on absence), matching the `query_responses` / `revoke_certificate` convention; JSON-RPC has no header channel, so this is the MCP equivalent of the REST `Sec-Audit-Failed` header (#1647). The REST `dex.signal.view` sibling instead fails closed — different surface, different posture.
- Write/execute tools (the authoritative table is `docs/user-manual/mcp.md`): `execute_instruction` — dispatches plugin commands to agents (auto-approved for `operator` tier; `supervised` tier is approval-gated via the ticket-then-recall flow; if neither `scope` nor `agent_ids` is provided, targets all agents) — `execute_bundle` (below), `revoke_certificate`, and the five Issue-13.5 write tools `set_tag`, `delete_tag`, `approve_request`, `reject_request`, `quarantine_device` (#289).
  - **The five write tools (#289 / Issue 13.5)** are the last-mile agentic write surface: `set_tag` (`Tag:Write`, fires the agent tag-push), `delete_tag` (`Tag:Delete`, approval-gated on operator + supervised), `approve_request` / `reject_request` (`Approval:Approve`, supervised tier — reviewer ≠ submitter store-enforced), and `quarantine_device` (`Security:Execute`, supervised, approval-gated — records the quarantine *and* dispatches the live quarantine-plugin isolation). The approval-gated members flow through the ticket-then-recall mechanism documented under **Error envelope** above.
- **Live-query bundle tools (`execute_bundle` / `get_bundle_result`)** — MCP parity for the `POST`/`GET /api/v1/bundles` REST surface (ADR-0011). `execute_bundle` (write/execute, `Execution:Execute`) fans one instruction into 1–32 plugin actions on **one** device via server-side async fan-out and returns `{execution_id, expected}` immediately; `get_bundle_result` (`Response:Read`) collates to `{complete, received, expected, steps[]}` in request order. Use instead of N `execute_instruction` calls when refreshing a device (N round-trips → 1). The agent is unchanged — each step is an ordinary command under one `bundle-…` correlation id; per-step `bundle.<plugin>.<action>` audit (`target_type=Agent`) mirrors REST, and collate enforces an ownership (IDOR) guard. Bundles are caller-polled, **not** in the executions drawer; v1 manifests are per-surface + in-memory (durable Postgres store is a committed follow-up — ADR-0011).
- **Periodic access review tools (`export_access_review` / `open_access_review` / `record_attestation` / `get_access_review` / `list_access_reviews` / `close_access_review`)** — MCP twins of the `/api/v1/access-reviews*` REST surface (SOC 2 CC6.2; full doc: `docs/auth-architecture.md` "Periodic access reviews"). `export_access_review`, `get_access_review`, and `list_access_reviews` carry `readOnlyHint:true`. **`record_attestation` carries `destructiveHint:true`** — it is an UPSERT: a second call for the same `(campaign_id, principal_type, principal_id, role_name)` overwrites the prior reviewer's decision/reviewer/justification, with no retained history of the earlier decision. The read tools (`export_access_review`, `get_access_review`, `list_access_reviews`) carry `readOnlyHint:true`, and `open_access_review` is `destructiveHint:false` (it mints a new campaign but touches no existing state). **`close_access_review` carries `destructiveHint:true`** — a one-way `open`→`closed` lifecycle transition (no reopen path) that permanently freezes outstanding attestations (corrected 2g PR 2, was shipped `false`). **`record_attestation`'s `decision:"flagged_revoke"` still records evidence only and never itself revokes the underlying grant** (flag ≠ revoke — acting on a flag is a separate, explicit role-unassignment or engine-principal-revoke call; the destructive part is the decision-overwrite, not a live grant mutation). JSON only: the REST `?format=csv` export has no MCP equivalent — a worker that wants a CSV download uses the REST endpoint directly. All six are gated on a **global**, **dedicated** `AccessReview:Read`/`AccessReview:Attest` (not `AuditLog:Read`/`AuditLog:Attest` — an earlier round gated on the latter, which over-disclosed the fleet-wide grant population to the `Operator`/`PlatformEngineer` roles; see `docs/security-reviews/access-reviews-2026-07-21.md` "#2225 round 2"), not a management-group-confined read (see the #2225 chokepoint note in `docs/user-manual/rest-api.md` "Access Reviews"), and every one of them — reads included — structurally denies a caller whose own session is engine-classed (the shared `deny_engine_session` belt).
- 3 resources: `yuzu://server/health`, `yuzu://compliance/fleet`, `yuzu://audit/recent`
- 4 prompts: `fleet_overview`, `investigate_agent`, `compliance_report`, `audit_investigation`

## Phase 2.5 (Implemented — MCP Streamable HTTP transport, track 2f PR 1 + PR 2)

The session-lifecycle + transport pre-check half of the Streamable HTTP transport is **live** (ADR-1005 execution plan **Decision 15 / track 2f** PR 1). Shipped:

- **`Mcp-Session-Id` sessions.** `initialize` mints a principal-bound ≥128-bit CSPRNG session id and returns it as the additive `Mcp-Session-Id` response header. Sessions are never *required* (plain-POST clients are unaffected); when a client presents one on a later request it is validated (unknown / expired / bound-to-another-principal → `404`, indistinguishable from never-existed — no cross-principal oracle — and the client re-initializes). `DELETE /mcp/v1/` ends a session. State is in-memory and bounded (idle TTL, per-principal + global caps that **reject** rather than evict a live session); a server restart drops sessions and the client re-initializes, per spec.
- **`Origin` validation** on every method against a configured allowlist (`--mcp-allowed-origin`; absent Origin allowed on this credential-gated endpoint, empty allowlist rejects any present Origin).
- **`MCP-Protocol-Version` negotiation.** Supported revisions `2025-03-26` and `2025-06-18`; `initialize` echoes the client's requested version when supported, else the `2025-03-26` baseline. A present-but-unsupported header → `400`. The negotiated revision is recorded on the `yuzu_mcp_initialize_protocol_total{revision}` counter (bounded to the supported set) so a future revision deprecation has usage data (track 2g PR 1).
- **`initialize.instructions` orientation blob** (track 2g PR 1, invariant A5 item 6). The `initialize` result carries a static, operator-authored `instructions` string orienting a fresh client — what Yuzu is, the operating model, a tool-family index, and where discovery starts. It is single-sourced with the `yuzu://about` + `yuzu://operating-model` resources (`server/core/src/mcp_orientation.{hpp,cpp}`) so the handshake and those resources cannot drift, and it is **static compiled-in content only** — never fleet-derived data, which would be a prompt-injection channel into every fresh client.
- **Notification POSTs answer `202`** (spec MUST; was `204`).
- **Kill switch** `--mcp-no-streaming` (no minting; `GET`/`DELETE` → `405`; plain JSON-RPC POST only) and audit verbs `mcp.session.open` / `mcp.session.close` / `mcp.session.reject` (the last on every denial — origin, unknown session, cap, protocol-version).
- New JSON-RPC error codes: `-32007` unknown session (`404`), `-32008` origin rejected (`403`), `-32009` bad protocol version (`400`), `-32010` session cap (`429`). Each carries the shared A4 `error.data` (a `correlation_id`, the always-present nullable `retry_after_ms`, and a `remediation`), built by the single `error_response_a4` helper so the transport denials match the REST/tool-call A4 envelope.

Session state is in-memory only and deliberately does **not** gate `/readyz`. Operator reference: `docs/user-manual/server-admin.md` (flags + Upgrade Notes) and `docs/user-manual/mcp.md`.

### The GET SSE channel (PR 2)

`GET /mcp/v1/` is the session's server→client channel. It replaces the PR-1 `405` placeholder:

- **Attach.** Requires the session's `Mcp-Session-Id` (absent → `400`; unknown / expired / another principal's → `404`) and `Accept: text/event-stream` (missing → `406`, `-32011`; wildcards like `*/*` deliberately do **not** opt in). Heartbeats every ~3 s keep intermediaries from idling the connection out; `X-Accel-Buffering: no` defeats reverse-proxy response buffering.
- **Resume.** Each session has its own bounded replay ring and its own event-id namespace starting at 1 (ids are **never** global, so a cursor from one session can never address another's frames). A reconnect with `Last-Event-ID` replays exactly the frames it missed. If the cursor's frames have already been evicted from the ring — or the cursor is one the server never issued — the session is **terminated** and the request `404`s: the client re-initializes, and durable results remain fetchable by `execution_id`. There is no silent gap, and the GET's answer is coherent with the client's next POST (which `404`s too).
- **Revocation.** The credential that opened a stream is re-validated on **every heartbeat tick**, so a revoked token or a signed-out session kills a *live* stream, not merely future attaches — the close frame says `credential_revoked`. Latency is one tick on a single server. Across **replicas** it is bounded by the 60 s token-cache TTL plus a tick, and that bound is an API-**token** property: the token cache is process-local, so a revoke handled by one replica reaches another replica's stream only when that replica's cache entry expires and it re-reads the store. Cookie sessions are per-process and in-memory, so a cookie-authenticated stream does not exist on another replica at all. Treat CC6.2 revocation latency as bounded by that, not as instantaneous. A stream authenticated by an **engine** principal carries a second, shorter bound of the same kind: its per-tick backing-principal check is served from a 15 s liveness cache (#2367), so revoking the *principal* on one replica reaches another replica's stream within that TTL plus a tick — on the replica handling the revoke it is **one tick**, the same bound as the token/session case above: the store invalidates its own cache synchronously with the write, so the next heartbeat tick reads through and observes the dead principal rather than serving a stale cached hit. An **unreachable** auth store is not a revocation: it is reported as indeterminate and buys a bounded 60 s grace window, after which the stream ends with the distinct reason `auth_unavailable`. For an **engine**-authenticated stream that window is measured from the stream's last **authoritative** credential confirmation, not from the tick the outage was first noticed — a cached answer keeps such a stream running but does not re-start its budget, so cache residency and the grace window cannot add up to more than the window itself, and a stream already riding a near-expired cache entry when the outage begins gets correspondingly less than the full 60 s. That guarantee is engine-specific: an **API-token**-authenticated stream still treats a token-cache hit as a fresh confirmation, so for those the token-cache residency and the grace window can still add (pre-existing, tracked as #2447). That distinction exists so an auth-backend blip cannot cut every stream on the fleet at once, and so an operator can tell a security event from an outage.
- **Caps.** Every held-open SSE response pins one HTTP worker for its whole life, so concurrency is admission-controlled — and **every** streaming surface leases from the same budget (MCP GET, `GET /api/v1/events`, the dashboard executions drawer, the legacy `/events` stream), because the worker pool is what they all share (ADR-0034). Capacity is `--max-sse-streams` (default 128, and the worker pool is sized *from* it); `--mcp-max-streams-per-principal` (default 4) is an anti-monopoly policy for the MCP surface, not a capacity limit. A cap hit **rejects the newcomer** with `429` (`-32012`) carrying an honest `retry_after_ms` — it never evicts a live stream. Utilisation: `yuzu_http_held_open_responses / yuzu_http_held_open_capacity`.
- **Takeover.** A second GET on a session supersedes the first (the old stream closes with `superseded`) rather than being rejected: the common second GET is a client reconnecting across a zombie TCP the server has not noticed yet, and rejecting it would lock that client out for a full write-timeout. It is admitted without a cap check but still takes a lease — a superseded provider goes on pinning its HTTP worker until it drains, and an *uncounted* pinned worker is exactly the hole the budget exists to close. The pool is bounded structurally instead: a session holds at most one draining stream, so a *third* concurrent GET on the same session gets `429 stream_handover_pending` until the handover completes, and the budget reserves two workers for every stream it admits.
- **Close reasons** are wire-visible and audited (`mcp.stream.attach` / `mcp.stream.close`): `client_disconnect`, `superseded`, `session_terminated`, `credential_revoked`, `auth_unavailable`. The close is delivered as a JSON-RPC `notifications/yuzu.stream_closed` notification carried as a normal `message` on the stream (2f PR 3b) — not a bespoke `event: stream-closed`, which a spec MCP client parsing JSON-RPC off the stream would never see. Its `params` carry the machine-parseable `reason` in the same A4 shape (`reason` / `correlation_id` / `retry_after_ms` / `remediation`) as every denial on this route, so a client has one error contract, not two. The frame is off-ring and id-less: a close is a point-in-time terminal signal, never replayed.

PR 2 gave the channel heartbeats and replayed frames; **PR 3a shipped its first producer**, the progress bridge (`notifications/progress` - see "Progress bridge (2f PR 3a)" below). Metrics: `yuzu_mcp_sessions_active`, `yuzu_mcp_sessions_opened_total`, `yuzu_mcp_streams_active`, `yuzu_mcp_streams_handover_pending`, `yuzu_mcp_streams_cap` (the EFFECTIVE cap after the boot clamp), `yuzu_mcp_stream_replay_ring_evictions_total`, `yuzu_mcp_stream_frames_dropped_total` (frames dropped before reaching a connection — usually a slow consumer's per-connection queue overflow, also a rare producer-side post-commit allocation failure (#2366); recoverable via Last-Event-ID), `yuzu_mcp_stream_frames_too_large_total` (a frame exceeded the per-frame byte cap and was truncated before entering the ring — counted rather than only logged, because an unbounded warn-per-publish is a log-flood vector), `yuzu_mcp_stream_rejects_total{reason}`, `yuzu_mcp_stream_closes_total{reason}` (alert on `auth_unavailable` and `internal_error`), `yuzu_mcp_stream_publish_failures_total` (a `publish()` call failed before the frame committed — pre-commit only; the frame was never published and no event id was consumed. A post-commit sink-enqueue failure instead counts as a normal `frames_dropped_total`/events-dropped gap. Non-fatal by construction but a near-miss for a worker-thread `std::terminate` — ticket on any `increase() > 0` over 15 m, do not page). Progress-bridge families (2f PR 3a): `yuzu_mcp_bridge_records_active`, `yuzu_mcp_bridge_reject_total{reason}`, `yuzu_mcp_bridge_degrade_total{reason}`, `yuzu_mcp_bridge_listener_failures_total`, `yuzu_mcp_bridge_mailbox_drops_total`, `yuzu_mcp_bridge_projector_cycles_total`, `yuzu_mcp_stream_terminal_publish_failures_total`, `yuzu_mcp_stream_final_unpinned_total` - each with its alerting posture in `docs/user-manual/metrics.md`.

**Shutdown:** httplib re-checks its shutdown flag between provider calls, so `stop()` drains live streams within about one heartbeat tick (~3 s, in parallel). A stream whose peer has stopped reading is bounded instead by the 30 s socket write timeout — size a container termination grace period above that if you run streaming clients.

## Progress bridge (2f PR 3a)

**Shipped.** When a `tools/call` for `execute_instruction` carries `_meta.progressToken`, the server correlates that request to its execution and projects `ExecutionEventBus` events onto the session's **GET** channel as `notifications/progress` (`progress`/`total` = agents responded / agents targeted), followed by the terminal result.

**Interim lifecycle shape (the GET-only rung).** In this rung the progress frames are delivered on the GET channel *after* the `tools/call` JSON-RPC response has already retired the request. A strict reading of the MCP progress lifecycle expects progress *before/during* an in-flight request, so this is a deliberate, recorded deviation: it is authorized in the A5 exception ledger (`docs/agentic-first-principle.md`, issue #2439) and is closed by the 2f **3b** streamed-POST rung, which delivers progress before the response. Stock SDK clients *drop* (they do not reject) frames for a token whose request has already retired, so the documented fallback is to poll by `execution_id`.

**Degradation is silent and safe.** If the bridge cannot correlate a request (capacity, unknown session, allocation failure), the call falls back to the plain response - which is self-sufficient, carrying `execution_id` - and counts `yuzu_mcp_bridge_degrade_total{reason}`. Live progress is an enhancement, never a dependency.

**Monotonicity.** `progress` is strictly increasing on the wire, as the MCP spec requires: the projector holds a per-record watermark and suppresses any snapshot that would not advance it.

**Terminal durability.** A terminal frame is pinned in the replay ring so a reconnecting client can still receive it; the `publish_final -> fallback -> poison` ladder (Decision 15(f)), with `yuzu_mcp_stream_terminal_publish_failures_total` and `yuzu_mcp_stream_final_unpinned_total`, makes any failure to do so visible rather than silent. Results always remain durably fetchable by `execution_id`.
