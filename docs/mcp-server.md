# MCP (Model Context Protocol) Server

Yuzu embeds an MCP server at `POST /mcp/v1/` using JSON-RPC 2.0 transport. This allows AI models (e.g., Claude Desktop) to securely query fleet status, check compliance, investigate agents, and — with appropriate authorization — execute instructions on endpoints.

CLAUDE.md keeps only the load-bearing invariants (embed point, tier-before-RBAC ordering, kill switches, audit pattern). This document is the full architecture and tool reference.

## Architecture

- **Embedded in existing server** — MCP runs inside the same cpp-httplib server as the REST API and dashboard. It reuses auth middleware, RBAC, rate limiting, CORS, and audit logging with zero duplication.
- **Module:** `server/core/src/mcp_server.hpp` / `mcp_server.cpp` — mirrors `RestApiV1` pattern (injected store pointers, same callback signatures).
- **JSON-RPC helpers:** `mcp_jsonrpc.hpp` (header-only) — parse/build JSON-RPC 2.0 envelopes.
- **Tier policy:** `mcp_policy.hpp` (header-only) — static allow-lists per tier, checked before RBAC.
- **Output serialization:** Uses local `JObj`/`JArr` string builders (same pattern as `rest_api_v1.cpp`) to avoid the 56GB nlohmann template bloat. `nlohmann::json` is used for parsing only.

## Security Model

- **Three authorization tiers** enforced *before* RBAC: `readonly` (read only), `operator` (+ tag writes, auto-approved executions **except the ~42 `plugin.action` pairs a compiled `ExecuteGate` marks `AdminOrApproval`/`AlwaysApproval` (#1398)** — those still deny `operator`-tier execute_instruction with no approval provenance, at the shared dispatch chokepoint below the MCP-tier layer), `supervised` (all ops via approval workflow).
- **MCP tokens** use the existing API token system (`api_token_store`) with a new `mcp_tier` column. MCP tokens require mandatory expiration (max 90 days).
- **Approval workflow** — Operations that `requires_approval(tier, type, op)` returns true for are routed to the `ApprovalManager`. Admins approve/reject via Settings UI or REST API. All admins see all pending approvals (both AI-initiated and human-initiated).
- **Kill switch:** `--mcp-disable` rejects all `/mcp/v1/` requests with `kMcpDisabled` JSON-RPC error. `--mcp-read-only` blocks non-read tools.
- **Boot-time registration validator (#2383):** `McpServer`'s constructor throws (fatal — the server refuses to boot, `Fatal exception: MCP tool security registration invalid ...` naming every offender, sorted) unless the served `kTools[]` names, the `kToolSecurity` registrations, and the `kWriteTools` read-only-guard set agree exactly (both directions, duplicates rejected), and every registered (securable, operation) pair is inside the closed RBAC catalogues mirrored from `rbac_store.cpp`'s seed (binding test: `test_rbac_store.cpp` "seeded catalogues match the MCP C8 validator mirrors"). Dispatch carries a defense-in-depth pre-gate: a served-but-unregistered tool is denied `kInternalError` (-32603, "tool security registration missing — denied fail-closed"; audit reason `tool security registration missing correlation_id=<cid>` — SIEM rules should prefix-match, the correlation id also appears in the `spdlog::error` line and the A4 envelope — plus the `yuzu_mcp_tool_security_misconfig_total` counter) rather than silently skipping the tier/approval gate; an unknown tool name still returns `kMethodNotFound` untouched, even if a stray registration row exists for it. Note: with `--mcp-disable` the constructor never runs, so a misregistered build boots and only fails when MCP is re-enabled (accepted residual — CI trips the same validator in every test fixture). Runbook: `docs/ops-runbooks/mcp-tool-registration-recovery.md`.
- **Service-scoped token default-deny at C8 (#2298 PR 3 — "the flip"):** every `kToolSecurity` row now also carries a `ServiceScopeClass` (`denied` | `confined` | `global_safe`, default `denied`). The check runs inside the same C8 block, immediately after the row lookup and BEFORE `tier_allows`/approval: a service-scoped token (`session->token_scope_service` non-empty) on a `denied`-class tool is refused `kPermissionDenied` structurally, before tier or approval ever run — the MCP-side twin of `AuthRoutes::require_permission`'s (REST-side) service-scoped default-deny branch (`docs/auth-architecture.md` "Service-scoped token fleet-wide confinement"). `confined` and `global_safe` both proceed past this check; `confined` is NOT a claim the tool is actually usable by a service-scoped caller — it means the tool's own downstream mechanism (`perm_fn`/`scoped_perm_fn`, or as of #3290 `fleet_read_fn_`/`require_fleet_read`) provides the real confinement. For most `confined` tools today that downstream mechanism is still a `perm_fn`/`scoped_perm_fn` check under the seeded-empty allow-list, so the tool commonly still 403s downstream; `query_installed_software` and, as of #1700/#3290 Phase 2, `get_agent_details` are the exceptions so far — their `fleet_read_fn_` confinement is real, not a still-denying placeholder (`docs/auth-architecture.md` "Phase 2 progress"). `global_safe` rows are boot-validated against `kServiceScopeGlobalSafe` (`service_scope_policy.hpp`) — a `global_safe` row with no matching allow-list entry is a boot failure, the same fail-fast posture as the #2383 validator above. Widening `kServiceScopeGlobalSafe` is a security decision (security-guardian sign-off), never inferred from adding a tool. Full design: `docs/adr/1006-service-scope-default-deny.md`.
- **Pre-approval input-schema validation (#2405):** inside the C8 approval block, tool arguments are validated against the tool's served `inputSchema` **before** an approval ticket is minted and **before** a recall consumes one — a schema-invalid supervised call can no longer waste an admin's approval or burn a one-time ticket (one check above the mint/recall fork, so the two paths cannot diverge; the degraded no-`ApprovalManager` deny still answers first, and C7/tier denials still precede validation so an unauthorized caller learns nothing about argument validity). The denial is `kInvalidParams` (-32602) with an A4 envelope whose audit row and `error.data` carry the **same** correlation id, plus the `yuzu_mcp_tool_args_invalid_total{tool}` counter (label bounded — only approval-gated tools reach the gate; `server.cpp` pre-seeds exactly that set via `approval_gated_tool_names()`). Validation exists ONLY on the approval-gated path — a deliberate consequence: the same argument shape can be stricter on the supervised tier than on operator (e.g. a typed `params` value is `-32602` supervised, while operator-tier keeps the pre-existing handler coercion via `dump()`); strict typing on the maker-checker path is the product decision, not an accident. Enforcement is the `mcp_input_schema` **subset compiler** (`server/core/src/mcp_input_schema.{hpp,cpp}`): a CLOSED keyword catalogue — `type`/`properties`/`required`/`enum`/`minimum`/`maximum`/`minLength`/`maxLength`/`pattern` (RE2, JSON-Schema search semantics)/`items`/`minItems`/`maxItems`/`additionalProperties` (schema-form or `false`)/`anyOf`-of-required-alternatives, with `description`/`default` ignored — deliberately **not** a conforming JSON-Schema validator; do not claim conformance. Yuzu deviations: `integer` is STRICT (`1.0` rejected — `param_int` only honors integer-typed JSON, so accepting an integral float would validate an argument the handler then silently defaults; out-of-int64 integers rejected for the same reason) and `minLength`/`maxLength` count **bytes** (for `maxLength` that is stricter than counting codepoints; for `minLength` it is looser above 1, and exact at `minLength: 1` — the not-empty case). Violation paths never carry caller-derived text — a map key validated via `additionalProperties` is reported as the wildcard `*`, so audit rows and envelopes stay free of untrusted argument content. `approval_id` is control-plane, not tool input: a present non-string one is rejected at `/approval_id`; a string one passes every gated schema (declared on `delete_tag`/`quarantine_device`, tolerated as an undeclared property on the rest). Handler-side validation stays as defense in depth. A pre-existing approved-but-unconsumed ticket whose arguments a later-tightened schema rejects becomes unrecallable **fail-closed** (never consumed); approval tickets also lazily expire after 7 days (pending, and approved-unconsumed post-review — PR #1796), so such a stray ticket ages out. **Post-consume ("semantic") burn (#2444 item 3):** args that pass the schema still consume a ticket, and the handler's own business/state check can still reject them — that residual class is alertable via `yuzu_mcp_approval_burned_total{tool,reason}`, wired via a `BurnGuard` RAII object that inspects the ACTUAL JSON-RPC response at function-scope exit (a per-request flag set only after `consume_ticket()` succeeds) — deliberately NOT wired inside `mcp_audit`, since several handlers' business-rejection paths (e.g. `revoke_certificate`'s "serial not found") never call `mcp_audit` at all and would otherwise silently under-count. `reason` is a single literal (`handler_reject`) today. Unlike the pre-consume counters above, this one fires strictly *after* a ticket is spent. It does not interact with the per-submitter `kMcpSubmitterPendingCap` (25): `pending_count_for()` counts only `status='pending'` rows and `consume_ticket()` never touches `status`, so a ticket already left the pending bucket at admin-approval time — before it can ever reach this burn class.
- **Server-side input bounds on `execute_instruction` (#2437):** the `maxLength`/`maxItems` in this tool's served schema are enforced **on every path** by the handler before dispatch, not only on the approval-gated path where the C8 gate validates them. That distinction mattered: the **operator** tier executes with *no* approval, so it had neither the schema check nor a handler check — the tier that needs no human in the loop was the unbounded one. Each rejection is `kInvalidParams` (-32602), an audit row (`result=denied`, `detail` = `input bound exceeded: <reason>`), and `yuzu_mcp_tool_args_too_large_total{tool,reason}` over a closed `reason` set. Bounds are byte counts (matching the compiler's `maxLength`-counts-bytes deviation): `plugin`/`action`/each `agent_ids` entry ≤ 128 B, `scope` ≤ 8192 B, each `params` value ≤ 64 KiB, `agent_ids` ≤ 10000 entries — plus two the closed subset **cannot** express: `params` ≤ 32 keys and each `params` key ≤ 256 B.
  - Those bounds borrow `kMaxParamCountPerStep`/`kMaxParamKeyLen`/`kMaxParamValueLen` from `bundle_service.hpp`, so the two execute surfaces agree on what a param may be — **shape and value size**. They used to disagree 8× on value size (8 KiB here, 64 KiB for a bundle step); that was not a decision, it was an accident of which constant was reached for, and it was documented as deliberate before anyone checked why. The smaller figure was also never *enforced* on the operator tier, so keeping it would have broken content-carrying plugin actions (a `filesystem` write, a script body) that worked in practice.
  - **The cost of that alignment, stated rather than dropped:** a bundle's per-step value cap was sized knowing it is amplified ×N by fan-out, and `execute_instruction` fans out too. Raising the per-call params ceiling from 256 KiB to 2 MiB multiplies what a `scope:"__all__"` dispatch copies per agent by 8×, and `agent_registry`'s gateway path queues a full `CommandRequest` copy per routed agent. That queue is unbounded independently of this change and is tracked separately; MCP nonetheless remains the *tighter* path, because the REST twins accept the same `params` with no bound at all.

  - **Not published, but NOT a ticket burn.** The closed subset has no `maxProperties`/`propertyNames`, so C8 cannot derive these two from the schema — instead `check_exec_instruction_shape` is called explicitly inside the C8 block, above the mint/recall fork, so a 33-param supervised call is denied `-32602` before a ticket is minted or consumed. What remains open is *discoverability*: the two bounds are absent from `tools/list`, so a client learns them only by being refused. Publishing them needs the catalogue extended (#2444).
  - **REST twin asymmetry, recorded here so it is findable:** `POST /api/command` and `POST /api/instructions/{id}/execute` accept the same `{plugin, action, params, scope, agent_ids}` shape under the same `Execution:Execute` and apply **no** bounds at all. #2437 closes this class on the MCP surface only; the REST twins are tracked as a follow-up.
  - **REST twin asymmetry, TARGETING — CLOSED (#2500).** The bullet above is about argument *size*, which remains open on REST. Targeting does not. `POST /api/command` and `POST /api/instructions/{id}/execute` used to **widen a supplied-but-empty target to the whole fleet**, a class #2437 had closed on MCP only. `/api/command` dropped non-string `agent_ids` entries in `extract_json_string_array` and then fell through to `send_to_all` when the list emptied, so `{"agent_ids":[1,2,3]}` from a client emitting numeric device ids dispatched fleet-wide under plain `Execution:Execute` — and audited as a success; the destructive-action guard that would have caught it is reached only for `kDestructiveActionSecurable`, which holds exactly one entry (`tar.purge_source`). `/api/instructions/{id}/execute` `400`d on `[1,2,3]`, but only because `get<std::string>()` threw into a generic catch, and it broadcast on `[]`, on a non-array `agent_ids`, and on a non-string `scope`. Both routes now refuse every one of those shapes with a `400`, a `yuzu_server_dispatch_target_rejected_total{route,reason}` increment and an audit row (`result=denied`, `detail=reason=<reason>`) — while an **omitted** target still means "the whole fleet" on both, which is the half of the rule a careless fix breaks. The rule and its closed reason set live in `server/core/src/dispatch_target_shape.hpp`, the same function `check_exec_instruction_shape` now delegates to, so MCP and REST cannot drift on what a target is. Still distinct from #1788, which covers scope *confinement*: fixing that would bound the blast radius to an operator's visible devices but would still let a specific-looking target list become "everything you can see". **Destructive-classified pairs are the one exception to "omitted means the fleet" — see the next bullet.**
  - **MCP `execute_instruction` gains the Destructive-class targeting refusal REST already had — CLOSED (#3685).** `/api/command`'s Destructive-class gate (one hardcoded `tar.purge_source` row historically, generalized to the full registry-classified catalogue in the #1.9 dispatch-chokepoint work) had no MCP equivalent: a Destructive `plugin.action` pair (17 rows today, e.g. `tar.purge_source`, `filesystem.delete_lines`, `registry.delete_key`) reached the shared dispatch chokepoint with `scope`/broadcast targeting — including the omitted-target `__all__` normalization the bullet above documents as intended for every OTHER pair. **An authorized caller** (an ordinary grant on the row's resolved securable — most Destructive rows need no admin/approval, e.g. `tar.purge_source` needs only `Infrastructure:Delete`) **dispatched normally and succeeded fleet-wide**, with no denial at all. A caller holding no grant for the row's securable WAS refused by the pre-existing chokepoint, but that denial surfaced only as the ambiguous `sent=0`/`no_agents_reached` envelope an offline/unreachable agent also produces — never a discriminated refusal naming the reason, and not the exposure that mattered here. It now refuses with the same `-32602`/`kInvalidParams` shape and the SAME message REST's `/api/command` 400 arm uses (`dispatch_destructive_gate.hpp`'s shared constant): `destructive action requires explicit in-scope agent_ids; broadcast and scope fan-out are refused`. Two gate sites, both required: the C8 pre-mint block (`tool_name=="execute_instruction"`, before an approval ticket is created or consumed — so a Destructive call on the `supervised` tier never wastes an admin's approval or burns a ticket on a call that was always going to be refused) and the main-handler backstop (the same pure function, the same shape-checked inputs, so the two sites are provably unable to disagree — it exists because `operator` tier's `requires_approval()` is false, so C8's entire approval block, including this check, is skipped for it entirely). The capability classifier (`ClassifyFn`, wired unconditionally at boot from `CommandCapabilityRegistry::classify`) is **fail-closed when unwired**: if it is ever unset, EVERY `execute_instruction` call — not only Destructive ones — is refused `kInternalError` with a distinguishable "classifier unavailable" denial, rather than silently reaching dispatch unclassified. A wired-but-inconclusive classify result (`Unclassified`/`Ambiguous` — the different case from unwired) was handled DIFFERENTLY at the two gate sites when this gate shipped: REST's `/api/command` switch keeps Policy B today (not independently denied — falls through to the shared dispatch chokepoint's own denial), and the C8 pre-mint site denies a classify-miss LOCALLY, minting no ticket — reusing the chokepoint's own `unclassified`/`ambiguous` denial reasons (`yuzu_server_dispatch_denied_total{reason}`, not the targeting-refusal series) rather than a new taxonomy. **The main-handler backstop's own Policy B fall-through is superseded by #3687 below**: a classify-miss reaching the main handler is now denied locally there too, by the pre-dispatch authorization dry run, rather than falling all the way through to `dispatch_fn`. C8 is the one site where Policy B's own reasoning (an early denial would only duplicate, never prevent, the chokepoint's evidence) did not fully apply even before #3687: falling through there let a classify-miss call mint an approval ticket and wait on a human before the chokepoint denied it anyway on actual dispatch — a real approval burned on a call that was always going to be refused. Counted on `yuzu_server_dispatch_target_rejected_total{route="mcp",reason="destructive_untargeted"}` (mutually exclusive with the `route="command"` REST arm — a call refuses at exactly one of the two surfaces) and audited (`result=denied`). The audit `detail` string differs by which of the two gate sites denied: Gate 8 round 3 prefixed the C8 pre-mint site's detail with `reason=` (`reason=destructive_untargeted <plugin>:<action>`) to match the shape of C8's own `ClassifyMiss` arm above; the main-handler backstop's detail is still the older, un-prefixed form (`destructive_untargeted <plugin>:<action>`) — a residual asymmetry, left as-is because the backstop is a different switch, out of this PR's C8-only scope. `POST /api/instructions/{id}/execute`, the dashboard execute surface, and MCP `execute_bundle` do not yet enforce this gate — tracked as a follow-up.
  - **MCP `execute_instruction` discriminates every dispatch-chokepoint denial reason instead of collapsing them into `no_agents_reached` — CLOSED (#3687).** The bullet above closed ONE denial reason (Destructive-untargeted, a targeting-SHAPE refusal that never reaches the shared chokepoint at all). Every reason the chokepoint itself can produce — `Unclassified`/`Ambiguous`/`AnonymousOperator`/`Forbidden`/`ApprovalRequired`/`KillSwitched` (`DispatchDenialReason`, `agent_registry.hpp`) — was, until now, reachable only by falling all the way through the main handler to `dispatch_fn`, which enforced the denial correctly but reported it as the SAME `agents_reached:0`/`no_agents_reached` envelope an empty target set or an offline/unreachable agent also produces (the gap the `#1398`-era note on the `execute_instruction` tool-table entry above used to describe as "tracked as #1398 Rung 4, not yet shipped" — that note is now stale; see it for the historical framing). `execute_instruction`'s handler now runs a pre-dispatch DRY RUN — the exact same `classify_and_authorize_dispatch` (`agent_registry.hpp`) plus the SAME `PluginConfigStore::action_allowed` per-action kill-switch check `ServerImpl::build_classified_command` itself composes, via the SAME injected RBAC binder (`ServerImpl::dispatch_has_permission`), never a re-implemented slice — BEFORE `dispatch_fn` is ever called. No target-agent list is needed: classification and authorization are decided from `(plugin, action, caller)` alone. On denial, `dispatch_fn` is never invoked (no phantom created-then-cancelled execution row, no bridge reservation) and the caller gets a JSON-RPC error naming the reason: `kInvalidParams` for `Unclassified`/`Ambiguous` (byte-identical message to the C8 pre-mint site and REST), `kPermissionDenied` for the other four — deliberately NOT `kApprovalRequired` (-32006) for `ApprovalRequired`, since that code's own contract mandates an `approval_id`/`status_url` to poll and this dry run mints no ticket (Decision 7: "no new ticket-mint surface", `docs/security-reviews/1398-dispatch-approval-gate-design.md`). Every denial's `error.data` carries a machine-readable `reason` field (the same snake_case `to_string(DispatchDenialReason)` vocabulary as the `yuzu_server_dispatch_denied_total{reason}` metric and the `mcp.execute_instruction|denied` audit detail this dry run also emits) so an agentic caller can branch programmatically instead of string-matching `message`. This is NOT a new enforcement point: `dispatch_fn` still re-runs the identical chokepoint decision internally a moment later and remains the surface that actually dispatches — the dry run only changes what a refused caller is TOLD. The authorizer (`McpServer::AuthorizeDispatchFn`) is wired unconditionally at boot, next to the Destructive-targeting classifier above, and is **fail-closed when unwired**, same posture as that classifier. REST's `/api/command` does NOT get the same full discrimination for free: `build_classified_command`'s denial handling collapses `Forbidden`/`AnonymousOperator`/`KillSwitched` into one generic `permission denied: <securable>:<operation>` 403 message (only the audit `reason=` and the metric label discriminate those three there) — full per-reason response-body discrimination is an MCP-only improvement in this PR. Only `execute_instruction` gained this dry run; `execute_bundle` and the other MCP dispatch tools are unaffected, tracked as a follow-up alongside the bullet above's list.
  - **Targeting is type-checked and an empty target set is refused.** A non-string `agent_ids` entry or `scope`, a supplied-but-empty `agent_ids` (published as `minItems: 1`) or empty `scope`, are all rejected rather than dropped — because a target set that empties out falls into the "nothing specified" default, which means the entire fleet, and the caller is told it succeeded. The supervised tier was protected by C8's `items.type=string`; the **operator** tier, which executes with no human in the loop, was not. Every rule the schema *cannot* express lives in one pure function (`check_exec_instruction_shape`) called from BOTH the C8 gate (before a ticket is minted or consumed) and the handler (for the ungated tiers, which never reach C8) — adding a rule at only one of those sites reintroduced a ticket burn twice during review.
  - The schema literals in `kTools[]` and the constants in `mcp_input_bounds.hpp` are **one contract in two places**, and a test reads the served schema back and asserts each literal equals its twin — so bumping one without the other fails a test rather than silently reopening the gap. The charset is deliberately *not* narrowed to `execute_bundle`'s `[a-z0-9_]` identifier rule: dotted server actions are live shipped content (`content/definitions/workflow_management.yaml` ships `plugin: server`, `action: workflow.list`), so importing that rule would reject working calls.

- **Adding a tool (checklist):** a new tool must land in **all** of: `kTools[]` (schema — which must compile under the `mcp_input_schema` closed keyword catalogue above, with every `required` name declared in `properties`; an unsupported keyword or malformed operand is a **boot failure** through the #2383 validator's 4th raw sequence, so the C8 gate can never meet a schema it only partially enforces; an approval-gated tool's schema must NOT set `additionalProperties:false` unless it also declares `approval_id` — otherwise its own recall argument would fail validation and every ticket it mints would be unrecallable; the boot validator enforces this rule, not just this checklist), `kToolAnnotation` (served hints), `kToolSecurity` (securable/operation drawn from the seeded RBAC catalogues), `kWriteTools` **iff** its operation is non-Read, plus its dispatch branch and per-handler `perm_fn`. A missing table entry is a boot failure (and a mass `[mcp]` test failure), by design. Any future per-tool metadata table must be folded into `validate_tool_security_registration` — never a second validator. Separately, `ToolDef::output_schema_json` (#2972's completeness gate, `test_mcp_server.cpp`'s `tools/list` contract test) — not boot-fatal like the tables above, but CI-fatal: a new tool without one fails that test unless explicitly added to the `kOutputSchemaExempt` allowlist there (a visible, reviewable line, not a silent gap). Add a schema whenever the tool's result shape is stable; only join the exemption list for a genuinely not-yet-designed result shape.
- **Reserved on-behalf-of headers rejected (ADR-1005):** MCP registers on the same httplib instance as REST, so the pre-routing chokepoint rejects any `/mcp/v1/` request carrying a reserved on-behalf-of header with `403` before the JSON-RPC layer runs — see `docs/auth-architecture.md` ("On-behalf-of assertions rejected") for the reserved-name list.
- **Transport request-body bound (#2437; the encoding half generalized to every route by #2407 D4):** every path under the `/mcp/` prefix (so `/mcp/v1/`, `/mcp/v1`, and a future `/mcp/v2/` by default — the cap matches the scope the auth chokepoint admits) admits only request bodies it can size in advance, enforced in the pre-routing chokepoint — which httplib runs **before it reads the body**, so a rejection costs a header parse rather than megabytes of buffering. Three possible rejections, all counted by `yuzu_mcp_body_too_large_total{reason}` and logged (throttled, sanitized) since there is no principal to audit pre-auth. The third is ALSO counted by the general `yuzu_body_cap_rejected_total{path_class="mcp",reason="unsupported_encoding"}` (see `docs/user-manual/metrics.md`) — the general counter is the fleet-wide view, and the MCP-specific series is kept so the existing #2437 alert does not silently lose an arm when a compressed body is refused:
  - **`413`, `reason=over_cap`** — a declared `Content-Length` above **4 MiB**.
  - **`411`, `reason=unmeasurable`** — a request carrying framing this server is not the sole interpreter of: **any** `Transfer-Encoding` (any value, any method), or a POST/PUT/PATCH with no `Content-Length`. The rule is deliberately broader than "reject chunked", because matching httplib's parsing by hand is what failed the first time: it tested `Transfer-Encoding` with a case-sensitive substring while httplib compares case-insensitively, so `Transfer-Encoding: Chunked` was admitted as a measurable body and then read as chunked under the 100 MB default — one capital letter defeating the cap.
  - **`415`** — **any** `Content-Encoding` other than `identity`. As of this change this is no longer folded into the `411` above as an MCP-specific rule: it moved to the general pre-routing gate (`body_cap_policy.hpp` / `server.cpp`) and applies UNCONDITIONALLY to every route class, not only `/mcp/`, independent of a class's `requires_measurable` bit. Same underlying reason as before: this build compiles `CPPHTTPLIB_BROTLI_SUPPORT`, httplib decompresses transparently and bounds only the **decompressed** size against its global limit, so `Content-Length` on a `Content-Encoding: br` body measures the compressed bytes and is no bound at all on what gets buffered. JSON-RPC clients send an identity-encoded body with a `Content-Length` and are unaffected; a proxy or streaming stack that re-frames requests will be refused, which is a deliberate trade. Ordering, settled: the cap is one lambda invoked from two sites — inside the health-probe branch, so the four probe paths are capped while staying exempt from the on-behalf-of guard and the rate limiter, and after both of those for every other route.
  - This is a **per-path** bound, deliberately *not* the server-global `set_payload_max_length`, which would also cap the multipart certificate upload and content distribution on the same httplib instance. Those keep the 100 MB default.
  - **4 MiB is a deliberate clamp, not a ceiling derived from every tool.** It sits above a maximal `execute_instruction` — **~3.27 MiB decoded, about 18% headroom**, down from 62% before the `params` value cap was aligned with `execute_bundle`'s 64 KiB. Read that 18% before widening any `execute_instruction` field bound again: the remaining room is real but no longer generous, and the sizing `static_assert` in `mcp_input_bounds.hpp` fails the build rather than letting a maximal legitimate call start 413-ing. It stays **deliberately below what `execute_bundle`'s own validator accepts**: `validate_bundle_steps` permits 32 steps × 32 params × 64 KiB ≈ 64 MiB, and one saturated step is already ~2 MiB, so a **2-step saturated bundle (~4.02 MiB) is refused before its validator runs.** That product bound was a per-step memory guard for the agent fan-out, never an advertised aggregate — but the asymmetry is real, is **not** shared by the REST twin `POST /api/v1/bundles`, and is pinned by a test. For multi-MiB bundle params, use the REST twin or raise the cap deliberately.
  - **Encoding caveat:** the per-field `execute_instruction` argument caps bound *decoded* bytes while this bounds the *raw* body, and legal `\uXXXX` escaping can inflate a payload several-fold. The tolerance is **1.22×** raw-to-decoded (it was 2.63× before the `params` widening — quantified here rather than described, because the adjective outlived the number it was calibrated to). Plain ASCII and base64 (1.00×), Windows paths at ~8% backslashes (1.08×), JSON-in-a-string at ~12% quotes (1.12×) and text with 3% newlines (1.03×) all fit. An all-quote payload (2×) or raw control bytes (6×) do not, and a simultaneously-saturated maximal call built from them is refused with a `413` telling the caller to reduce the arguments. So: the headroom absorbs realistic escaping of a maximal `execute_instruction`; it is **not** a proof against a maximally-escaped one.
  - **What "maximal" bounds:** the ~3.27 MiB figure covers the *declared* fields. `execute_instruction`'s root schema does not set `additionalProperties: false` and undeclared properties are deliberately tolerated, so a schema-valid call can legitimately exceed it, up to the 4 MiB transport cap. The figure answers "does a legitimate maximal call fit", not "is 3.27 MiB the largest accepted body".
  - **JSON nesting is bounded at 32 levels**, rejected as a `-32700` parse error before the document is built. `nlohmann`'s `dump()` is recursive (its parser and destructor are not), so a ~0.95 MiB body of nested arrays — a quarter of the cap, comfortably admitted by it — segfaults the process, and callers `dump()` caller-supplied values. Guarding an individual `dump()` would miss every other recursive traversal, so the tree is never constructed. The deepest legitimate MCP request is `execute_bundle` at about seven levels.
  - **Deployment caveat:** a rejected body is never read off the socket. httplib stamps `Connection: close` on any status ≥ 400 so a conforming client closes, but if a **reverse proxy is ever placed in front of Yuzu**, an unread `Content-Length` body is a textbook request-smuggling primitive between proxy and origin. The shipped rigs expose the server directly; front it with care.
- **Audit:** Every MCP tool call logged with `action: "mcp.<tool_name>"` and `mcp_tool` field on `AuditEvent`.
- **Response-collection scope (`query_responses`) — #1634, FIXED.** `query_responses` is now gated by `fleet_read_fn_`/`require_fleet_read` (ADR-0017 admit-then-filter), not the old flat global `Response:Read` check the inert per-row filter sat behind — a management-group-confined operator is admitted and sees only their in-scope agents' rows, real cross-operator isolation. The visible-agent set is resolved (`distinct_agent_ids`/`distinct_agent_ids_by_execution`) and pushed into `ResponseStore::query`/`query_by_execution` as SQL `agent_id = ANY(...)` **before** `LIMIT`/`OFFSET` (ADR-0017 INV-3), not as a post-fetch filter — a capped/paginated read that filtered after `LIMIT` could otherwise hand a confined caller a short or empty page despite visible rows existing past the hidden ones the cap already truncated (a real defect an adversarial review found in the first #1634 migration pass, fixed same-branch). A corrupt/load-failed `rbac.db` still fails **closed** (zero rows) via the same gate. When rows ARE dropped, `query_responses` emits a **second** audit row `result=denied` (`detail` carries the distinct dropped-agent count) **in addition to** the `result=success` row — a SIEM rule must treat the two as a pair for one call (informational access-boundary evidence for CC6.1, not a failed call). RBAC-off → unrestricted (legacy-open). The result object carries `audit_persisted:false` if any of that call's audit rows could not persist, and `result_truncated_by_cap:true` if the caller's own scoped query hit the row cap (now signals THIS caller's page was truncated, not a raw-then-filtered cap hit that could fire entirely inside another operator's rows). *(The same real gate now also covers `aggregate_responses`, REST `/executions/{id}/visualization` + the legacy `/api/responses/*` family, `GET /api/v1/executions/{id}`, REST `/api/v1/events`, dashboard `/sse/executions/{id}`, and MCP `get_execution_status`/`list_executions`; `query_responses`/`aggregate_responses`/`get_execution_status`/`list_executions` are reclassified `ServiceScopeClass::confined`. `list_executions` has a weaker mechanism — execution rows carry no single `agent_id`, so a confined caller is restricted to their own dispatches rather than a real per-row visible-agent check. Still open, unrelated files, tracked separately: REST `GET /api/v1/execution-statistics/agents` + the workflow executions LIST fragment `#3526`; `/fragments/results` has no audit trail `#3528`. See `docs/auth-architecture.md`'s "Third migration (#1634)" for the full account.)* **(#3344 note, FIXED:** `query_responses`' `retry_after_ms` poll hint used to read `execution_tracker` directly, gated only by `Response:Read` and resolved before the scope filter — a confined caller with zero visible agents on an out-of-scope `execution_id` could learn "non-terminal" via the hint's presence alone even though every response row was filtered out. The hint is now suppressed (nullopt, not false — same convention as the instruction_id-only unknowable case) whenever the caller's resolved in-scope agent set for that execution is empty.)

## Error envelope

JSON-RPC error responses from the denial paths (read-only mode, tier policy, approval-required, the #2383 missing-security-registration misconfig deny, and the #2405 pre-approval input-schema deny) carry a structured `error.data` field (A4, per `docs/agentic-first-principle.md`):

```json
{ "correlation_id": "req-<hex-ms>-<hex-seq>", "retry_after_ms": null, "remediation": "use a higher-tier MCP token, or the REST API / dashboard" }
```

> **Supervised-tier / approval-gated operations — ticket-then-recall (#289).**
> An operation for which `requires_approval(tier, type, op)` is true is answered
> with `kApprovalRequired` (-32006). Its `error.data` extends the A4 envelope
> with two extra fields:
>
> ```json
> { "correlation_id": "req-<hex-ms>-<hex-seq>", "retry_after_ms": 30000,
>   "remediation": "an admin must approve this approval_id (see status_url), then re-call this tool with the approval_id argument to execute",
>   "approval_id": "<32-hex>", "status_url": "/api/v1/approvals/<32-hex>" }
> ```
>
> `retry_after_ms` is honest here, not `null` (#3344, `kMcpApprovalPollRetryMs`
> in `mcp_retry.hpp`) — this IS retryable, on human timescales, and approval
> minting is deduplicated so a recall before the ticket resolves returns the
> same pending ticket rather than minting a second one.
>
> Before ANY of the below — mint, dedup, recall lookup, consume — the
> arguments must pass the #2405 input-schema validation (Security Model
> above); a schema-invalid call answers `kInvalidParams` (-32602) with
> nothing minted and nothing consumed.
> The **first** call mints an `ApprovalManager` approval (`definition_id =
> "mcp.<tool>"`, `submitted_by` = the caller, `scope_expression` = the
> canonical JSON of the tool arguments) and returns the envelope above. An admin
> approves it (Settings UI / REST `POST /api/approvals/{id}/approve`; reviewer ≠
> submitter is store-enforced, so self-approval is impossible). The caller then
> **re-calls the same tool** passing the returned `approval_id` as an argument;
> the server verifies the approval is (a) approved, (b) for this exact tool
> (`definition_id`), (c) for these exact arguments (canonical-args match,
> `approval_id` excluded from the comparison), and (d) not yet consumed, then
> **atomically consumes it** (one-time; a replay of a consumed ticket, or a
> concurrent second recall, is rejected — the mutating op runs at most once).
> The consume step additionally requires (e) the ticket was minted by the MCP
> surface itself, not a REST/schedule mint that happens to share this tool's
> `definition_id` and arguments (#2442), and (f) the recalling principal is
> the ticket's own submitter (#2442) — a Viewer who merely read the ticket id
> off `GET /api/approvals` cannot redeem it. (e) and (f) are enforced only at
> this consume step, not at the pending-poll lookup above, and their refusal
> reads identically to an ordinary replay — see -32003 below for why. (A
> wrong-tool/arguments mismatch is a DIFFERENT, earlier refusal — a distinct
> message, at (b)/(c) above, not this one; it is not part of the anti-oracle
> group.) A successful consume lets the call through to the
> handler. A recall against a still-**pending**
> ticket returns the same `kApprovalRequired` envelope (keep polling
> `status_url`); a rejected/expired/mismatched/consumed ticket returns
> `kPermissionDenied` (-32003). `confirm_engine_rotation`'s recall additionally
> runs a pre-consume precondition (#2443) that rechecks live rotation state
> before consuming the ticket; a precondition failure also returns
> `kPermissionDenied` (-32003) but with a distinct, deliberately generic
> message ("approval cannot be redeemed right now...") and — unlike the four
> causes above — leaves the ticket UNCONSUMED and still recallable. This
> generic gate governs every approval-gated
> tool — the supervised tier's `execute_instruction` / `revoke_certificate` /
> `execute_bundle`, plus `delete_tag` (operator + supervised) and
> `quarantine_device` (supervised). **Degraded path:** if the server has no
> `ApprovalManager` (a stripped deploy / test harness), it cannot mint a pollable
> ticket, so it falls back to a `kTierDenied` (-32004) with no `approval_id`.
> **Note:** the per-tool RBAC check (`perm_fn`) runs on the *recall*, after the
> ticket is consumed, so a token that passes the MCP tier check but fails RBAC
> can mint→approve→then 403 (burning the ticket) — a rare consequence of the
> deliberate tier-then-RBAC two-gate split.

`correlation_id` is a per-error token (`req-<hex-ms>-<hex-seq>`, the same format as the REST `X-Correlation-Id` header) returned to the caller in the error body, so a client can cite a stable handle when reporting a failure. **It is not persisted to the audit log today** — the audit row for a denied call (`mcp.<tool>`) is written separately and does not carry the token — so server-side correlation relies on any `spdlog` line the handler emits at that moment, not on `audit.db`. Two exceptions stamp the SAME token into the audit detail (one-cid pattern): the #2383 misconfig deny (`... correlation_id=<cid>`) and the #2405 input-schema deny (`arguments do not match the tool input schema at '<path>' correlation_id=<cid>`). `retry_after_ms` is `null` on tier-denial errors (a token's tier is fixed — the denial is not retryable as-is), but non-null on approval-required (`-32006`, #3344: it IS retryable, on human timescales — see above); `remediation` carries an actionable hint — escalate to a higher-tier token, or use the REST API / dashboard. Per-tool validation errors (e.g. the dex-perf tools) populate `correlation_id`, a `null` `retry_after_ms`, and a field-specific `remediation`. Parse `error.code` for the error class and `error.data.correlation_id` for client-side traceability.

### `retry_after_ms` floors (#3344)

Every `retry_after_ms` emission — error-shaped (A4 `error.data`) and, for the
three result-poll tools below, success-shaped (in the tool's own structured
payload) — is a named constant in `server/core/src/mcp_retry.hpp`, each
carrying a mechanical derivation comment (no dispatch-to-first-result latency
histogram exists to measure from — `yuzu_command_duration_seconds` is full
command completion, not first-result):

| Constant | Value | Covers |
|---|---|---|
| `kMcpStoreFaultRetryMs` | 5000 | Generic transient store/subsystem fault on an error-shaped response (REST 503 parity) |
| `kMcpStoreFaultShortRetryMs` | 2000 | Plugin-config / API-token rotation family (REST `Retry-After: 2` parity) |
| `kMcpProviderWarmupRetryMs` | 5000 | A DEX/app-perf provider still initializing at server start |
| `kMcpResultPollRetryMs` | 2000 | Success-shaped result-not-ready poll — `get_execution_status`, `query_responses`, `get_bundle_result` |
| `kMcpApprovalPollRetryMs` | 30000 | Approval-ticket poll (`-32006`) — human-timescale, anti-amplification derived |

Several constants share a numeric value with a neighbour — that is
coincidental historical pricing, not a shared derivation, and each is kept a
distinct symbol so one can be re-tuned later without dragging the other.

The three result-poll tools are counted at `yuzu_mcp_poll_total{tool,result}`
(`result` is `ready` or `not_ready`, per served verdict, excluding pre-verdict
denials) so the floors above can be data-tuned from real poll-rate evidence
instead of ossifying as guessed constants. See
`docs/observability-conventions.md`.

It is intentionally endpoint-evidence first: OpenShift, KVM/libvirt, Postgres/Oracle, Teams/Zoom, registry/build-cache, and similar platform internals are labelled as connector gaps unless the facts are already present in Yuzu inventory/responses or supplied by the user.

### Resources

- `yuzu://capabilities` — what MCP can answer now, what may need live read-only dispatch, what requires external connectors, and what is unsafe without approval.

### High-level tools

These tools are read-only and available to the `readonly` MCP tier, subject to normal RBAC checks. They advertise `outputSchema` and return both legacy MCP `content[]` text and `structuredContent`.

- `get_fleet_posture_fast` — compact cached posture summary. The cache TTL defaults to 30 seconds and responses include `generated_at`, `data_age_seconds`, `partial`, and `missing_sources`. `data_age_seconds` reflects the **real age of the cached snapshot at read time** — it is recomputed per request, so a cache hit reports a non-zero age (it is not the value baked in at generation).
- `classify_operational_question` — classifies a question as `answerable_now`, `answerable_with_live_dispatch`, `requires_external_connector`, `unsafe_without_approval`, or `outside_yuzu_scope`. **This classification is advisory only — a UX hint for the agentic worker, not a security control.** It uses ASCII keyword matching that can be evaded by rephrasing or Unicode homoglyphs; never treat it as an authorization decision. Real enforcement is the MCP tier + RBAC check on each tool, and its `recommended_next_tools` are always read-only.
- `get_incident_playbook` — returns a scenario workflow, first tool, safe tool path, connector gaps, and approval boundaries. `scenario` is matched **exactly** against a playbook name, category, or curated tag (e.g. `openshift`, `teams`, `postgres`) — not by loose substring, so a short/generic query returns "unknown scenario" rather than the wrong playbook.
- `summarize_working_set` — summarizes a fleet, agent, execution, or result-set working set into a bounded model-ready narrative with resource links. The `agent` kind is management-group scoped (an out-of-scope agent is reported as not-present, never leaking its hostname/os); the `execution` kind additionally requires `Execution:Read`.

## Phase 2.5 (Implemented — MCP Streamable HTTP transport, track 2f PR 1 + PR 2)

The session-lifecycle + transport pre-check half of the Streamable HTTP transport is **live** (ADR-1005 execution plan **Decision 15 / track 2f** PR 1). Shipped:

- **`Mcp-Session-Id` sessions.** `initialize` mints a principal-bound ≥128-bit CSPRNG session id and returns it as the additive `Mcp-Session-Id` response header. Sessions are never *required* (plain-POST clients are unaffected); when a client presents one on a later request it is validated (unknown / expired / bound-to-another-principal → `404`, indistinguishable from never-existed — no cross-principal oracle — and the client re-initializes). `DELETE /mcp/v1/` ends a session. State is in-memory and bounded (idle TTL, per-principal + global caps that **reject** rather than evict a live session); a server restart drops sessions and the client re-initializes, per spec.
- **`Origin` validation** on every method against a configured allowlist (`--mcp-allowed-origin`; absent Origin allowed on this credential-gated endpoint, empty allowlist rejects any present Origin).
- **`MCP-Protocol-Version` negotiation.** Supported revisions `2025-03-26` and `2025-06-18`; `initialize` echoes the client's requested version when supported, else the `2025-03-26` baseline. A present-but-unsupported header → `400`. The negotiated revision is recorded on the `yuzu_mcp_initialize_protocol_total{revision}` counter (bounded to the supported set) so a future revision deprecation has usage data (track 2g PR 1).
- **`initialize.instructions` orientation blob** (track 2g PR 1, invariant A5 item 6). The `initialize` result carries a static, operator-authored `instructions` string orienting a fresh client — what Yuzu is, the operating model, a tool-family index, and where discovery starts. It is single-sourced with the `yuzu://about` + `yuzu://operating-model` resources (`server/core/src/mcp_orientation.{hpp,cpp}`) so the handshake and those resources cannot drift, and it is **static compiled-in content only** — never fleet-derived data, which would be a prompt-injection channel into every fresh client.
- **Notification POSTs answer `202`** (spec MUST; was `204`).
- **Kill switch** `--mcp-no-streaming` (no minting; `GET`/`DELETE` → `405`; plain JSON-RPC POST only — and it also degrades the streamed-POST arm back to plain JSON, so it is the kill switch for BOTH progress surfaces, not just the GET channel) and audit verbs `mcp.session.open` / `mcp.session.close` / `mcp.session.reject` (the last on every denial — origin, unknown session, cap, protocol-version).
- New JSON-RPC error codes: `-32007` unknown session (`404`), `-32008` origin rejected (`403`), `-32009` bad protocol version (`400`), `-32010` session cap (`429`). Each carries the shared A4 `error.data` (a `correlation_id`, the always-present nullable `retry_after_ms`, and a `remediation`), built by the single `error_response_a4` helper so the transport denials match the REST/tool-call A4 envelope.

Session state is in-memory only and deliberately does **not** gate `/readyz`. Operator reference: `docs/user-manual/server-admin.md` (flags + Upgrade Notes) and `docs/user-manual/mcp.md`.

### The GET SSE channel (PR 2)

`GET /mcp/v1/` is the session's server→client channel. It replaces the PR-1 `405` placeholder:

- **Attach.** Requires the session's `Mcp-Session-Id` (absent → `400`; unknown / expired / another principal's → `404`) and `Accept: text/event-stream` (missing → `406`, `-32011`; wildcards like `*/*` deliberately do **not** opt in). Heartbeats every ~3 s keep intermediaries from idling the connection out — sent only when a tick has nothing else to deliver, since a pass that just wrote real frames has already proved the connection live; `X-Accel-Buffering: no` defeats reverse-proxy response buffering.
- **Resume.** Each session has its own bounded replay ring and its own event-id namespace starting at 1 (ids are **never** global, so a cursor from one session can never address another's frames). A reconnect with `Last-Event-ID` replays exactly the frames it missed. If the cursor's frames have already been evicted from the ring — or the cursor is one the server never issued — the session is **terminated** and the request `404`s: the client re-initializes, and durable results remain fetchable by `execution_id`. There is no silent gap, and the GET's answer is coherent with the client's next POST (which `404`s too).
- **Revocation.** The credential that opened a stream is re-validated on **every heartbeat tick**, so a revoked token or a signed-out session kills a *live* stream, not merely future attaches — the close frame says `credential_revoked`. Latency is one tick on a single server. The re-validation work (the auth-store read plus the session-registry touch) is bounded to **once per tick regardless of frame rate** — a busy stream is woken by every published frame, but only the drain rides the wake, so backend load does not scale with how chatty the stream is. Across **replicas** it is bounded by the 60 s token-cache TTL plus a tick, and that bound is an API-**token** property: the token cache is process-local, so a revoke handled by one replica reaches another replica's stream only when that replica's cache entry expires and it re-reads the store. Cookie sessions are per-process and in-memory, so a cookie-authenticated stream does not exist on another replica at all. Treat CC6.2 revocation latency as bounded by that, not as instantaneous. A stream authenticated by an **engine** principal carries a second, shorter bound of the same kind: its per-tick backing-principal check is served from a 15 s liveness cache (#2367), so revoking the *principal* on one replica reaches another replica's stream within that TTL plus a tick — on the replica handling the revoke it is **one tick**, the same bound as the token/session case above: the store invalidates its own cache synchronously with the write, so the next heartbeat tick reads through and observes the dead principal rather than serving a stale cached hit. An **unreachable** auth store is not a revocation: it is reported as indeterminate and buys a bounded 60 s grace window, after which the stream ends with the distinct reason `auth_unavailable`. For an **engine**-authenticated stream that window is measured from the stream's last **authoritative** credential confirmation, not from the tick the outage was first noticed — a cached answer keeps such a stream running but does not re-start its budget, so cache residency and the grace window cannot add up to more than the window itself, and a stream already riding a near-expired cache entry when the outage begins gets correspondingly less than the full 60 s. That guarantee is engine-specific: an **API-token**-authenticated stream still treats a token-cache hit as a fresh confirmation, so for those the token-cache residency and the grace window can still add (pre-existing, tracked as #2447). That distinction exists so an auth-backend blip cannot cut every stream on the fleet at once, and so an operator can tell a security event from an outage.
- **Caps.** Every held-open SSE response pins one HTTP worker for its whole life, so concurrency is admission-controlled — and **every** streaming surface leases from the same budget (MCP GET, MCP streamed POST, `GET /api/v1/events`, the dashboard executions drawer, the legacy `/events` stream), because the worker pool is what they all share (ADR-0034). Capacity is `--max-sse-streams` (default 128, and the worker pool is sized *from* it); `--mcp-max-streams-per-principal` (default 4) is an anti-monopoly policy for the MCP surface, not a capacity limit. A cap hit **rejects the newcomer** with `429` (`-32012`) carrying an honest `retry_after_ms` — it never evicts a live stream. Utilisation: `yuzu_http_held_open_responses / yuzu_http_held_open_capacity`.
- **Takeover.** A second GET on a session supersedes the first (the old stream closes with `superseded`) rather than being rejected: the common second GET is a client reconnecting across a zombie TCP the server has not noticed yet, and rejecting it would lock that client out for a full write-timeout. It is admitted without a cap check but still takes a lease — a superseded provider goes on pinning its HTTP worker until it drains, and an *uncounted* pinned worker is exactly the hole the budget exists to close. The pool is bounded structurally instead: a session holds at most one draining stream, so a *third* concurrent GET on the same session gets `429 stream_handover_pending` until the handover completes, and the budget reserves two workers for every stream it admits.
- **Close reasons** are wire-visible and audited (`mcp.stream.attach` / `mcp.stream.close`): `client_disconnect`, `superseded`, `session_terminated`, `credential_revoked`, `auth_unavailable`. The close is delivered as a JSON-RPC `notifications/yuzu.stream_closed` notification carried as a normal `message` on the stream (2f PR 3b) — not a bespoke `event: stream-closed`, which a spec MCP client parsing JSON-RPC off the stream would never see. Its `params` carry the machine-parseable `reason` in the same A4 shape (`reason` / `correlation_id` / `retry_after_ms` / `remediation`) as every denial on this route, so a client has one error contract, not two. The frame is off-ring and id-less: a close is a point-in-time terminal signal, never replayed.

PR 2 gave the channel heartbeats and replayed frames; **PR 3a shipped its first producer**, the progress bridge (`notifications/progress` - see "Progress bridge (2f PR 3a)" below). Metrics: `yuzu_mcp_sessions_active`, `yuzu_mcp_sessions_opened_total`, `yuzu_mcp_streams_active`, `yuzu_mcp_streams_handover_pending`, `yuzu_mcp_streams_cap` (the EFFECTIVE cap after the boot clamp), `yuzu_mcp_stream_replay_ring_evictions_total`, `yuzu_mcp_stream_frames_dropped_total` (frames dropped before reaching a connection — usually a slow consumer's per-connection queue overflow, also a rare producer-side post-commit allocation failure (#2366); recoverable via Last-Event-ID), `yuzu_mcp_stream_frames_too_large_total` (a frame exceeded the per-frame byte cap and was truncated before entering the ring — counted rather than only logged, because an unbounded warn-per-publish is a log-flood vector), `yuzu_mcp_stream_rejects_total{reason}`, `yuzu_mcp_stream_closes_total{reason}` (alert on `auth_unavailable` and `internal_error`), `yuzu_mcp_stream_publish_failures_total` (a `publish()` call failed before the frame committed — pre-commit only; the frame was never published and no event id was consumed. A post-commit sink-enqueue failure instead counts as a normal `frames_dropped_total`/events-dropped gap. Non-fatal by construction but a near-miss for a worker-thread `std::terminate` — ticket on any `increase() > 0` over 15 m, do not page). Progress-bridge families (2f PR 3a): `yuzu_mcp_bridge_records_active`, `yuzu_mcp_bridge_reject_total{reason}`, `yuzu_mcp_bridge_degrade_total{reason}`, `yuzu_mcp_bridge_listener_failures_total`, `yuzu_mcp_bridge_mailbox_drops_total` (retired #2412 - kept registered at zero; the bounded arming mailbox it counted was replaced by a single latest-wins progress slot), `yuzu_mcp_bridge_progress_suppressed_total` (#2438/#2412 - progress candidates that never reached the wire: H1 monotonic-suppression drops and latest-wins supersedes), `yuzu_mcp_bridge_projector_cycles_total`, `yuzu_mcp_stream_terminal_publish_failures_total`, `yuzu_mcp_stream_final_unpinned_total`, `yuzu_mcp_stream_pin_displaced_total`, plus `yuzu_mcp_bridge_forced_expire_total{disposition}` (#2489 - which way the ring-only pressure hatch DECIDED to settle each record it force-expired: `none` / `fallback_final` / `synthesize_unavailable`, a distinction that previously existed only in audit; counted at the decision, so pair it with the publish-failure family for delivery), `yuzu_mcp_bridge_pressure_budget_exhausted_total` (a pressure pass stopped on its per-invocation victim budget with the cap still exceeded; the rest roll to the next tick) and the teardown-completeness families `yuzu_mcp_bridge_teardown_incomplete_total{reason}`, `yuzu_mcp_bridge_teardown_retry_total{outcome}` (#2513 - a later sweep's retry attempt recovered or exhausted its budget), `yuzu_mcp_bridge_projection_degraded_total` (#2528 - a projection claim released without the record lock, so the settle was lossy) and `yuzu_mcp_maintenance_tick_failures_total{tick}` (#2487; on-call procedure in `docs/ops-runbooks/mcp-bridge-teardown-recovery.md`) - each with its alerting posture in `docs/user-manual/metrics.md`.

**Shutdown:** httplib re-checks its shutdown flag between provider calls, so `stop()` drains live GET streams within about one heartbeat tick (~3 s, in parallel). Since #3042, `ServerImpl::stop()` also close-signals every live MCP session first (`McpSessionRegistry::shutdown()`, called before `web_server_->stop()`) — this wakes a waiting GET pump immediately (the same mechanism a DELETE or idle-GC close uses) rather than leaving it to notice on its next tick, and it delivers a clean `session_terminated` close frame instead of a bare connection drop. A stream whose peer has stopped reading is bounded instead by the 30 s socket write timeout, which neither mechanism can shorten — the pump is mid-write, not waiting.

**A streamed POST also drains well inside its response cap — but by polling, not by a wake.** Its response installs through the identical `res.set_chunked_content_provider` mechanism (`McpPostPump::pump_once`, bounded per call by the same `cfg_.tick`, ~3 s, as the GET pump — see `mcp_stream.cpp`), so httplib's between-provider-call shutdown check applies here too: on an ordinary `stop()` a streamed POST's response ends within about one tick, the same bound as GET, not the `kMcpStreamedPostCapDefault` (120 s) cap. But the mechanism differs from GET's: a streamed-POST sink is a standalone `SseSinkState` that `McpSessionRegistry::shutdown()`'s `close()` call never touches, so it has no wake to receive — it instead notices on its own next `session_alive_()` tick check that the registry has drained, and closes with `session_terminated` at that point. Either way the underlying execution is unaffected: closing the response stream does not cancel it, and its result stays fetchable by `execution_id`.

The 120 s cap governs a separate, unrelated case: a long-running execution during ordinary (non-shutdown) operation. If the cap expires while the server keeps running, the bridge runs ONE further drain pass that delivers the progress already latched, then settles the response on the pass after it (#2739) — so a single streamed-POST *call* can legitimately hold its worker for up to the cap plus those pump ticks plus its socket-write time; that is a client-side read-timeout concern, not a shutdown-sizing one. (A terminal latching inside that window is delivered as a normal completion, which only ends the response sooner; progress latched after the drain pass parks to the replay ring for GET resume rather than the wire.)

What genuinely bounds graceful shutdown, for either GET or streamed POST, is a stream stuck mid-write to a blackholed or drip-feeding peer — bounded by the 30 s socket write timeout, since neither close-signal above reaches a pump that is already mid-write rather than waiting. Size a container termination grace period and `TimeoutStopSec` with that write-timeout worst case in mind, not the 120 s cap: the shipped systemd unit and every shipped compose file that runs `yuzu-server` use 210 s (see `docs/user-manual/server-admin.md`'s Sizing bullet) — a comfortably conservative margin over the write-timeout bound. Tracked for a bounded drain (a pump stop-token) — the residual write-blocked case — in the follow-ups below.

## Progress bridge (2f PR 3a)

**Shipped.** When a `tools/call` for `execute_instruction` carries `_meta.progressToken`, the server correlates that request to its execution and projects `ExecutionEventBus` events onto the session's **GET** channel as `notifications/progress` (`progress`/`total` = agents responded / agents targeted), followed by the terminal result.

**Lifecycle shape — two, and the client chooses.**

- **Streamed POST** (2f PR 3b, "Streamed POST" below). Send an SSE-capable `Accept` alongside the `progressToken` and the POST response *is* the progress channel: frames arrive before the result, which is the ordering the MCP progress lifecycle expects. **This closes the deviation** recorded against #2439 in the A5 exception ledger (`docs/agentic-first-principle.md`).
- **GET channel** (the 3a shape, still fully supported). Without an SSE `Accept` the frames are delivered on the session's GET channel *after* the `tools/call` response has retired the request. Stock SDK clients *drop* (they do not reject) frames for a retired token, so the fallback there is to poll by `execution_id`. This stays the right shape for a client that keeps one GET channel open and would rather not hold a POST open per call.

**Degradation is silent and safe.** If the bridge cannot correlate a request (capacity, unknown session, allocation failure), the call falls back to the plain response - which is self-sufficient, carrying `execution_id` - and counts `yuzu_mcp_bridge_degrade_total{reason}`. Live progress is an enhancement, never a dependency.

**Monotonicity.** `progress` is strictly increasing on the wire, as the MCP spec requires: the projector holds a per-record watermark and suppresses any snapshot that would not advance it.

**A pin released to admit a new call (#2740).** A streamed POST whose peer dies before the final is written leaves that final pinned: the prompt release happens only once the final reaches the wire, and the remaining routes — a GET resume acking past the pinned id, or session death — both need a channel a POST-only client does not have. Four such calls used to exhaust a session's four streamed slots permanently, with a 429 telling the client to wait for calls that had already ended. Admission now reclaims a slot first: the session's OLDEST parked record whose committed final no wire took delivery of is unpinned, counted (`yuzu_mcp_bridge_pin_displaced_for_admission_total`) and audited (`mcp.bridge.pin_displaced_for_admission`), and the new call is admitted. That final is unpinned, not erased — it stays in the ring until ordinary eviction and stays fetchable by `execution_id`, so a resume can often still collect it. Live calls are never displaced, so the concurrency limit holds by construction (with two bounded exceptions, both leaving a session transiently one call over its cap for the lifetime of the over-admitted call: #2795, a release that loses a race to another release route still admits (counted as `yuzu_mcp_bridge_pin_release_raced_total`; do not alert - a client can reach it by racing its own resume); and a release whose own attempt throws, which is contained and counted as `yuzu_mcp_bridge_pin_release_failed_total` - alert on that counter). Orphan pins — a final whose owning record a teardown erased without unpinning — are reclaimed the same way and are checked FIRST, and are the case that matters most: no route a POST-only client can reach releases them (a GET resume cursor does clear them, but that needs a channel such a client does not have), since the pin-ack sweep and the delivered-final path both need a record and a cursor-less GET resume releases nothing. A refusal therefore now means the reclaim found nothing to take. Two refusals are possible and they are answered differently. With a charge outstanding — calls genuinely in flight — the answer stays "wait for one to finish". With every slot held by a pin, the reclaim failed for one of three reasons: a final still being written by a live pump, a transient decline while one of the session's records is mid-projection, or a slot genuinely stuck (an unreleasable pin the scan could not attribute). The first two clear on retry, and the client cannot tell which case it is in, so that refusal says retry first and only then suggests collecting outstanding results by resuming with `Last-Event-ID` or re-initializing.

**Terminal durability.** A terminal frame is pinned in the replay ring so a reconnecting client can still receive it; the `publish_final -> fallback -> poison` ladder (Decision 15(f)), with `yuzu_mcp_stream_terminal_publish_failures_total` and `yuzu_mcp_stream_final_unpinned_total`, makes any failure to do so visible rather than silent. The exemption covers the **most recent** pinned terminals up to the per-session slot count, not an unbounded set. Exhausting the slots used to mean admission accounting had drifted — the bridge admits streamed records against the same count the array is sized to — though since #2740 the reclaim releases a pin deliberately - which does NOT put the session over cap and cannot itself cause a displacement - while its two accepted residuals (#2795 raced, #2805 contained throw) each can, so drift is now a conclusion to reach rather than assume — and in that degraded state the oldest pin yields to the newest, since the newest is the terminal a client is likeliest still waiting to resume. That is reported by `yuzu_mcp_stream_pin_displaced_total` (alertable on `> 0`); a displaced terminal is still committed and stays in the ring until ordinary eviction reaches it - it loses its eviction EXEMPTION, nothing more. Not "delivered": these frames are ring-only, and nothing delivers one except a resume. Results always remain durably fetchable by `execution_id`.

## Streamed POST — SSE on the response (2f PR 3b)

**Shipped, ON by default** (`--mcp-enable-streamed-post`; pass `--no-mcp-streamed-post` to opt out). The four defects that gated the on-by-default flip — #2739 (response cap), #2740 (pin-slot lockout), #2785 (resume ids on POST frames) and #2789 (per-principal reject coverage) — and the operational/documentary prerequisites (#2791 concurrent test coverage, #2792 wedge-alert semantics and runbook, #2793 customer-manual entries) are all fixed and merged. A `tools/call` for `execute_instruction` that carries `_meta.progressToken` **and** an SSE-capable `Accept` gets its POST response held open as an SSE stream: `notifications/progress` frames as the work happens, the JSON-RPC result **last**, then EOF. This is the spec's progress-before-response ordering.

### Opting in

| Client sends | Server answers |
|---|---|
| `_meta.progressToken` + `Accept: text/event-stream` | SSE stream on the POST response |
| `_meta.progressToken`, no SSE `Accept` | plain JSON now, progress on the GET channel |
| SSE `Accept`, no `_meta.progressToken` | plain JSON (the token is the real opt-in) |
| neither | plain JSON — byte-identical to pre-2f |

`Accept: text/event-stream;q=0` **opts in**. RFC 9110 reads `q=0` as "not acceptable", and this is a deliberate deviation: a client that sends a `progressToken` and then disclaims the media type is contradicting itself, and honouring the token is the useful reading. The token, not the header, is the gate.

### Response shape

Headers are `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`, `X-Content-Type-Options: nosniff`, and `X-Correlation-Id`.

`X-Accel-Buffering` is understood by nginx only. Envoy, HAProxy, ALB and Cloudflare each need their own no-buffering opt-out — without it the proxy buffers the stream, the server cannot detect that the client has gone, and the response runs to its full cap holding a worker and an admission slot. Same caveat as the GET channel (`docs/user-manual/server-admin.md`). Frames are JSON-RPC objects under the default `message` event type. Progress frames are strictly increasing (see Monotonicity above). The stream ends one of two ways:

- **A result frame, then EOF.** The normal case. No close frame follows it — that would be a second, contradictory terminal on a stream that already answered.
- **A `notifications/yuzu.stream_closed` frame, then EOF.** Everything else. It carries a `reason`, the `execution_id`, and `partial: true`.

### Close reasons, and what a client should do

| `reason` | Meaning | Client action |
|---|---|---|
| `completed` | result delivered | nothing — you have the answer |
| `cap_expired` | the response's time budget elapsed; **the execution continues** | fetch by `execution_id` |
| `record_gone` | this response could not continue — the bridge record was reaped (session/pressure teardown) or the server is shutting down; **the execution continues** | fetch by `execution_id`, or reconnect via GET to resume |
| `cancelled` | your `notifications/cancelled` detached the response; **the execution continues** | fetch by `execution_id` if you still want it |
| `session_terminated` | the session ended | re-`initialize` |
| `credential_revoked` | your credential stopped being valid | re-authenticate |
| `auth_unavailable` | the auth backend could not answer within the grace window | retry |
| `internal_error` | a server-side fault ended the response | fetch by `execution_id` |
| `client_disconnect` | the peer went away (recorded server-side; you will not see this frame) | n/a |

**The invariant behind half that table: closing a response never cancels work.** A dispatched command keeps running on real agents, and its result stays durably fetchable by `execution_id` (`get_execution_status`, `query_responses`). `notifications/cancelled` detaches *your stream*, not the fleet change you asked for.

### Admission and refusals

A streamed POST holds an HTTP worker open for its lifetime, so it leases from the same budget as the GET channel (ADR-1005 Decision 15(h)) and is capped per principal. Refusals are answered, not degraded — a client that asked for a stream is told it is not getting one:

| Condition | Status | JSON-RPC error | Retry? |
|---|---|---|---|
| per-principal or global stream cap (pre-admission `StreamBudget`, `reason=post_per_principal_cap`/`post_global_cap`) | 429 | `-32012` | yes — `Retry-After` + `retry_after_ms` (30s: a streamed slot is held until the work finishes, so the GET figure would just cause a retry storm) |
| server-wide bridge record cap (`reserve()`'s own `global_record_cap`, Decision 15(d) — bounded in-memory state; distinct check from the pre-admission budget above, `reason=post_record_cap`; **fixed at 256, not currently operator-configurable by any flag or env var** — unlike the row above, there is no dial to raise; a sustained condition shows as `yuzu_mcp_bridge_records_active` approaching 256) | 429 | `-32012` | yes — `Retry-After` + `retry_after_ms` (30s, same as the row above); or retry without an SSE `Accept` for a plain response |
| this session's streamed-call cap (`reason=post_pin_slots`) | 429 | `-32012` | yes — retry. Admission first reclaims a slot from an undelivered final (#2740), so a retry can succeed before any call finishes. A refusal that survives that means either every slot is a call genuinely in flight ("wait for one to finish" is then true) or the reclaim found nothing takeable — see "A pin released to admit a new call" above |
| request id already in flight | 409 | `-32600` | no — use a fresh id |
| session unknown or expired | 404 | `-32007` | re-`initialize` |
| streaming disabled / shutting down | 200 | — | none needed; you get the plain response |
| server could not allocate | 200 | — | none needed; you get the plain response |

Two further shapes are **500s raised after dispatch** — the only refusals where the work is already running. Both carry `execution_id` in `error.data` alongside the correlation id, because the recovery is to fetch that execution, never to retry a mutating call:

| Condition | Status | Meaning |
|---|---|---|
| the stream could not be established | 500 | the command IS running; fetch by `execution_id`, or retry without an SSE `Accept` |
| the response could not be completed after dispatch | 500 | the command IS running; fetch by `execution_id` |

The last two admission conditions **degrade** rather than fail: the plain response is self-sufficient (it carries `execution_id`), so answering it beats advising a retry into a resource failure. Every refusal happens before the execution row is created, so a rejected call has dispatched nothing.

### Resuming, and the one case you cannot resume

Streamed frames are also committed to the session's replay ring, so a dropped connection can resume on the GET channel with `Last-Event-ID`. The result frame is **pinned**: ring eviction skips it, so a client that reconnects after a long gap still collects its answer.

If the ring has moved past your cursor, the server answers `kGap` rather than replaying a shortened history — a silently-short replay would leave you believing you had the lot. **Recovery from a gap is re-`initialize` plus fetch-by-`execution_id`**, not a retry of the original call: re-issuing a mutating `tools/call` would run it twice.
