# Resource Ledger - #4666 PR-1 bounded async log hand-off primitive

This ledger lists every thread, queue buffer, sink wrapper, and lock the PR-1 diff introduces, with
its owner and release path, for `agents/core/src/log_handoff.{hpp,cpp}`. A Resource Ledger is a
policy-floor artifact (CLAUDE.md standing rule 2), so it is a standalone file rather than a line in a
PR description. Nothing else changes in this PR — no production call site installs this primitive
yet (`main.cpp`/`service_win.cpp`/`guardian_engine.cpp`/`guardian_spark_runtime.cpp` are all
untouched; that wiring is PR-2, documented in this file's own "PR-2 wiring" section below).
Format follows
`docs/resource-ledgers/spark-criterion10-timing-instrumentation.md`.

No BLOCKING or CRITICAL finding in round 6 — the first round in this chain with no new code-level defect (only pre-existing/adjacent wording gaps and internal-consistency polish). See round 6's own section below for detail.

One BLOCKING (policy floor) and eight SHOULD findings, converged on independently by up to three parties each (cpp-safety, quality-engineer, happy-path, unhappy-path, cpp-expert, docs-writer, compliance-officer, sre — see `governance.d/` for the full run ledger), all fixed in one hardening commit per Gate 7's fold rule (none opened a new independently-reviewable surface):

- **BLOCKING, policy floor:** `U5` and `BLOCKER-1 regression` (`tests/unit/test_log_handoff.cpp`) called `REQUIRE(ok)` BEFORE joining their spawned `std::thread`s — on exactly the regression each test exists to catch, `REQUIRE`'s throw would unwind the stack while the thread was still joinable, and `std::thread::~thread()` on a joinable thread calls `std::terminate()` (SIGABRT of the whole binary). Fixed: cleanup (release the sink, join every thread) now runs unconditionally before any assertion, matching `BLOCKER round-2`'s already-correct pattern. Verified red-then-green by the orchestrator directly: against the true pre-fix `9646bd9ed` primitive, `BLOCKER-1` with the fixed test code now fails CLEANLY (`REQUIRE(ok)` false, exit 42) instead of `SIGABRT`ing.
- **SHOULD:** `teardown()`'s T0 (`clear_global_drain_handle`/`close_drain_admission`) ran BEFORE the `try` block, so a `std::mutex::lock()` throw there would escape the `noexcept` function via `std::terminate()` instead of the documented fail-closed `hard_exit()`. Fixed: both calls moved inside the `try`, still before the `ShutdownDeadlineGuard` is constructed (preserving the "fast, never blocks" timing intent).
- **SHOULD:** `register_global_drain_handle()`'s allocating work (`make_shared<DrainHandle>`, the sinks vector copy) ran AFTER the `LogHandoff` object already existed, so a `bad_alloc` there would unwind through a live object's destructor, mutating global logger state despite `create_with_sinks()`'s "nothing is installed" construction-failure contract. Fixed: that work now happens before the object exists; `DrainHandle` moved from an anonymous namespace to file scope so it can be forward-declared in the header and passed as a parameter. One small, accepted residual remains (a bare mutex lock after the object exists) — see the CONSTRUCTION FAILURE note in `log_handoff.hpp`.
- **SHOULD:** `install()` had no guard against being called after `teardown()`; `logger_` is null post-teardown, and `spdlog::registry::set_default_logger(nullptr)` unconditionally nulls the registry's `default_logger_` even for a null input (verified directly against `registry-inl.h`) — reintroducing the exact straggler-segfault hazard T2's null-sink swap exists to prevent. Fixed: `install()` now returns `nullptr` and does nothing if `logger_` is already null.
- **SHOULD:** the `construction_fault_for_test_` flag was consumed AFTER the `sinks.empty()` check, so a fault flag set ahead of an (accidental) empty-sinks call was never consumed and could leak into the next, unrelated test. Fixed: the flag is now consumed first, unconditionally.
- **SHOULD (doc accuracy):** the header's numbered T0/T1 step list had not been updated across either fix round, even though the free-standing prose paragraphs below it had. Fixed: the list now mentions `close_drain_admission()` at T0 and `wait_for_worker_exit()` at T1.

### Gate 8 targeted re-review of the hardening commit above (round 2; cpp-safety, security-guardian, quality-engineer) — 3 further findings, all fixed in a second commit

- **CRITICAL, BLOCKING (cpp-safety):** `~LogHandoff()`'s existing guard — `if (!torn_down_.load()) teardown();` — meant that when `torn_down_` was ALREADY `true` (set by a concurrent EXPLICIT `teardown()` call on another thread whose `teardown_body()` had not yet finished), the destructor never called `teardown()` at all, so it never reached the new `wait_for_teardown_completion()` and proceeded straight to destroying `pool_`/`logger_`/`wrapped_sinks_`/etc while the winner's `teardown_body()` could still be reading or writing those same members — a genuine use-after-free/data race, and precisely the defect class the concurrent-teardown-completion fix above exists to close. The header's own THREAD-SAFETY CONTRACT paragraph and this ledger's row on `teardown_done_mu_`/etc both named "the destructor" as one of the forms now covered — that claim was false for this exact interleaving. **Fixed: `~LogHandoff()` now calls `teardown()` unconditionally**, dropping the guard. Safe and cheap for the ordinary single-threaded case (the same thread's own earlier explicit `teardown()` call already set `teardown_done_`, so the exchange-then-wait returns immediately, no self-deadlock).
- **MEDIUM (security-guardian):** `teardown_with_action_for_test()` had no `try`/`catch` around T0/the guard/`teardown_body()`, unlike production `teardown()`. `ShutdownDeadlineGuard::~ShutdownDeadlineGuard()` unconditionally calls `cancel()` on ANY unwind through its scope, so an exception there would suppress the watchdog action (if not already fired) AND skip `mark_teardown_complete()` — leaving a concurrent loser on the same object blocked in `wait_for_teardown_completion()` with nothing watching it, on this test-only path specifically. **Fixed:** wrapped in a `try`/`catch(...)` that calls `mark_teardown_complete()` before rethrowing, preserving the documented "exception fails the TEST_CASE, not the whole binary" contract while also waking any loser.
- **BLOCKING (quality-engineer):** in fixing the BLOCKING finding above, the first hardening commit deleted `BLOCKER-1 regression`'s `yuzu::test::ScopeExit release_on_exit{[&] { h.sink->release(); }};` with nothing replacing its coverage for the test's FIRST assertion (which runs before either spawned thread exists) — reopening the identical whole-binary-`hard_exit()`-on-a-still-paused-sink hazard the file's own GATE DISCIPLINE convention exists to prevent, on a different trigger. **Fixed:** the `ScopeExit` is restored (idempotent alongside the explicit `release()` calls later in the test, same pattern `BLOCKER round-2` already uses). `U5` had the identical, pre-existing gap (predating this PR's hardening commit) — fixed in the same pass since it was cheap and already in scope.

All three verified: full `[log_handoff]` suite green (12094 assertions/14 cases) across 5 standalone runs plus the full `--suite agent` pass, and a TSan run, all after these three fixes.

### Second Gate 8 pass on the destructor fix (round 3; cpp-safety) — 1 further BLOCKING + 1 SHOULD, both fixed in a third commit

The destructor fix above (unconditional `teardown()`) is correct and necessary, but tracing its loser-branch call to `mark_teardown_complete()`'s counterpart all the way through surfaced a heap-use-after-free this commit's own change made a ROUTINE occurrence rather than a rare corner case:

- **BLOCKING (heap use-after-free):** `mark_teardown_complete()` called `teardown_done_cv_.notify_all()` AFTER releasing `teardown_done_mu_` (mirroring `DrainLease`'s own "notify after unlock" pattern) — a valid optimization there ONLY because `DrainGate` is kept alive independently by a `shared_ptr` the caller holds. Here the notified object (`teardown_done_mu_`/`teardown_done_cv_`) is a PLAIN MEMBER of the same `LogHandoff` a loser is about to destroy: if the winner unlocked before notifying, a loser that acquired the lock in that window, saw the predicate already true (`condition_variable::wait`'s predicate overload never actually blocks in that case), and returned could proceed straight into `~LogHandoff()` — destroying `teardown_done_mu_`/`teardown_done_cv_` — before the winner's own `notify_all()` call ran, which would then be a UAF on the WINNER's thread. This is exactly the "destructor races an in-flight `teardown()`" scenario the unconditional-destructor fix above exists to handle correctly, and that fix is precisely what makes this window a routine occurrence rather than a corner case. **Fixed:** `notify_all()` now runs WHILE STILL HOLDING the lock, so by the time the winner releases the mutex the notify has already happened — a loser can never observe the predicate true without the notify having already completed.
- **SHOULD:** `teardown()`'s loser branch called `wait_for_teardown_completion()` (which constructs a `std::unique_lock`, and `std::mutex::lock()` is permitted by the standard to throw `std::system_error`) with no `try`/`catch`, unlike T0's already-covered mutex locks — an exception there would escape the `noexcept teardown()` via `std::terminate()`. Pre-existing since the first hardening commit, but the unconditional-destructor fix above makes this branch execute on essentially every already-torn-down destruction, raising its practical exposure well past "rare corner case." **Fixed:** wrapped in the same `try { ... } catch (...) { hard_exit(kLogTeardownExitCode); }` shape T0 already uses.

Verified: full `[log_handoff]` suite green across 5 more standalone runs, the full `--suite agent` pass, a fresh TSan run, AND (new for this pass, since this specific bug class — a notified object's lifetime racing its own notifier — is ASan's domain, not TSan's) an ASan+UBSan build (`x64-linux-asan` triplet, `-Db_sanitize=address,undefined`) run clean across 3 runs.
