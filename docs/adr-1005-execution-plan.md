# ADR-1005 Execution Plan — Program Ladder + Vulnerability-Management Module Scoping

This document is the execution plan for [ADR-1005](adr/1005-headless-platform-use-case-engines.md) (PR #1918): headless platform, use-case engines, agentic-first as a core principle. It is **not** an ADR — it does not make new binding architectural decisions; it sequences ADR-1005's decisions into a phased program and works out the detailed scoping of the first use-case engine (UCE) module, vulnerability management, which re-homes the shipped server-side NVD sync + CVE matching (ADR-1005 grandfathered surface #2 — as extended 2026-07-07/08 to absorb the in-server vuln stack: the ADR-0023 correlation engine and the ADR-4001 dashboard lens; see "Relationship to ADR-0023 and ADR-4001" under Module scoping).

Two items below are flagged as candidates for their own future ADRs rather than settled here: the UCE host stack/runtime choice (deferred pending a requirements doc) and the auth-architecture delegation follow-up (ADR-1005's own named prerequisite).

**Assumption:** this plan assumes ADR-1005 is accepted (independent review + tracking issue + status flip, handled separately).

**Numbering note:** "Decision N" (bare) below refers to this plan's own 16-item decision log; "ADR-1005 Decision N" refers to ADR-1005's 7 decisions. The two number lines are independent and collide (e.g., this plan's Decision 5 is the catalogue-grain join; ADR-1005's Decision 5 is delegation) — always read the prefix.

## Decision log

These decisions resolve open scoping questions ADR-1005 deliberately left to "first module scoping" (ADR-1005 Decision 6) and the execution sequencing it leaves to a follow-up program. None override or amend ADR-1005 itself. One entry (Decision 15) is not module scoping but an execution-level surface-conformance commitment under ADR-1005 Decision 3/4's already-binding machine-surface mandate — recorded in this log because this plan is the program ledger for that surface.

1. **v1 vuln module is read-only against the server.** Write-back/orchestration (result-set materialization by the engine, remediation dispatch) waits for ADR-1005 Decision 5 delegation to ship. This constraint is enforced structurally, not just by omission: Phase 6 (module cutover to engine-principal auth) and Phase 7 (NVD removal) are both scoped and gated without requiring delegation — see Program ladder.
2. **Hand-off seam included, mechanism pinned.** The module's findings page hands off a device cohort as a **server-side object created via the server's public API, under the operator's own session** (e.g. a result set). The write must originate from **the operator's own browser, calling the Yuzu server's own origin using the operator's existing Yuzu session** — never a credential or token the UCE backend holds or forwards on the operator's behalf. This is what keeps decision 1's read-only property real: if the UCE backend ever held or proxied a write-capable credential, it would be performing the write, not the operator, regardless of whose session initiated it.
3. **Consumer model.** Agentic workers and orchestrators (e.g. a ServiceNow-style integration) consume the **Yuzu server directly** over REST/MCP and compose their own interpretation from server primitives. **No machine consumer of the UCE exists in this scoping** — the UCE's only external interface is its human UI. The UCE-host UI ↔ UCE-host backend seam is private (one product); ADR-1005's parity/discoverability obligations discharge at the *server* surface, not inside the UCE. **This exemption is scoped to parity/discoverability only. It does not extend to ADR-0017 management-group confinement, which is a separate requirement — see Decision 14.**
4. **Scale target:** build for 2,000 devices, **design for up to 500,000**. *(Amended 2026-07-11, maintainer direction: the ceiling is superseded — design for **≥500,000 endpoints with no architectural device-count ceiling**; no seam may carry a super-linear-in-fleet term or a fleet-inventory replica; linear irreducible output is acceptable. Requirements grade: `docs/uce-host-requirements.md` NF-1.)*
5. **Catalogue-grain join; no fleet-inventory replica in the engine.** The module never syncs a copy of per-device installed-software inventory. Cycle: sync CVE feeds → match feed data against the server's `software_catalog` rollup (distinct name/version pairs — on the order of 10–50k entries even at 500k devices, an estimate not yet empirically validated) → expand only the *matched* entries to affected devices via `query_software(name)` → persist **findings only**. This keeps egress at O(catalogue) + O(hits) instead of O(fleet), and removes bulk changed-since delta sync from this module's critical path. *(Grain correction 2026-07-12: the catalogue rollup carries distinct **names + device/version counts**, not name/version pairs — `SoftwareCatalogRow` has no version strings — so the match is a two-tier read: tier-1 name-level candidate filter on the catalogue, tier-2 per-device `query_software(name)` full-identity match; the 10–50k estimate is re-derived for that model at M2. See `docs/uce-host-requirements.md` F-1/F-4.)* **Caveat:** the bounded-cardinality assumption now applies at the **tier-2** per-device match (long-tail per-build or portable-app version strings could push per-device distinct-identity counts materially higher); M2's acceptance criterion (below) includes the re-derived two-tier cardinality/egress check against the 500k design ceiling before this assumption is load-bearing for a real deployment.
6. **The UCE host owns one shared fleet-data access layer**, used by every module (vulnerability management now; software asset management and others later) — API-backed reads, cached, request-paced against a single shared budget toward the server. Modules store only their own derived domain state (findings, license positions, etc.), never a fleet copy. The interface is designed so a synced replica could be introduced behind it later; the trigger for that is a module demonstrating a genuine need for device-grain data residency, not module count. **A likely candidate for that trigger is the second module itself:** software asset management's per-device license attribution may need device-grain data from day one. That module's own scoping must re-examine device-grain residency as an explicit first step, not assume this layer suffices by inheritance from the vuln module.
7. **NVD re-home is a strangler migration, not a code move.** The UCE module builds and proves its own feed-ingest + matcher first; a parity gate (module output == existing `POST /api/nvd/match` output on a reference inventory) precedes any server-side deletion — see the strengthened acceptance criterion on M3 below, and Phase 7. **No `/api/v1/nvd/*` twin is built** on the server — the existing capability has no REST-versioned or MCP twin today, and building one would freeze the interpretation logic into the platform contract at the exact moment it's being extracted. The gap closes by removing the capability, not by twinning it. (2026-07-08: this refusal covers **legacy** capability being extracted; it is not contradicted by ADR-4001's `/api/v1/vuln/*` + MCP twins, which ADR-1005 Decision 4 *mandates* for new work — those ship with the versioned-surface deprecation rider and their read-contract carries forward as the module's own spec; see "Relationship to ADR-0023 and ADR-4001".)
8. **Agent-side `vuln_scan` plugin:** the `inventory` collection action and the generic rule-evaluation / content-delivery plumbing stay core (mechanism, per ADR-1005 Decision 2). The plugin's embedded static `cve_rules.hpp` CVE list and its use as an authoritative `cve_scan` finding source are **frozen (no further rule updates) and marked deprecated**. The long-term replacement is engine-published content delivered through the existing content-distribution plane — the ruleset becomes engine-authored content evaluated by the agent's existing generic engine, which is cleanly mechanism-side.
9. **Postgres migration interplay and the audit-attribution window.** Two audit needs have different timelines and are treated separately:
   - **Actor attribution (`principal_class`: human / agent / engine) is needed the moment Phase 4 makes engine principals live**, independent of delegation. This is a small, additive field — it does not need to wait for a Postgres migration and is **pulled into Phase 4 directly** (see Phase 4, and Phase 3a below) so that no engine-principal action is ever audited without knowing what kind of actor performed it. Revoked engine-principal rows are soft-retained (never hard-deleted) so this attribution stays resolvable after a credential is revoked.
   - **The full delegation audit shape** (engine principal id, `is_delegated`, delegated operator identity, delegation artifact id, `delegation_verification_status`) lands with `AuditStore`'s Postgres migration (ladder Wave 1, already a mandatory-backfill item) — nothing can populate these fields correctly before Phase 5 ships, so there is no benefit to an earlier throwaway SQLite schema change. If Wave 1 slips past Phase 5's need for it, an additive SQLite column is the fallback for this delegation-specific shape only (not for `principal_class`, which ships earlier regardless — see Phase 3a/3b split below).
   - The engine-principal class does **not** wait for `RbacStore`'s later Postgres migration wave — adding an `engine` value to `principal_type` is additive on either substrate. **`ApiTokenStore`'s Postgres migration is pulled forward** to precede the engine-principal work, since it is already marked unblocked-to-migrate and engine credentials are semantically new rows worth being born on Postgres rather than migrated later. `ApiToken` rows carry an explicit, persisted principal-kind field set at creation time; session synthesis branches on that stored field, never on inference over the `principal_id` string shape — this is what keeps a legacy human-attributed token and a new engine-attributed token unambiguous during the live Phase 4 cutover.
10. **The API versioning/deprecation policy is written early — folded into Phase 0, not a separate parallel track.** ADR-0021 is landing new API surface now that needs a published compatibility posture regardless of delegation's timeline; there is no reason to wait. MCP tool versioning follows the same posture as REST: additive-only evolution, with a versioned tool name (e.g. `query_software_v2`) only on a breaking change — no per-tool semver scheme.
11. **UCE host stack is deferred** until a committed requirements document exists; the runtime/language choice is then made via its own review (ADR-worthy: hard to reverse, a real trade-off, and will surprise a future reader without the context). What is decided now: the UCE host's data layer is **its own Postgres database**, never the server's connection pool (ADR-1005 Decision 3 — no new private seam, no shared database access). *(Refined 2026-07-12, maintainer + colleague decision, trade-offs accepted: “its own Postgres database” is realised as a **separate database on the same PostgreSQL instance** as the server's — separate role, separate pool, cross-database access inside the instance forbidden (`postgres_fdw`/`dblink`/cross-DB grants) and mechanically revoked; the UCE deployable (backend + GUI, one artifact) runs on **its own VM in the same data centre**. Isolation mechanics, cross-origin consequences, and the phased implementation plan: `docs/uce-deployment-topology-design.md`; requirements grade: `docs/uce-host-requirements.md` NF-2/NF-3/NF-7/NF-8.)* Location is **inside the Yuzu repository**, under `engines/` (`engines/host`, `engines/modules/vuln`), shipped as a separate deployable artifact from `yuzu-server`, with CI enforcing that nothing under `engines/` includes or links against `server/` code.
12. **Naming:** "UCE" is adopted **by this plan** as shorthand for ADR-1005's "use-case engine" / "use-case engine host" — ADR-1005 itself does not abbreviate. The source directory stays the plain-English `engines/`.

(2026-07-08: ADR-4001/4002 began that scoping; 4001's surface is absorbed as grandfathered — see "Relationship to ADR-0023 and ADR-4001" — while the boundary analysis for 4002's scoring substrate remains owed at its own merge.)

Distinct from and additional to it (2026-07-07): a disclosure for any customer piloting **today's in-server vuln capability** (ADR-0023 M1a/M1b, absorbed as grandfathered — and, per the 2026-07-08 extension, explicitly including the **ADR-4001 `/vuln` dashboard lens**, where the interim status is far more customer-visible than a background scanner) — that it is interim, honestly scale-ceilinged, and scheduled for re-homing — owed by Workstream G **now**, independent of module-pilot scheduling, not deferred to Phase 7's deprecation cycle, and in place before any ADR-4001 implementation PR merges (enforced alongside the item-(xi) sequencing gate).

Machine-scope is not "no personal data": the dataset is device-attributable and therefore GDPR personal data when a device is person-assigned — classification settled in `docs/uce-host-requirements.md` §7 and the SOC 2 §3.5 findings row. 14. **Findings-viewing must enforce ADR-0017 management-group confinement, keyed to the viewing operator.** The module's own reads (Decision 5's catalogue-grain join, M2/M3) are necessarily fleet-wide — that is what makes the egress footprint tractable. But nothing about that read scope should leak into what an individual operator sees in the findings UI afterward. Decision 3's exemption of the UCE UI↔backend seam from ADR-1005 parity/discoverability obligations does **not** extend to this: confinement is a distinct requirement, and this plan already enforces it for Phase 5's delegated reads via the existing `authorize_list_read` chokepoint. **The mechanism for the module's own findings-viewing enforcement is not yet designed here, only required:** the UCE is a separate deployable with no Yuzu server session of its own (Decision 11), so it cannot literally call the same server-side chokepoint at view time. How it binds a viewing operator to their Yuzu management-group scope — a per-operator scoped read-through at view time, a session-exchange/identity-assertion mechanism, or a confinement predicate synced alongside findings and re-validated on a short TTL (never a stale cached snapshot, given Decision 6's shared access layer is explicitly a cache) — is an open design question. It is a **required, named deliverable of Phase 2c's requirements doc**, not something the citation above already solves. Whatever mechanism 2c selects, the outcome must match: a group-confined operator's findings page shows the same device set for a given CVE that `/devices` would show that operator for the same scope — never more. **This is a hard interlock, not a v2 nice-to-have, and it is unconditional: it gates M3's acceptance and Phase 6 the moment the mechanism must exist, not only once a multi-group or MSP-style customer happens to be onboarded** — mirroring the Phase 1/Interim-rules pattern already used for engine principals and quotas, but stronger: Phase 6 cuts the module over to fleet-wide-reading engine-principal credentials regardless of which customer is live at the time, so the gate fires on the mechanism's own live-and-verified state (M3's condition (d)), never on customer topology (see Program ladder and Phase 6). A multi-group/MSP pilot is simply the scenario where an unmet gate would be most visibly harmful — it does not define when the gate fires. One additional constraint sits on top of the gate without being its trigger: between M2 (module reading fleet-wide) and M3(d) verifying, the findings UI must not be exposed to a multi-group or MSP-style pilot customer — the phase gate prevents *cutover* with confinement unbuilt, and this clause closes the residual pre-cutover window where an in-development findings view could show a pilot operator unconfined cross-group data (the Workstream G pilot-readiness note in Decision 13 discloses this same boundary customer-side).
15. **MCP Streamable HTTP transport is a committed platform-surface requirement (2026-07-11).** The server's MCP endpoint (`/mcp/v1/`) gains the MCP-spec Streamable HTTP transport (protocol revisions 2025-03-26 and 2025-06-18): `Mcp-Session-Id` session lifecycle (minted on `initialize`, never required — plain-POST clients unaffected; unknown/expired id → 404, client re-initializes; `DELETE` supported), a GET SSE channel with `Last-Event-ID` resume, `Origin` validation on every method, notification POSTs answering 202 (spec MUST; today 204), and `notifications/progress` for long-running tools — `execute_instruction`/`execute_bundle` accept `_meta.progressToken` and, when the caller also accepts `text/event-stream`, answer over SSE with progress frames then the JSON-RPC response, holding the response open to terminal under a hard duration cap. This **supersedes the `docs/mcp-server.md` Phase-2 statement "No MCP-specific streaming transport is planned"** — recorded here rather than silently edited, since it reverses a written non-goal. Scope boundary: this is the **transport** layer of ADR-1005 Decision 3/4's machine surface; it is **not** the deferred durable/replayable event-subscription egress primitive — Decision 13's deferral and the egress-primitive decision (batch-join for the vuln module) stand unchanged, and this transport sits on no UCE milestone's critical path. Design commitments: sessions are transport affinity + a replay cursor only, held **in memory** (server restart → 404 → re-initialize per spec; no new store, no Postgres exception needed); streaming ships **ON by default** with a `--mcp-no-streaming` kill switch; **backward compatibility is a hard acceptance gate** — existing plain-POST flows stay byte-identical, the only externally visible changes to legacy clients are the 204→202 notification status and a new additive `Mcp-Session-Id` response header on `initialize` (safely ignored by clients that don't use it); the progress bridge consumes the existing `ExecutionEventBus`/`/api/v1/events` taxonomy (one bus, one taxonomy — no per-route event format); cancellation is transport-side only (`notifications/cancelled` ends the stream; dispatched instructions continue — a real instruction-recall primitive is a separate tracked platform follow-up, to carry an issue number before 2f PR 1 merges). Charter note: this entry is spec-conformance execution of ADR-1005 Decision 3/4's already-binding machine-surface mandate — how the mandated MCP surface complies with the MCP transport spec — not a new architectural boundary; its operational choices (in-memory sessions, ON-by-default, kill-switch shape) are reversible, below-ADR-bar commitments. **Security and bounds pre-commitments** (binding acceptance criteria for every 2f PR, not reviewer memory): (a) session ids are ≥128-bit CSPRNG values **bound at mint to the authenticated principal** — a valid id presented under any other principal returns 404 indistinguishable from unknown (no existence oracle), and a client-supplied `Mcp-Session-Id` on `initialize` is never adopted (fixation); the session id is transport affinity only, never itself an auth credential — per-request token auth stands. (b) The GET channel's exemption from per-tool tier/RBAC gating holds **because and only while** it carries this principal-bound session's own request-originated messages; any broadening (server-initiated messages beyond the session's own requests, cross-session fan-out) reopens the tier question. (c) Live streams re-validate the presented credential on each heartbeat tick and terminate on revocation — revocation cuts a live stream, not only future attaches. (d) All in-memory state is bounded: idle session TTL, per-principal and global session caps, and a bounded, per-session, non-durable replay ring; a resume past the ring window yields 404/re-initialize (matching the restart posture) — never a silent gap, since the 2f verification bullet promises the final response is replayable. (e) `Origin` absent is allowed only while `/mcp/v1/` requires an explicit credential (what defeats DNS rebinding); a present Origin is validated against a configured allowlist (scheme+host+port), not heuristics. (f) Stream-lifecycle honesty: a streamed POST that reaches the hard cap, or whose execution never reaches a terminal state (e.g. all targets offline), ends with a machine-parseable A4-shaped final frame carrying partial status and stating the execution continues server-side — cap expiry is never indistinguishable from completion; the durable result stays fetchable by `execution_id` (`get_execution_status`/`query_responses`) after any stream or session death, and an in-flight streamed request's final-response frame is eviction-exempt in the session ring while the session lives (bounded: one pending response per streamed request); ring contents inherit the classification of the durable responses they mirror — non-durable, bounded, no new data-inventory entry. (g) Streamed mutating tools remain non-idempotent: the recovery path for a broken stream is GET + `Last-Event-ID` resume or the durable `execution_id` fetch — never a blind re-POST; 2f PR 3's tool descriptions must instruct agentic clients accordingly. (h) The concurrent-stream caps and worker-pool budget cover **every** held-open response — streamed POSTs included, not only the GET channel — and the budget is computed once across ALL held-open SSE on the shared web server (`/api/v1/events` + dashboard SSE + MCP GET + streamed POST): combined caps stay below the worker-pool size minus a plain-REST reserve, never per-feature silos. (i) Credential re-validation distinguishes definitive revocation (terminate the stream) from indeterminate auth-backend failure (bounded grace window — no mass stream kill on a backend blip), and is cached so re-validation load stays cheap at fleet scale. (j) SSE event ids are per-session, never global; a session-cap hit rejects the new `initialize` with an A4 error rather than evicting a live session's streams; a `notifications/cancelled` close-frame states that the execution continues, and the cancellation is audited. (k) The metric family is named now, not left to PR 4 discretion: `yuzu_mcp_sessions_active`, `yuzu_mcp_sessions_opened_total`, `yuzu_mcp_streams_active`, `yuzu_mcp_stream_replay_ring_evictions_total` (the (d)/(f) promise-degradation signal, analogous to the shipped `yuzu_server_sse_api_replay_gap_total`), `yuzu_mcp_stream_rejects_total{reason}` — bounded labels pre-seeded to 0 per `docs/observability-conventions.md`. Delivered as parallel track **2f** (see Program ladder).
16. **The agentic context contract (invariant A5) is adopted as a standing platform requirement (2026-07-11).** Every new or materially changed in-scope machine surface (an MCP tool, or a capability whose Decision-4 twin includes one) must meet the seven-item contract now specified as **A5 in `docs/agentic-first-principle.md`** — standard spec annotations (`title`/`readOnlyHint`/`destructiveHint`/`idempotentHint`/`openWorldHint`), decision-grade descriptions, bounded documented input schemas, typed output schemas, self-recovering A4 errors with honest `retry_after_ms`, a maintained `initialize.instructions` orientation blob, and machine-readable specs exposed as MCP resources — or record an exception in **A5's own ledger** (`docs/agentic-first-principle.md` §A5 Exceptions — deliberately distinct from ADR-1005's twin-existence ledger; one control question per ledger) — each entry carries an issue number and a revisit-by date, and `enterprise-readiness` reviews the accumulated exceptions at Gate 6 so they cannot accrete into a shadow non-compliant surface. Rationale: the 2026-07-11 survey found the prose surface strong but the machine-readable metadata thin (no handshake instructions, destructiveness prose-only on destructive tools, ~40 tools without annotations or output schemas, `retry_after_ms` hardcoded null) — a spec-faithful agentic client currently learns far less than one that parses English. Like Decision 15, this entry is execution of ADR-1005 Decision 3/4's machine-surface mandate (context quality is part of the surface), not new architecture; it binds forward from adoption per A5's backfill policy. Enforcement rides the existing A1–A4 wiring: the Gate 4 consistency-auditor standing question gains the A5 conformance clause (PR 0.1's mechanism), and `security-guardian` co-checks `readOnlyHint`/`destructiveHint`/`idempotentHint` truthfulness against tier + dispatch behavior — a false safe-direction hint (incl. `idempotentHint: true` on a non-idempotent dispatch, which invites the blind re-POST Decision 15(g) forbids) is a BLOCKING (HIGH) finding; "materially changed" is defined per-se in A5's Materiality clause (tier, securable/operation, dispatch behavior, side-effect set, or spec-visible output). The existing-tool backlog is delivered as parallel track **2g** (see Program ladder); 2g PR 1 and 2f PR 1 both touch the `initialize` handler — independent tracks, coordinate at PR review, either order works.

## Program ladder

Critical path: **auth-architecture follow-up design → engine-principal class → module cutover**. Delegation (full write-back) is **not** on this critical path, since v1 ships read-only and autonomous per Decision 1 — it runs in parallel and gates only the later write-back phase.

```
P0 (docs: governance wiring + doc fan-out + versioning policy) ──► P1 (interim interlocks)
   │
   ├──► 2b auth follow-up design ──► P4 engine principals ──► P6 module → engine auth ──► P7 NVD strangler removal
   ├──► 2c UCE requirements + stack ADR (confinement-mechanism design only) ─────────────► feeds 2d
   ├──► 2e keyset pagination on query_software (#1634, independent of auth) ──────────────► gates M3(a2)
   ├──► 2f MCP Streamable HTTP transport (Decision 15 — independent; gates nothing downstream)
   ├──► 2g Agentic context contract backfill (Decision 16 / A5 — independent; gates nothing downstream)
   └──► 2d module domain half (M1–M4; M3 = parity + confinement gate, needs 2e) ─────────► P7
             └─ M3(d) confinement mechanism live + verified ──────────────────────────► gates P6 directly
        P3a audit principal_class (pulled forward, cheap) ──► gates P4
        P3b full delegation audit fields (PG Wave 1) ─────────────────────► P5 delegation
                                                                             (write-back only — off the P6/P7 critical path)
```

2e is deliberately pulled out of Phase 6: it is an ordinary authenticated-read improvement with no dependency on engine-principal auth, so gating it behind Phase 4/6 would have transitively delayed M3's parity gate behind the entire auth chain despite 2d being described as this program's most independent track. Likewise, Phase 6 depends on M3's condition (d) specifically — the confinement mechanism landing and being verified — not on M3's other four conditions (a/a2/b/c, the matching-parity and shadow-match work), which gate Phase 7 only; 2c is a design input consumed by 2d, not itself the thing Phase 6 waits on.

### Phase 4 — Engine principal class

Gated on Phase 2b's design being accepted **and Phase 3a** (actor-class attribution must exist before engine principals can act).

- **PR 4.1** — `ApiTokenStore` migrates to Postgres (pulled forward per Decision 9), with the persisted principal-kind field from Decision 9 included at creation.
- **PR 4.2** — introduce the `engine` RBAC principal type and a machine principal class on `Session`; engine token sessions attribute to the engine principal itself, not the creating human, branching on the persisted principal-kind field (never inferred).
- **PR 4.3** — engine-principal lifecycle surface (create/rotate/revoke, named responsible human owner, grant justification captured at creation, folded into the existing periodic access-review cadence) on both REST and MCP, plus an admin-console page composing that API. Least-privilege is enforced, not merely asserted: the grant model is default-deny per securable, with no "all permissions" toggle available to an engine principal — recreating the ServiceNow-integration's admin-token pattern must not be possible through this surface, not just discouraged by it. **How an issued credential is classified internal (first-party module, e.g. Phase 6's own credential) vs. external (third-party/BYO) is not yet designed here — it is a required, named deliverable of this PR.** Decision 9's persisted principal-kind field distinguishes human/agent/engine only; Phase 8's external-issuance gate (versioning policy, quota cap) has nothing to key off without a further internal/external attribute (or an equivalent operational convention) on that same field. **Whatever mechanism this PR selects, an unclassified or ambiguously-classified credential must default to external** (the stricter, gated treatment) — never to internal — so a classification bug or a not-yet-wired write path fails toward re-checking the Phase 8 interlocks, not toward silently skipping them.
- **PR 4.4** — minimum per-principal concurrency/quota cap, closing Issue 1.3, with a quota-exhaustion counter emitted so the server side can independently observe a UCE module approaching its budget (not reliant on the module self-reporting).
- **PR 4.5** — `principal_class=engine` becomes a live metric value.

### Phase 6 — Module moves to engine auth

Gated on **Phase 4 and M3's condition (d)** — the Decision 14 confinement mechanism, designed in 2c and built as part of 2d, live and verified per M3(d) — independent of M3's other four conditions (a/a2/b/c), which gate Phase 7 instead (not Phase 5 — v1 remains autonomous and read-only per Decision 1). The vuln module switches from a plain API token to engine-principal credentials with least-privilege grants (explicitly not the union-of-permissions pattern of the existing ServiceNow integration). This phase changes only which credential the module authenticates with — the device-expansion cap fix (2e) is independent and may already be in place by the time this phase runs. **M3(d) must be live and verified before this phase runs, full stop — not merely before a multi-group customer is onboarded, and not merely once 2c's design doc is accepted.** The module's own reads are fleet-wide from M2 onward (Decision 5), so an unconfined findings-viewing path is already exposed the moment credentials switch, regardless of which customer happens to be looking; gating this only on customer topology, or on design-doc acceptance rather than the built-and-verified mechanism, would let cutover proceed with the confinement gap still open.

### Module milestones (Phase 2d's longest track)

- **M1** — UCE host skeleton (server-API client with a min/max supported server-API version handshake, a sync scheduler, the shared fleet-data access layer from Decision 6, a UI shell) plus NVD 2.0 feed sync with a watermark, landing in the module's own Postgres. *Acceptance: CVE count and watermark match a server-side sync over the same window; the host itself exposes a readiness probe and a metrics surface matching `docs/observability-conventions.md` before this milestone is considered done — a CVE-matching module that silently stops syncing must be observable to an operator, not just to the server.*
- **M2** — catalogue-grain inventory join per Decision 5: read the fleet-wide software catalogue plus per-name device expansion, over a plain API token, autonomous reads only, request-paced. *Acceptance: the module's catalogue snapshot matches server reads for a pilot fleet, AND a synthetic high-cardinality version-string seed is used to measure sync/egress against the 500k design ceiling (validating or correcting the 10–50k catalogue-size estimate in Decision 5), AND the device-expansion read is exercised specifically for correctness (not just the catalogue read) given the 1000-row cap tracked at #1634.*
- **M3** — matcher parity, a findings store with a disposition lifecycle (exact state list pending
  reconciliation — see "Findings models compose, they don't compete" above), findings UI, and the
  operator hand-off seam from Decision 2. *Acceptance, strengthened — this is the gate that authorizes Phase 7's irreversible deletion, so it carries five conditions across two axes (matching-logic parity and device-expansion completeness are different checks, since `/api/nvd/match` itself has no device-count dimension — it takes a `{name,version}` inventory and returns CVE matches, nothing more):*
  - *(a) Matching-logic parity: given the identical `{name,version}` inventory input, the module's matcher returns the identical set of CVE findings as the existing `/api/nvd/match` route.*
  - *(a2) Device-expansion completeness (depends on 2e): for a software title seeded via a controlled synthetic fixture (not discovered through the same `query_software` path under test, to avoid a circular check) to be installed on more than 1,000 devices, the module's own device-expansion enumeration (via the keyset-paginated `query_software` from 2e) returns the complete device list with no cap-related truncation — verified against the fixture's known device count, not against `/api/nvd/match`, which was never involved in device counting.*
  - *(b) A production-scale shadow-match run against the live fleet during the deprecation window, comparing the **per-device set of CVE ids**, not just aggregate finding counts — a compensating false-positive/false-negative pair must not pass this check by netting out to the same total.*
  - *(c) Sign-off from someone other than the engineer who built the matcher and the reference corpus, since a milestone that grades its own homework is not an independent gate for an irreversible deletion.*
  - *(d) Decision 14's findings-viewing confinement is live and verified — a group-confined operator's findings view matches what `/devices` would show them for the same scope.*
  - *Phase 7's own implementation should additionally exercise synthetic adversarial version-string edge cases (epoch prefixes, backport/distro suffixes, wildcard CPEs) as part of its test design — this milestone's acceptance criteria establish the gate's structure, not an exhaustive input corpus.*
- **M4** — surpass parity: real package/version identity matching, version-range evaluation, additional feed sources for reduced false positives. *Acceptance: a fully-patched reference OS image reports zero package-level CVEs.*

### Egress-primitive decision

ADR-1005 Decision 6 requires evaluating at least two consumer archetypes even if only one ships.

- **Batch-join** (changed-since reads over the catalogue rollup plus per-name device expansion): matches the module's actual data cadence — CVE feeds update on an hourly-to-daily cycle, and per-agent inventory changes at most once a day. At the 500,000-device design ceiling, catalogue-grain access keeps this to tens of thousands of rows per cycle (pending the M2 cardinality validation above), not a fleet-wide scan.
- **Streaming** (a durable, replayable event subscription on inventory or catalogue mutations): evaluated and **not selected for v1** — it would add a new durable-log/retention/backpressure subsystem for data that does not benefit from sub-daily latency in this module, and would reintroduce gap-detection/replay-horizon complexity that batch-join avoids by construction.

Decision: **batch-join ships**; streaming is deferred, not rejected, and nothing in this plan precludes adding it later behind the same shared fleet-data access layer (Decision 6) if a future module demonstrates a genuine latency need.

- **Phase 4/5:** an engine token's session attributes to the engine principal (not its creator) in audit rows; attempting to issue an **external** engine credential via the admin console with either of the two Phase 8 interlocks (versioning policy published, quota cap live) deliberately unmet is refused with an audited denial, not merely a UI warning — Phase 6's own module credential is exempt from this check because it is **internal** (first-party, not the external/BYO case this gate targets); its read-only scope (Decision 1) is a separate property and is not itself what exempts it, so a future read-only *external* credential must still pass this gate. (The internal/external classification mechanism itself is PR 4.3's open deliverable — see Phase 4.) A delegated read on behalf of a group-confined operator returns only that operator's groups; the self-target guard blocks an engine from acting against its own delegated operator's account.
- **Phase 6:** a group-confined operator's findings-page device **set** for a given CVE matches what `/devices` would show them for the same scope — a count-only comparison is insufficient here for the same reason M3(b) rejects it for the shadow-match: a compensating over-inclusion/under-inclusion pair must not pass by netting out to the same total.
