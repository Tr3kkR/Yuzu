[CDX-P1-001]  HIGH · CONFIDENCE(hi) · PROVENANCE(test-run)
The A2 permission-discovery twins bypass the topology floor and disclose the complete RBAC role graph
- Location:  `server/core/src/discover_routes.cpp:56` and `server/core/src/discover_routes.cpp:369`; `server/core/src/mcp_server.cpp:1302` and `server/core/src/mcp_server.cpp:9336`
- Claim:     REST `GET /api/v1/discover/permissions` and MCP `discover_permissions` return the full role-to-permission authorization topology through unfloored `Infrastructure:Read`, so a plain authenticated user on the default RBAC-off installation can still retrieve the data this change says is admin-only.
- Evidence:  `build_permissions_catalog()` iterates `rbac_store.list_roles()` and, for every role, `rbac_store.get_role_permissions(role.name)`, then emits the resulting `roles[].permissions[]` grid (`discover_routes.cpp:56-80`). The REST handler calls `perm_fn(..., "Infrastructure", "Read")` (`discover_routes.cpp:369-380`). The MCP security row is `{"discover_permissions", {"Infrastructure", "Read"}}` and its handler repeats the same gate before calling the same builder (`mcp_server.cpp:1302`, `9336-9353`). The existing test passed and explicitly asserted that the REST gate is `Infrastructure:Read` (`test_discovery_routes.cpp:142-177`). `kTopologyFloor` contains only `AccessReview:Read`, `UserManagement:Read`, and `EnginePrincipal:Read` (`authz_topology_floor.hpp:52-56`).
- Scenario:  RBAC is left at its fresh-install default OFF → an attacker authenticates as an ordinary `user` → calls `GET /api/v1/discover/permissions` or the MCP twin → legacy authorization allows `Infrastructure:Read` → the response reveals every built-in/custom role and every permission/effect, including the same and strictly richer role graph than `/api/v1/rbac/roles` plus `/roles/{role}/permissions`, despite those routes now being floored.
- Inference: The discovery catalog is not merely a list of capability names; because it contains the complete role-to-allowed-operations grid, it is the authorization topology named by the floor. Sharing the same underlying `RbacStore` reads makes these two routes alternate transports around the intended chokepoint, and the passing test demonstrates the bypass configuration rather than refuting it.
- Anchor:    CONTRACT — `docs/auth-architecture.md` “The authorization topology floor (#2376)” says authorization topology reads require admin under RBAC-off and identifies the RBAC role graph as protected (`§` lines 1550-1601); `.claude/routed-concerns.md` “Authorization-topology floor (#2376)” requires `kTopologyFloor` to be the single chokepoint; `docs/agentic-first-principle.md` A2 identifies `/discover/permissions` as the full role → allowed-operations grid and requires authenticated discovery, not weaker authorization than its underlying data.
- Fix:       Gate both `GET /api/v1/discover/permissions` and `discover_permissions` on `UserManagement:Read` (including `kToolSecurityRows`, the handler gate, OpenAPI/user docs, and tests), so they reuse the existing floored pair while preserving REST/MCP parity; add an RBAC-off ordinary-user denial integration test for both twins and an RBAC-on holder test proving a live grant is not shadowed.
- Falsifier: A response-capture test showing an ordinary non-admin session with RBAC disabled receives 403 from both `/api/v1/discover/permissions` and MCP `discover_permissions` on the reviewed head, without changing the injected `perm_fn` semantics.
