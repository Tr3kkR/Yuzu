# Observability Conventions — Yuzu

The `sre` and `architect` agents load this document on any change that adds, removes, or modifies metrics, audit events, or lifecycle events. CLAUDE.md keeps a one-line pointer.

## Prometheus metrics

- All metrics use the `yuzu_` prefix.
  - Server metrics: `yuzu_server_*`
  - Agent metrics: `yuzu_agent_*`
- **Consistent label set:** `agent_id`, `plugin`, `method`, `status`, `os`, `arch`, `principal_class`. Avoid one-off labels — they prevent cross-cutting Grafana queries. `principal_class` (ADR-1005) is a **closed** set — `human` | `agent` | `none` | `engine` — on `yuzu_http_requests_total`; never free-form, never an authorization signal. **Hybrid basis (execution-plan PR 4.5):** `human`/`agent`/`none` classify by CREDENTIAL PRESENTATION (session cookie / bearer-or-API token / neither) — a traffic-shape signal, not a validated session. `engine` is the one exception — it requires the RESOLVED session (an engine principal authenticates with a Bearer token indistinguishable from a human API token at the header level, so presentation alone can't tell them apart), piggybacked off the session already resolved at the pre-routing chokepoint for the PR 4.4 quota gate (zero extra per-request auth cost). A request bearing an engine token whose session resolution FAILS stays presentation-shaped `agent`, never `engine` — see `server/core/src/principal_class.hpp` for the classifier pair (`principal_class_of` / `principal_class_resolved`).
- **Histogram buckets** (default for latency-style histograms): `0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0, 10.0`.
- **Bounded-label counters are pre-seeded to 0 at startup** — every known label combination of a closed-set label is initialised when the metric is described, so the family + HELP/TYPE are present on a healthy server and `absent()` alerts stay meaningful (examples: the NVD `reason` series, `yuzu_onbehalf_rejected_total{surface=http|grpc}`).
- **Fleet rollups over dynamically-reporting agents are absent-not-zero, NOT pre-seeded** — the complementary rule. A gauge family aggregated per-cycle from the reporting agent population (`yuzu_fleet_net_*`, `yuzu_fleet_spark_*`, `yuzu_fleet_perf_*`, `yuzu_fleet_guardian_journal_*`) is `clear_gauge_family()`'d and re-emitted each sweep, so a `(metric, os[, …])` nobody reported this cycle goes **absent**, never a fabricated 0. Pre-seeding `{os=windows}` before any Windows agent enrolls would fabricate a false "0 problems" reading — the exact trap this avoids. `> 0` alerts against a genuinely-absent series correctly evaluate to no-match (not a false negative), so the alert still fires the instant real data appears. The pre-seed-to-0 rule above is for **server-owned** closed-set series known at startup; this absent-not-zero rule is for **agent-population** rollups whose label values are only known once agents report. Note the `> 0`-still-fires remark above is about ABSENCE semantics only - it is not an endorsement of `> 0` as an alert form for any given family. The `yuzu_fleet_guardian_journal_*` **counter table** in particular is **monitor-only**: an unlabelled fleet SUM of per-agent cumulative counters, where neither `> 0` nor `increase()` is sound (see its type-honesty note). That claim is scoped to the counter table, not the whole name prefix - the family also carries three `*_seconds_max` **age gauges** with different semantics (next bullet).
- **Rollup op is chosen per table and lives in the CONSUMER, never in the row.** The `{tag, gauge, help}` row shape is deliberately op-agnostic; SUM is implicit in the counter table's `+=` and MAX in the age table's `std::max` (`agent_registry.cpp`), and each (agent struct, table) pair carries its own sizeof pin. A **MAX-rolled family** answers "how bad is the WORST endpoint" (a fleet SUM of ages is meaningless), carries a mechanical `_max` suffix on every gauge name so the semantics are visible on a graph, and - unlike the counter families - supports sound absolute-threshold alerting (`> X for: Y`; see the commented staleness examples in `yuzu-alerts.yml`). Caveat inherent to MAX: one agent's plausible-but-forged value below the plausibility ceiling OWNS the fleet value (a sum dilutes, a max is captured), so attribution needs a per-agent axis (#2083-class).
- **Emission-posture decision rule for agent-reported fleet signals:** sparse-omit-zero is correct ONLY when a 0 is uninformative (a counter that never fired). When 0 is a REAL reading (an age: "fresh just now"), the writer must emit it and dormancy must be expressed as **structural absence** (the emitter receives nullopt and ships nothing), never an omitted zero - otherwise a dead-idle producer is indistinguishable from a healthy idle one, and a fabricated dormant 0 would claim a live fresh producer. Reference implementation: `emit_guardian_journal_age_tags` + `GuardianEngine::journal_age_stats()` (the staleness pair emits including 0 while the drain worker is live; the whole family is absent while dormant).
- **A fleet rollup should be table-driven, and its meta-signals are the exception to absent-not-zero.** `yuzu_fleet_guardian_journal_*` is the reference shape: one `{tag, gauge, help}` row per signal drives the `clear_gauge_family()`, the accumulate, the publish AND the `describe()` registration, so a new signal cannot ship with a gauge but no HELP, or be cleared but never published. Follow it for new rollups rather than the hand-listed net/spark form. Its two meta-signals (`..._reporting`, `..._tag_rejected`) sit deliberately OUTSIDE the table and publish on every completed sweep **including at 0**: they are server-owned counts with a true value every cycle, so a 0 is a measurement rather than a fabricated zero. Note the corollary - because they are never cleared they retain their last value, so neither their absence nor a 0 detects a stalled sweep; use the sweep-duration histogram for that.
- Health endpoints (`/livez`, `/readyz`, `/healthz`) reflect every component's health and are scrapable.
- **Security events route to the SIEM via Prometheus, not directly.** We do not write security events to a SIEM sink from the app. Emit them through the Prometheus counter with an `event="security"` label; Splunk (and every other SIEM) has a Prometheus receiver and filters on `event`. This keeps a single egress path and lets the SIEM, not the app, decide what to ingest. Examples: `yuzu_grpc_subscribe_peer_mismatch_total{event="security",gateway_mode="false"}` (IP-binding stolen-session signal, #1059) and `yuzu_grpc_subscribe_identity_mismatch_total{event="security"}` (mTLS-identity stolen-session signal, #1118 — no `gateway_mode` label, since the mTLS check is gateway-mode-independent). Pair the metric (real-time SIEM/alerting) with the audit row (forensic detail): **the metric is the signal, the audit row is the evidence.** Carve-out: an event with **no resolvable principal** (e.g. a pre-auth ingress rejection like `yuzu_onbehalf_rejected_total`) has nothing to attribute an audit row to — it emits metric + (possibly sampled) log only, and the surface's doc must say so explicitly.

`yuzu_grpc_subscribe_peer_advisory_total{event="security",reason="mtls_identity_match|trusted_nat_cidr"}` (#1128) is the **tolerated** counterpart of `_peer_mismatch_total`: a Subscribe peer-IP mismatch that was downgraded to advisory (not rejected) under a NAT-aware accommodation. It pairs with a `session.peer_mismatch` audit row carrying `result="ok"` and `outcome=advisory` (vs the reject row's `result="denied"`). Read the two metrics together — a spike in `_advisory_total` alone is benign multi-egress churn; a spike in both `_advisory_total` and `_mismatch_total` is worth investigating. The `reason` label distinguishes which accommodation fired.

`yuzu_auth_lockout_applied_total` / `yuzu_auth_lockout_blocked_total` (SOC 2 CC6.3, account lockout) follow the same metric-is-the-signal / audit-row-is-the-evidence split, but with a deliberate asymmetry SIEM consumers must know. `_applied_total` increments **once** when an account crosses the failed-login threshold and is locked — paired one-to-one with a single `auth.lockout.applied` audit row. `_blocked_total` increments on **every** subsequent login attempt against an already-locked account; those blocked attempts are metric-only (**no** per-attempt audit row) to prevent audit-log flooding during a sustained brute-force. Read them together: a sustained spike in `_blocked_total` after a single `_applied_total` increment is the expected brute-force-against-a-locked-account shape; a spike in `_blocked_total` with **no** preceding `_applied_total` is anomalous (counter corruption or a pre-check bypass) and worth investigating. The matching admin-unlock and successful-login-reset both emit `auth.lockout.cleared`.

`yuzu_auth_local_disabled_total{target=break_glass|other}` (SOC 2 CC6.3, hardened mode) is the **only** signal for a local-password login rejected under `--auth-mode=sso-only` — that denial is deliberately **metric-only, never a per-attempt audit row** (same anti-flood rationale as `_blocked_total`: a credential spray under sso-only would otherwise grow `audit.db` without bound, and the account never locks on this path to short-circuit it). The CC6.3 *activation* evidence is the boot-posture log line, not a per-attempt row. The bounded `{target}` label (cardinality 2) lets a SIEM alert specifically on `target=break_glass` — repeated probing of the named break-glass account, a higher-signal event than generic `other` spray.

`yuzu_auth_break_glass_login_total` (SOC 2 CC6.6) increments **after** the break-glass password is verified (a wrong password takes the `auth.login_failed` path and never increments it), paired with a `Severity::kCritical` `auth.breakglass.login` audit row. Because break-glass use is rare by design there is no flood risk; alert on **any** increment. The richer evidence chain for SIEM correlation is the audit row (`auth.breakglass.armed` → `auth.breakglass.login`/`auth.breakglass.denied`); wire an alert on the counter as the cheap always-on signal.

`yuzu_auth_service_token_role_capped_total` (no labels) increments every time `synthesize_token_session` floors a service-scoped API token's session role to `user`, i.e. on every service-scoped session — not just when the creator's live role would otherwise have differed. It's deliberately **operational, not `event="security"`**: this is confinement working as designed on every legitimate service-scoped request, not an anomaly, so there is no expected-vs-unexpected split to alert on (a "did the cap actually change the outcome" signal would need the creator's live role, i.e. the `get_user_role()` lookup this branch deliberately skips for the common case). Purpose is debuggability, not detection — an operator investigating why a service-scoped token behaves as `user` can confirm the cap is active from this counter alone, with no audit row needed (there is nothing to audit — the session was never anything other than `user`).

`yuzu_auth_service_scope_default_denied_total{permission,path_class}` (#2298 PR 3 — "the flip") increments every time a service-scoped API token is refused a `(securable_type, operation)` pair because it isn't on the seeded-empty `kServiceScopeGlobalSafe` allow-list — at both increment sites: `AuthRoutes::require_permission` (REST, `path_class` via `resolve_body_cap`) and MCP's C8 `denied`-class short-circuit (`path_class="mcp"`, wired separately since C8 returns before `require_permission` ever runs — see `docs/adr/1006-service-scope-default-deny.md` Consequences). It's deliberately **operational, not `event="security"`** — a hit is the flip working as designed on a not-yet-migrated route, not an anomaly — and its purpose is Phase 2 migration *prioritization*: `permission` names which `(securable, operation)` pair to consider re-admitting first, ranked by real call volume rather than guesswork. No alert rule exists for it (tracked as a follow-up); the pairing evidence for any individual denial is the `auth.permission_required`/`mcp_audit("denied", ...)` audit row (metric-is-the-signal, audit-row-is-the-evidence, same split as elsewhere on this page). **Once a `(permission, path_class)` pair's LAST route migrates onto `require_fleet_read` (#3290 Phase 2 — `Inventory:Read` first), that series stops incrementing entirely for the migrated route(s)** — the migrated route no longer reaches `require_permission`'s service branch at all. This is exact for MCP's `path_class="mcp"`: `query_installed_software` was the only `Inventory:Read` MCP tool, so `(Inventory:Read, mcp)` genuinely goes flat/absent post-migration. It is NOT yet true for REST's `path_class`: `GET /api/v1/inventory/tables` and `POST /api/v1/inventory/query` still gate via `require_permission` on the same `Inventory:Read` permission and resolve to the same catch-all `path_class="default"` (`body_cap_policy.hpp`'s `kBodyCapTable` has no `/api/v1/inventory` prefix entry) that `/inventory/software` used pre-migration — so `(Inventory:Read, default)` keeps incrementing from those still-unmigrated siblings, and a flat REST series should NOT be read as "the migration didn't take" or a real one dismissed as noise. Read the series per-route only once every route sharing a `(permission, path_class)` pair has migrated. No production fleet exists yet, so this metric currently has no real traffic to prioritize by; Phase 2 migration order is documented reasoning instead (`docs/security-reviews/service-scope-phase2-migrations-2026-08.md`), revisited once real traffic exists.

`yuzu_server_quarantine_gate_total{outcome}` and `yuzu_server_system_reserved_push_total{capability,result}` (#881 / #3402) are both bounded-label, pre-seeded-to-0 families driven from their own `constexpr` arrays (`kQuarantineGateOutcomes`; `kSystemReservedPushes` x `kSystemReservedPushResults`), so an emit site cannot add a label value without it appearing in the boot seed. The gate family is deliberately **operational, not `event="security"`**: `outcome="exempt_control_plugin"` and `outcome="fresh"` are the containment gate working on every dispatch, and the value worth alerting on is `fail_closed`, which means instruction dispatch is refusing the whole fleet because containment state is unreadable — a **dispatch outage**, not a quarantine event. The push family meters the three server-internal pushes that deliberately BYPASS that gate; its `result="undelivered"` series is the one that matters (an undelivered `__guard__.push_rules` leaves a device unenforced) and is pre-seeded precisely so it can be alerted on before it ever fires. Both follow the standard split: the per-denial evidence is the `quarantine.dispatch_denied` audit row, the metric is the signal. Note the deliberate exception on the neighbouring `yuzu_server_dispatch_target_rejected_total{route,reason}` family — its `reason="quarantined"` value is EXCLUDED from the `YuzuDispatchTargetRejected` alert, because correct containment would otherwise page (one looping automation against a contained host clears the `>3/15m` threshold, and a fail-closed episode increments by the whole fleet at once); a rule that fires on the control working gets silenced, taking the genuine near-miss signal with it.

`yuzu_server_quarantine_reapply_total{result}` and `yuzu_server_quarantine_endpoint_unconfirmed{reachability}` (#3425) extend the same `#881` family with the reconnect-reconciliation half: the gate above stops *Yuzu* reaching a contained device, this pair covers the device's OWN firewall converging after it reconnects. The counter is another bounded-label, pre-seeded-to-0 family driven from its own `constexpr` array (`kQuarantineReapplyResults`), same discipline as `kQuarantineGateOutcomes`. The gauge is the one exception to this page's counter-heavy convention: it measures CURRENT divergence (an active record not yet confirmed contained), which must be able to go back down when a reconcile succeeds, so a monotonic counter cannot express it — seeded to `0` for both label values at boot for the identical "absent must not read as never ran" reason. It is also the one metric on this page that is explicitly **per-replica, never summed**: each server instance's view of "is this agent's session live" is local to the gRPC connections it holds, so `sum()`ing the gauge across instances double-counts every agent connected to a DIFFERENT replica than the one publishing the metric. The `reachability` label is the SAME exclusion shape as `yuzu_server_dispatch_target_rejected_total{reason="quarantined"}` two paragraphs up, applied to a gauge instead of a counter: `reachability="offline"` is excluded from the shipped alert (`YuzuQuarantineEndpointUnconfirmed`) because a device quarantined while off is legitimately unconfirmed for its whole offline duration, and paging on that is paging on correct behaviour — the alert fires only on `reachability="connected"`, the population where non-confirmation is a genuine reconciliation failure rather than an unreachable device. The evidence trail is the `quarantine.reapply` audit row (system principal, `trigger=tick|heartbeat` or a `CONFIRMED` detail), the same audit-row-is-the-evidence/metric-is-the-signal split as everywhere else on this page. `yuzu_server_quarantine_reconciler_tick_healthy` (added in the same #3425 line, governance round 11) is a THIRD shape again: an unlabelled boolean freshness gauge, pre-seeded to `1` rather than `0` — the divergence gauge above is only ever `.set()` on a tick that reaches its normal publish, so on a tick that aborts early it silently FREEZES instead of reading absent or zero; this gauge is what distinguishes "genuinely confirmed" from "haven't been able to check," and it is the one gauge on this page where the optimistic pre-seed is the deliberately correct choice, not the `0` convention used everywhere else.

The NVD CVE sync exposes three server metrics — `yuzu_nvd_total_cves` (gauge), `yuzu_nvd_backfill_complete` (gauge), and `yuzu_nvd_sync_failures_total{reason}` (counter, `reason` ∈ {`connection`, `http_429`, `http_403`, `http_other`, `parse`}). The counter follows the standard bounded-label convention: every `reason` series is initialised to `0` at startup so the family (and its HELP/TYPE) is present on a healthy server and `absent()`-style alerts stay meaningful. See [metrics.md → NVD CVE sync metrics](user-manual/metrics.md#nvd-cve-sync-metrics) for the full per-metric reference and `reason`-label semantics.

`yuzu_server_principal_quota_exhausted_total{side,limit}` (PR 4.4, ADR-1005 class engine principals) registers the same bounded-label family: all 4 series in the `side` (`engine`|`operator`) x `limit` (`concurrency`|`rate`) closed cross-product are pre-seeded to `0` at startup. It is deliberately **operational, not `event="security"`** — hitting a per-principal quota cap is expected steady-state behaviour for a busy engine principal, not an attack signal — and it carries no `principal_id` label (bounded cardinality only; a per-principal breakdown belongs in a future dashboard join against the engine-principal store, not a Prometheus label). `side="operator"` is pre-seeded but dormant until Phase 5 delegation debits the operator side too. Its companion `yuzu_server_principal_quota_admits_total{side}` (governance hardening round) registers the same bounded-label, pre-seeded-to-0 family for the admit path — every request that clears both quota dimensions increments it, making the exhaustion *rate* (`exhausted / (exhausted + admits)`) computable rather than just the raw exhaustion count. See [metrics.md → Per-principal quota metric](user-manual/metrics.md#per-principal-quota-metric-pr-44-adr-1005-class-engine-principals) for the full reference and the audit-row carve-out rationale.

`yuzu_engine_principal_confirm_total{surface,result}` (#2404) registers the same bounded-label, pre-seeded-to-0 family: the `surface` (`rest`|`mcp`) x `result` (`success`|`conflict`|`client_error`|`transient`) closed cross-product (8 series) is initialised at startup so a `409`-conflict or `503`-transient retry storm on the credential-confirm endpoint is alertable (it has no per-route label on `yuzu_http_requests_total`). Unlike the access-review counters below, it IS wired on **both** surfaces (a distinct `surface` label prevents double-count) because an agentic MCP client and a REST client can each drive the replay-storm shape #2404 fixes. **Scope contract:** it counts only confirm calls that reached the credential store **or** found it unavailable at the store-open guard — pre-store denials (permission, input-validation, the MCP approval-gate consumed-ticket replay) are deliberately excluded, so the label set stays a fact about store outcomes rather than a catch-all endpoint tally; the increment is stamped **before** the audit emission so an audit-store failure cannot suppress it. Deliberately **operational, not `event="security"`** — a replay conflict is an expected agent-retry shape, not an attack signal — and carries no `principal_id` label; pair it with the `engine_principal.credential.confirm` audit rows for per-principal forensics (same metric-is-the-signal / audit-row-is-the-evidence split).

`yuzu_api_token_confirm_total{surface,result}` (P2 #11, SOC 2 CC6.3) registers the human-owned twin of `yuzu_engine_principal_confirm_total` immediately above: the same `surface` (`rest`|`mcp`) x `result` (`success`|`conflict`|`client_error`|`transient`) closed cross-product (8 series), pre-seeded to `0` at startup for the same `absent()`-alert reason, and exported as a `constexpr` symbol (`rotation_sweep_naming.hpp`'s `kApiTokenConfirmTotalMetric`) rather than a string literal so the registration site and the increment sites can't silently diverge into a shadow series. It shares the sweep-driver's kind-discrimination header alongside `yuzu_api_token_rotation_auto_revoked_total` and `yuzu_api_token_rotation_events_total{reason}` (the human twins of the two `yuzu_engine_principal_rotation_*` sweep counters — the T12 maintenance sweep in server.cpp routes each swept row to the engine or human family, never both, keyed on the row's own `principal_kind`; see `rotation_sweep_naming.hpp`'s header comment for the full chokepoint rationale). **`yuzu_api_token_confirm_total` is live — both transports increment it**: `rest_api_v1.cpp`'s `POST /api/v1/tokens/{id}/confirm` handler (`surface="rest"`) and `mcp_server.cpp`'s `confirm_api_token_rotation` tool handler (`surface="mcp"`), both through the shared `kApiTokenConfirmTotalMetric` symbol. It follows the identical scope contract and stamp-before-audit discipline as its engine twin, pairing with whatever audit action the confirm-rotation piece emits for per-principal forensics (distinct from the `api_token.rotation.auto_revoke` / `.successor_unused` rows this piece DOES ship — see [audit-log.md](user-manual/audit-log.md), those are the sweep-driven auto-revoke/successor-unused half, not confirm). See [metrics.md → Human API-token confirm metric](user-manual/metrics.md#human-api-token-confirm-metric-p2-11) for the full reference.

`yuzu_mcp_poll_total{tool,result}` (#3344) registers the same bounded-label, pre-seeded-to-0 family: the `tool` (`get_execution_status`|`query_responses`|`get_bundle_result`) x `result` (`ready`|`not_ready`) closed cross-product (6 series) is initialised at startup. These three tools are the only MCP surfaces that emit a **success-shaped** `retry_after_ms` hint (pending execution/incomplete bundle/rows-still-in-flight is not an error, so the hint lives in the tool's own structured payload, not the A4 `error.data`); `not_ready` means this exact response carried the hint, `ready` means it was served terminal/complete without one. **Scope contract:** it counts only calls that reached a served verdict — pre-verdict denials (tier, permission, invalid-params, not-found) are deliberately excluded, already visible via the existing denial counters and A4 envelopes, so this series stays a fact about poll outcomes rather than a catch-all tool tally. Deliberately **operational, not `event="security"`** — a high poll rate is expected agentic-worker behaviour, not an anomaly. Its purpose is the same data-driven tuning role as the NVD sync failures above: the named `retry_after_ms` floor constants (`server/core/src/mcp_retry.hpp`) were shipped as a mechanical derivation (no dispatch-to-first-result latency histogram exists to measure from) rather than a measured one, and this series' `not_ready` fraction is what lets a future PR re-tune them from real data instead of guessing again. See [docs/mcp-server.md → `retry_after_ms` floors](mcp-server.md#retry_after_ms-floors-3344) for the full constant table.

`yuzu_server_rotation_initiator_disagreements_total` / `yuzu_server_rotation_pair_resolve_failures_total`
(#2961) are `ApiTokenStore`-owned gauges, gauge-published on every `/metrics`
scrape (no counter pre-seed needed — same shape as `yuzu_server_token_cache_size`).
`_initiator_disagreements_total` is a **tamper/corruption signal on an
authorization input**, not an operational one: `resolve_rotation_initiator`
fails a confirm closed when its RAM grace-cache copy of `requesting_user`
and the durable `api_tokens.rotation_initiator` column disagree, which is
not reachable through any live code path (both are written from the same
value in the same locked mint transaction) — alert on **any** nonzero
value, not a rate threshold. `_pair_resolve_failures_total` is operability-
only (a swallowed post-revoke partner-clear failure; stale metadata, not a
lockout risk). See [metrics.md → Rotation-durability tamper/corruption gauges](user-manual/metrics.md#rotation-durability-tampercorruption-gauges-2961)
for the full reference.

Periodic access reviews (SOC 2 CC6.2, hardening round) added four bounded-label series wired at the REST handlers only (MCP twins not double-counted): `yuzu_access_review_export_total{format}` (`format` ∈ `json`|`csv`, pre-seeded to `0`), `yuzu_access_review_export_duration_seconds` (histogram, the `build_access_review` grant-population read latency), `yuzu_access_review_campaigns_opened_total` (no labels), and `yuzu_access_review_attestations_total{decision}` (`decision` ∈ `attested`|`flagged_revoke`, pre-seeded to `0`). All four are **operational, not `event="security"`** — a review export or a recorded decision is expected, self-audited operator activity (own audit rows: `access_review.exported`, `.campaign_opened`, `.attested`/`.flagged`), not an anomaly signal; pair the counters with the audit rows for evidence, same metric-is-the-signal/audit-row-is-the-evidence split used elsewhere on this page. See [metrics.md → Access review metrics](user-manual/metrics.md#access-review-metrics) for the full reference.

`InstructionStore` (ADR-0058) registers two bounded-label, pre-seeded-to-0 families at boot: `yuzu_server_instruction_read_degrade_total{reason}` (`reason` ∈ `store_not_open`|`pool_acquire_timeout`|`query_error`) and `yuzu_server_instruction_write_degrade_total{reason}` (`reason` ∈ the five call sites that can fail — `insert_definition_row`|`update_definition`|`delete_definition`|`insert_set_row`|`delete_set`) both increment on a genuine DB/lease failure at their respective read or write call sites, distinct from a legitimate not-found/empty result (the ADR-0036 fail-open class this migration closes). Both are deliberately **operational, not `event="security"`** — ordinary Postgres contention, not an attack signal. No dedicated audit row backs either (the class is infrastructure health, not an access decision); pair with the `spdlog::error`/`spdlog::warn` log line at the same call site for the specific offending id/reason. This store has no legacy-SQLite backfill (ADR-0009's fresh-start-by-default class) and so no backfill-outcome metric.

`RuntimeConfigStore` (ADR-0060) registers one bounded-label, pre-seeded-to-0 family at boot: `yuzu_server_runtime_config_read_degrade_total{reason}` (`reason` ∈ `store_not_open`|`pool_acquire_timeout`|`query_error`|`crypto_error`), incremented independently by `get_all()`, `get()`, and `read_secret()` (each holds its own sampler so a hot call site's degrade cannot mask a cold one from ever logging) on a genuine DB/lease/decrypt failure, distinct from a legitimate not-found/empty result. Deliberately **operational, not `event="security"`** — a `crypto_error` here means an undecryptable secret (KEK/DB pairing mismatch, corruption), the same fail-closed class `docs/user-manual/server-admin.md`'s "Key management (secrets KEK)" section already documents for `AuthDB`/`WebhookStore`, not an intrusion signal. No dedicated audit row backs it; pair with the `spdlog::warn` log line at the same call site. This store has no legacy-SQLite backfill (ADR-0009's fresh-start-by-default class) — the separate `warn_if_legacy_data_present()` boot check is a one-shot log line, not a metric.

`UpdateRegistry` (ADR-0061) registers two bounded-label, pre-seeded-to-0 families at boot, gated on `--ota-enabled`'s default-on state: `yuzu_server_update_registry_read_degrade_total{reason}` and `yuzu_server_update_registry_write_degrade_total{reason}` (both `reason` ∈ `store_not_open`|`pool_acquire_timeout`|`query_error` — a narrower, uniform vocabulary than `InstructionStore`'s per-call-site write reasons, since every one of `UpdateRegistry`'s four methods shares the same three failure shapes). Plain counter increments, no rate-limited sampler — unlike `RuntimeConfigStore`'s hot admin-read paths, this store's own call pattern (admin-driven writes, per-heartbeat-but-not-per-request reads) isn't the log-flood-prone shape a sampler exists for (see `docs/postgres-store-playbook.md`'s "Degrade log level" note for the log-level-vs-counter distinction this store's authoring made explicit). This is the ONLY post-boot degrade signal for this store — `is_open()` is construction-time-only and never re-checked at runtime, so a healthy boot followed by a sustained Postgres degrade during a live OTA rollout has no other observable trace. Deliberately **operational, not `event="security"`**. No dedicated audit row backs either family; pair with the `spdlog::error` log line at the same call site. This store has no legacy-SQLite backfill (ADR-0009's fresh-start-by-default class) — the separate `legacy_sqlite_probe::warn_if_legacy_rows()` boot check is a one-shot log line, not a metric.

`SessionStore` (HA WS-1/1a, ADR-2002 §4) registers two bounded-label, pre-seeded-to-0 families at boot: `yuzu_auth_session_store_degrade_total{op}` (`op` ∈ `validate`|`create`|`touch`|`generation_refresh`|`reap`|`invalidate_user`) and `yuzu_auth_session_reap_total` (plain counter). The degrade family increments on a genuine PostgreSQL read/write failure on the durable-session auth hot path — a `validate` degrade for an uncached token fails the request **closed** (401), a `create` degrade fails the login closed, and `generation_refresh`/`touch`/`invalidate_user`/`reap` degrades are best-effort paths that log and continue (the absolute `expires_at` on every cached session is the backstop). Deliberately **operational, not `event="security"`** — ordinary Postgres contention/failover on the session store, the same class as `yuzu_auth_read_degrade_total` and `yuzu_server_rbac_read_degrade_total`, not an attack signal; pair with the `spdlog::warn`/`debug` line at the same call site. `yuzu_auth_session_reap_total` is the retention-sweep proof (rows deleted by the ~15-minute clock-guarded reap) — the evidence artifact for this store's storage-limitation control, and belongs alongside the `Yuzu*Retention*` series in any retention dashboard. The reap pass is single-writer on Postgres today (one server); it joins the shared clock-guarded-retention family and becomes PG-shared-state under the ADR-0012 advisory lock when a second replica lands. This store has no legacy backfill — there was never a durable session table (fresh-start).

**The rotation sweep (#2964) now carries the full clock-guarded-retention shape**, the same seven-part contract `audit_store`'s retention pass follows — reused via the shared `audit_retention_rules.hpp::classify`, not forked. `yuzu_rotation_sweep_declined_total` and `yuzu_rotation_sweep_lock_skipped_total` are the two liveness-adjacent counters this adds to the existing `yuzu_rotation_sweep_capped_total` family (kind-neutral naming throughout, shared across engine-credential and human API-token rotation pairs — a tick-level clock-guard verdict is not attributable to one kind's rows). Unlike `audit_store`, this pass is single-writer-on-Postgres **by construction**: it takes a store-wide session advisory lock in its own key namespace before classifying, so `lock_skipped_total` is expected to be nonzero only on a multi-replica deployment, and — the operationally load-bearing fact — **must stay at exactly `0` on a single-replica deployment** (the default), since one thread taking one lock once per tick can never legitimately lose an election against itself; any movement there on a single replica is a fault, not routine contention. As with `audit_store`, an accepted, un-capped, un-declined tick increments **none** of this family's counters, so a dead sweep thread is invisible to all of them — the same silence-means-healthy gap the audit family closes with its unconditional passes-attempted counter and last-pass gauge. `yuzu_rotation_sweep_last_pass_timestamp_seconds` (gauge, pre-seeded at `0` at boot) and `yuzu_rotation_sweep_bootstrap_declines_total` (counter) close that gap the same way; `YuzuRotationSweepNotRunning` (`docs/prometheus/yuzu-alerts.yml`) alerts on the gauge's staleness. The gauge is stamped on `Ok`/`Declined` verdicts only — it proves the classification transaction ran, not that any predecessor was actually revoked, so pair it with `yuzu_rotation_sweep_lost_revocations_total` (an accepted tick that lost some or all of its per-pair revoke transactions to pool contention still stamps this gauge fresh). See [metrics.md → Rotation-sweep clock guard metrics](user-manual/metrics.md#rotation-sweep-clock-guard-metrics-2964) for the full reference, plus `docs/ops-runbooks/rotation-sweep-clock-guard.md` for operator triage.

## Audit events

Structured JSON envelope:

```json
{
  "timestamp": "2026-04-18T12:34:56.789Z",
  "principal": "alice",
  "action": "noun.verb",
  "target_type": "User",
  "target_id": "bob",
  "result": "ok|denied|error",
  "detail": "free-form context"
}
```

- Suitable for direct delivery to Splunk HEC or generic webhook sinks.
- Indexed by `timestamp` and `principal` for efficient queries.
- **`detail` is SANITISED on read, not delivered verbatim.** `AuditStore::query()` applies
  `sanitized_detail()` at the single point where a stored row becomes a value a caller can hold, so
  every reader (REST v1, the legacy REST route, MCP, Settings - six call sites) is covered by
  construction rather than by each remembering. Today the rule replaces the `value=` segment of a
  `target_type="RuntimeConfig"` row naming a secret-valued key: those rows recorded the plaintext
  credential before the write path was fixed, and they are still on disk. A reader therefore never
  receives the stored bytes for a secret-bearing target. **Any new audit reader must go through
  `AuditStore::query()`** - reading `audit_events` directly re-opens the disclosure.
- **Never add a `detail` filter or free-text search to `AuditQuery`.** It has fields for
  `principal`, `action`, `target_type`, `target_id`, `since`/`until` and `action_prefixes`, and
  deliberately none for `detail`. A `LIKE`/search parameter over `detail` would let any
  `AuditLog:Read` holder binary-search the *stored* bytes and recover exactly the credentials the
  read-time sanitiser exists to withhold - converting the redaction into a disclosure oracle. The
  absence of that filter is what makes read-time redaction sufficient rather than cosmetic, so it is
  a standing constraint, not an unimplemented feature.
- **A raw database extract will NOT match API or export output**, for rows predating the read-time
  sanitiser. The rows are deliberately left byte-unchanged - rewriting audit history to remove
  embarrassing content is a worse posture than declining to disclose it, and there is no hash chain
  over `audit_events` that would make such a rewrite distinguishable from concealment. The
  consequence is a real discrepancy: an auditor given DB-level access sees the stored plaintext,
  while the same row sampled through `GET /api/v1/audit` shows `value=<redacted>`. **Disclose that
  discrepancy proactively** rather than letting it be discovered - it is a compensating disclosure
  control operating at the read layer, not a claim about what is stored.
- Denied operations MUST emit an audit event — `spdlog::warn` alone breaks the SOC 2 CC7.2 evidence chain. Example: the MCP Streamable HTTP transport (track 2f) emits `mcp.session.open` / `mcp.session.close` (`result="success"`) and `mcp.session.reject` (`result="failure"`, `detail="reason=origin|protocol_version|unknown_session|missing_session_header|per_principal_cap|global_cap|id_generation|shutdown"`) on `target_type="McpSession"` — the reject verb fires on **every** transport denial (origin, protocol-version, unknown/expired session, cap), routed through the shared `try_persist_audit` kernel so a persist failure is logged, never silently swallowed. (Note: `mcp.session.reject` itself uses `result="failure"` for every transport-layer denial, not `"denied"` — `tools/call` (the `mcp.<tool_name>` verb) instead uses `"denied"` for most client-caused rejections (tier, read-only, schema, input-bounds, per-submitter cap, approval mismatch/replay — see `docs/user-manual/audit-log.md`'s "Result vocabulary"), with several known exceptions still client-caused but audited `"failure"` (`approve_request`/`reject_request`, `set_tag`'s validation-failure rejection, `execute_bundle`'s out-of-scope rejection, and the access-review campaign family among them — not an exhaustive list, tracked for a full sweep in #3176; `delete_tag`'s not-found rejection uses its own third token, `"not_found"`, not `"failure"`). So the `mcp.*` verbs are not one surface-wide convention, and even within `tools/call` `"denied"` is the dominant pattern rather than an invariant. Do not author a `mcp.*` SIEM rule assuming one token family covers every verb; check the specific verb.)

**MCP Streamable HTTP streams (track 2f PR 2)** add two verbs — `mcp.stream.attach` and `mcp.stream.close` (the latter carrying `reason=` from the closed set `client_disconnect|superseded|session_terminated|credential_revoked|auth_unavailable|internal_error|cancelled|cap_expired|record_gone|completed` — the last four are the streamed-POST surface, produced by its pump — live wherever `--mcp-enable-streamed-post` is set, which is the default (opt out with `--no-mcp-streamed-post`)) — and widen the `mcp.session.reject` `reason=` set with `not_acceptable`, `per_principal_stream_cap`, `global_stream_cap`, `stream_handover_pending`, `terminal_poisoned`, and `replay_window_exceeded` (the last on `mcp.session.close`), plus the streamed-POST admission denials `post_per_principal_cap`, `post_global_cap`, `post_record_cap`, `post_pin_slots`, `post_duplicate_request_id` and `post_unknown_session` (2f PR 3b; `post_record_cap` added #2918). Both `mcp.stream.*` verbs carry `surface=post` on a streamed POST, so a GET attach and a POST attach stay separable in the log rather than both reading as "a stream". Every value here is a static literal, no label ever derived from caller input — but only most are pre-seeded on the matching `yuzu_mcp_stream_rejects_total{reason}` / `yuzu_mcp_stream_closes_total{reason}` counter: `terminal_poisoned` (from the 2f PR 3a `kPoisoned` close reason) is missing from `server.cpp`'s hand-written pre-seed list (a pre-existing gap, not introduced here), so that series stays absent, not `0`, until the first poisoning event — the same class of drift the `kPostRejectReasons` derived-list pattern exists to prevent for the streamed-POST family, just not yet applied here.
- **Shutdown-time teardowns are evidence-silent only while what they reap stays independently recoverable (#2489 comp-S1, #2517).** The MCP progress bridge audits every record it reaps on a live server (`mcp.bridge.forced_expire`, `mcp.bridge.session_dead`). A record `shutdown()`'s own walk finds already CLEANLY resolved (its terminal published, or a real POST-wire delivery, or normal projector settlement) is reclaimed silently: the process is terminating, the audit sink is itself tearing down, and the client's result stays durably fetchable by `execution_id`, so the absent row evidences nothing that was actually lost. That is the exemption this convention describes, and it still applies to the ordinary case.
  A record `shutdown()` finds *claimed but with its terminal disposition never resolved* - a pressure-visitor claim (`torn_down`) whose `teardown_claimed` call never reached (or never completed) Step 1, most often because a concurrent `sweep()` lost the race against `shutdown_started_` - does NOT get the exemption: `shutdown()` poisons the stream (any currently-connected client gets an honest close instead of heart-beating past process exit) and emits ONE aggregate `mcp.bridge.shutdown_reap` audit row naming the count, rather than per-record rows (publishing per-record evidence here would itself violate `teardown_claimed`'s exactly-once arbitration - the abandoned claim is never re-entered, only poisoned). Read a gap between `yuzu_mcp_bridge_records_active` at its last scrape and the reap rows in the log, with no `shutdown_reap` row either, as a clean shutdown; a `shutdown_reap` row names exactly how many were not. This inference holds only while the reap walk itself completes without throwing - the whole walk still runs inside one swallowing `catch (...)` (#2515, unaddressed by this fix), so a throw partway through can leave both an absent row AND an unresolved record, which is NOT the clean-shutdown case. No metric backs this - the process is exiting and the series would never be scraped, so the audit row is the only durable evidence. The convention generalises: a background reaper may skip its audit on the shutdown path only while what it reaps stays independently recoverable OR was never left in an unresolved state to begin with. One that reaps something a client cannot re-fetch, or whose disposition was never decided, owes an aggregate "N records reaped at shutdown" row instead.
- **Store-availability 503 guards do NOT audit.** A request rejected because a store's database never opened (`is_open()` gate, e.g. the `/api/v1/tokens` routes per #347 CH-3) is an *operational* event, not a principal action: the guard runs before any token/principal interaction, so there is no operation to evidence. The CC7.2 evidence for the outage is the boot-time `spdlog::error` plus the store's entry in the `/readyz` conjunction (and, once #1385 lands, the store-readiness gauge). This is the platform-wide convention for every store-down guard — do not add per-request audit rows to these paths.

## Event format (envelope)

All events — lifecycle, compliance, audit, system — follow a common envelope so downstream parsers can demultiplex by `event_type` without per-source schemas:

```json
{
  "event_type": "...",
  "timestamp": "...",
  "source": "server|agent|gateway",
  "payload": { ... }
}
```

## Response schemas

All instruction response data must be **typed** for downstream consumption (ClickHouse, Splunk, etc.). Permitted column types:

- `bool`, `int32`, `int64`, `string`, `datetime`, `guid`, `clob`

`clob` is reserved for large text fields with configurable truncation. See `docs/data-architecture.md` for the analytics-integration view.
