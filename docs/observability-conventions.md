# Observability Conventions — Yuzu

The `sre` and `architect` agents load this document on any change that adds, removes, or modifies metrics, audit events, or lifecycle events. CLAUDE.md keeps a one-line pointer.

## Prometheus metrics

- All metrics use the `yuzu_` prefix.
  - Server metrics: `yuzu_server_*`
  - Agent metrics: `yuzu_agent_*`
- **Consistent label set:** `agent_id`, `plugin`, `method`, `status`, `os`, `arch`, `principal_class`. Avoid one-off labels — they prevent cross-cutting Grafana queries. `principal_class` (ADR-1005) is a **closed** set — `human` | `agent` | `none` | `engine` — on `yuzu_http_requests_total`; never free-form, never an authorization signal. **Hybrid basis (execution-plan PR 4.5):** `human`/`agent`/`none` classify by CREDENTIAL PRESENTATION (session cookie / bearer-or-API token / neither) — a traffic-shape signal, not a validated session. `engine` is the one exception — it requires the RESOLVED session (an engine principal authenticates with a Bearer token indistinguishable from a human API token at the header level, so presentation alone can't tell them apart), piggybacked off the session already resolved at the pre-routing chokepoint for the PR 4.4 quota gate (zero extra per-request auth cost). A request bearing an engine token whose session resolution FAILS stays presentation-shaped `agent`, never `engine` — see `server/core/src/principal_class.hpp` for the classifier pair (`principal_class_of` / `principal_class_resolved`).
- **Histogram buckets** (default for latency-style histograms): `0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0, 10.0`.
- **Bounded-label counters are pre-seeded to 0 at startup** — every known label combination of a closed-set label is initialised when the metric is described, so the family + HELP/TYPE are present on a healthy server and `absent()` alerts stay meaningful (examples: the NVD `reason` series, `yuzu_onbehalf_rejected_total{surface=http|grpc}`).
- **Fleet rollups over dynamically-reporting agents are absent-not-zero, NOT pre-seeded** — the complementary rule. A gauge family aggregated per-cycle from the reporting agent population (`yuzu_fleet_net_*`, `yuzu_fleet_spark_*`, `yuzu_fleet_perf_*`, `yuzu_fleet_guardian_journal_*`) is `clear_gauge_family()`'d and re-emitted each sweep, so a `(metric, os[, …])` nobody reported this cycle goes **absent**, never a fabricated 0. Pre-seeding `{os=windows}` before any Windows agent enrolls would fabricate a false "0 problems" reading — the exact trap this avoids. `> 0` alerts against a genuinely-absent series correctly evaluate to no-match (not a false negative), so the alert still fires the instant real data appears. The pre-seed-to-0 rule above is for **server-owned** closed-set series known at startup; this absent-not-zero rule is for **agent-population** rollups whose label values are only known once agents report. Note the `> 0`-still-fires remark above is about ABSENCE semantics only - it is not an endorsement of `> 0` as an alert form for any given family. The `yuzu_fleet_guardian_journal_*` **counter table** in particular is **monitor-only**: an unlabelled fleet SUM of per-agent cumulative counters, where neither `> 0` nor `increase()` is sound (see its type-honesty note). That claim is scoped to the counter table, not the whole name prefix - the family also carries three `*_seconds_max` **age gauges** with different semantics (next bullet).
- **Rollup op is chosen per table and lives in the CONSUMER, never in the row.** The `{tag, gauge, help}` row shape is deliberately op-agnostic; SUM is implicit in the counter table's `+=` and MAX in the age table's `std::max` (`agent_registry.cpp`), and each (agent struct, table) pair carries its own sizeof pin. A **MAX-rolled family** answers "how bad is the WORST endpoint" (a fleet SUM of ages is meaningless), carries a mechanical `_max` suffix on every gauge name so the semantics are visible on a graph, and - unlike the counter families - supports sound absolute-threshold alerting (`> X for: Y`; see the commented staleness examples in `yuzu-alerts.yml`). Caveat inherent to MAX: one agent's plausible-but-forged value below the plausibility ceiling OWNS the fleet value (a sum dilutes, a max is captured), so attribution needs a per-agent axis (#2083-class).
- **Emission-posture decision rule for agent-reported fleet signals:** sparse-omit-zero is correct ONLY when a 0 is uninformative (a counter that never fired). When 0 is a REAL reading (an age: "fresh just now"), the writer must emit it and dormancy must be expressed as **structural absence** (the emitter receives nullopt and ships nothing), never an omitted zero - otherwise a dead-idle producer is indistinguishable from a healthy idle one, and a fabricated dormant 0 would claim a live fresh producer. Reference implementation: `emit_guardian_journal_age_tags` + `GuardianEngine::journal_age_stats()` (the staleness pair emits including 0 while the drain worker is live; the whole family is absent while dormant).
- **A fleet rollup should be table-driven, and its meta-signals are the exception to absent-not-zero.** `yuzu_fleet_guardian_journal_*` is the reference shape: one `{tag, gauge, help}` row per signal drives the `clear_gauge_family()`, the accumulate, the publish AND the `describe()` registration, so a new signal cannot ship with a gauge but no HELP, or be cleared but never published. Follow it for new rollups rather than the hand-listed net/spark form. Its two meta-signals (`..._reporting`, `..._tag_rejected`) sit deliberately OUTSIDE the table and publish on every completed sweep **including at 0**: they are server-owned counts with a true value every cycle, so a 0 is a measurement rather than a fabricated zero. Note the corollary - because they are never cleared they retain their last value, so neither their absence nor a 0 detects a stalled sweep; use the sweep-duration histogram for that.
- Health endpoints (`/livez`, `/readyz`, `/healthz`) reflect every component's health and are scrapable.
- **Security events route to the SIEM via Prometheus, not directly.** We do not write security events to a SIEM sink from the app. Emit them through the Prometheus counter with an `event="security"` label; Splunk (and every other SIEM) has a Prometheus receiver and filters on `event`. This keeps a single egress path and lets the SIEM, not the app, decide what to ingest. Examples: `yuzu_grpc_subscribe_peer_mismatch_total{event="security",gateway_mode="false"}` (IP-binding stolen-session signal, #1059) and `yuzu_grpc_subscribe_identity_mismatch_total{event="security"}` (mTLS-identity stolen-session signal, #1118 — no `gateway_mode` label, since the mTLS check is gateway-mode-independent). Pair the metric (real-time SIEM/alerting) with the audit row (forensic detail): **the metric is the signal, the audit row is the evidence.** Carve-out: an event with **no resolvable principal** (e.g. a pre-auth ingress rejection like `yuzu_onbehalf_rejected_total`) has nothing to attribute an audit row to — it emits metric + (possibly sampled) log only, and the surface's doc must say so explicitly.

`yuzu_grpc_subscribe_peer_advisory_total{event="security",reason="mtls_identity_match|trusted_nat_cidr"}` (#1128) is the **tolerated** counterpart of `_peer_mismatch_total`: a Subscribe peer-IP mismatch that was downgraded to advisory (not rejected) under a NAT-aware accommodation. It pairs with a `session.peer_mismatch` audit row carrying `result="ok"` and `outcome=advisory` (vs the reject row's `result="denied"`). Read the two metrics together — a spike in `_advisory_total` alone is benign multi-egress churn; a spike in both `_advisory_total` and `_mismatch_total` is worth investigating. The `reason` label distinguishes which accommodation fired.

`yuzu_auth_lockout_applied_total` / `yuzu_auth_lockout_blocked_total` (SOC 2 CC6.3, account lockout) follow the same metric-is-the-signal / audit-row-is-the-evidence split, but with a deliberate asymmetry SIEM consumers must know. `_applied_total` increments **once** when an account crosses the failed-login threshold and is locked — paired one-to-one with a single `auth.lockout.applied` audit row. `_blocked_total` increments on **every** subsequent login attempt against an already-locked account; those blocked attempts are metric-only (**no** per-attempt audit row) to prevent audit-log flooding during a sustained brute-force. Read them together: a sustained spike in `_blocked_total` after a single `_applied_total` increment is the expected brute-force-against-a-locked-account shape; a spike in `_blocked_total` with **no** preceding `_applied_total` is anomalous (counter corruption or a pre-check bypass) and worth investigating. The matching admin-unlock and successful-login-reset both emit `auth.lockout.cleared`.

`yuzu_auth_local_disabled_total{target=break_glass|other}` (SOC 2 CC6.3, hardened mode) is the **only** signal for a local-password login rejected under `--auth-mode=sso-only` — that denial is deliberately **metric-only, never a per-attempt audit row** (same anti-flood rationale as `_blocked_total`: a credential spray under sso-only would otherwise grow `audit.db` without bound, and the account never locks on this path to short-circuit it). The CC6.3 *activation* evidence is the boot-posture log line, not a per-attempt row. The bounded `{target}` label (cardinality 2) lets a SIEM alert specifically on `target=break_glass` — repeated probing of the named break-glass account, a higher-signal event than generic `other` spray.

`yuzu_auth_break_glass_login_total` (SOC 2 CC6.6) increments **after** the break-glass password is verified (a wrong password takes the `auth.login_failed` path and never increments it), paired with a `Severity::kCritical` `auth.breakglass.login` audit row. Because break-glass use is rare by design there is no flood risk; alert on **any** increment. The richer evidence chain for SIEM correlation is the audit row (`auth.breakglass.armed` → `auth.breakglass.login`/`auth.breakglass.denied`); wire an alert on the counter as the cheap always-on signal.

The NVD CVE sync exposes three server metrics — `yuzu_nvd_total_cves` (gauge), `yuzu_nvd_backfill_complete` (gauge), and `yuzu_nvd_sync_failures_total{reason}` (counter, `reason` ∈ {`connection`, `http_429`, `http_403`, `http_other`, `parse`}). The counter follows the standard bounded-label convention: every `reason` series is initialised to `0` at startup so the family (and its HELP/TYPE) is present on a healthy server and `absent()`-style alerts stay meaningful. See [metrics.md → NVD CVE sync metrics](user-manual/metrics.md#nvd-cve-sync-metrics) for the full per-metric reference and `reason`-label semantics.

`yuzu_server_principal_quota_exhausted_total{side,limit}` (PR 4.4, ADR-1005 class engine principals) registers the same bounded-label family: all 4 series in the `side` (`engine`|`operator`) x `limit` (`concurrency`|`rate`) closed cross-product are pre-seeded to `0` at startup. It is deliberately **operational, not `event="security"`** — hitting a per-principal quota cap is expected steady-state behaviour for a busy engine principal, not an attack signal — and it carries no `principal_id` label (bounded cardinality only; a per-principal breakdown belongs in a future dashboard join against the engine-principal store, not a Prometheus label). `side="operator"` is pre-seeded but dormant until Phase 5 delegation debits the operator side too. Its companion `yuzu_server_principal_quota_admits_total{side}` (governance hardening round) registers the same bounded-label, pre-seeded-to-0 family for the admit path — every request that clears both quota dimensions increments it, making the exhaustion *rate* (`exhausted / (exhausted + admits)`) computable rather than just the raw exhaustion count. See [metrics.md → Per-principal quota metric](user-manual/metrics.md#per-principal-quota-metric-pr-44-adr-1005-class-engine-principals) for the full reference and the audit-row carve-out rationale.

Periodic access reviews (SOC 2 CC6.2, hardening round) added four bounded-label series wired at the REST handlers only (MCP twins not double-counted): `yuzu_access_review_export_total{format}` (`format` ∈ `json`|`csv`, pre-seeded to `0`), `yuzu_access_review_export_duration_seconds` (histogram, the `build_access_review` grant-population read latency), `yuzu_access_review_campaigns_opened_total` (no labels), and `yuzu_access_review_attestations_total{decision}` (`decision` ∈ `attested`|`flagged_revoke`, pre-seeded to `0`). All four are **operational, not `event="security"`** — a review export or a recorded decision is expected, self-audited operator activity (own audit rows: `access_review.exported`, `.campaign_opened`, `.attested`/`.flagged`), not an anomaly signal; pair the counters with the audit rows for evidence, same metric-is-the-signal/audit-row-is-the-evidence split used elsewhere on this page. See [metrics.md → Access review metrics](user-manual/metrics.md#access-review-metrics) for the full reference.

## Audit events

Structured JSON envelope:

```json
{
  "timestamp": "2026-04-18T12:34:56.789Z",
  "principal": "alice",
  "action": "noun.verb",
  "target_type": "User",
  "target_id": "bob",
  "result": "ok|denied|error",
  "detail": "free-form context"
}
```

- Suitable for direct delivery to Splunk HEC or generic webhook sinks.
- Indexed by `timestamp` and `principal` for efficient queries.
- Denied operations MUST emit an audit event — `spdlog::warn` alone breaks the SOC 2 CC7.2 evidence chain. Example: the MCP Streamable HTTP transport (track 2f) emits `mcp.session.open` / `mcp.session.close` (`result="success"`) and `mcp.session.reject` (`result="failure"`, `detail="reason=origin|protocol_version|unknown_session|missing_session_header|per_principal_cap|global_cap"`) on `target_type="McpSession"` — the reject verb fires on **every** transport denial (origin, protocol-version, unknown/expired session, cap), routed through the shared `try_persist_audit` kernel so a persist failure is logged, never silently swallowed. (Note: the MCP surface uses `"success"`/`"failure"` result tokens, not the `"ok"`/`"denied"` of the envelope example above — a pre-existing surface-wide convention across all `mcp.*` verbs; author SIEM rules for `mcp.*` accordingly.)

**MCP Streamable HTTP streams (track 2f PR 2)** add two verbs — `mcp.stream.attach` and `mcp.stream.close` (the latter carrying `reason=` from the closed set `client_disconnect|superseded|session_terminated|credential_revoked|auth_unavailable|internal_error`) — and widen the `mcp.session.reject` `reason=` set with `not_acceptable`, `per_principal_stream_cap`, `global_stream_cap`, `stream_handover_pending`, and `replay_window_exceeded` (the last on `mcp.session.close`). Every value is a static literal, pre-seeded on the matching `yuzu_mcp_stream_rejects_total{reason}` / `yuzu_mcp_stream_closes_total{reason}` counter — no label is ever derived from caller input.
- **Store-availability 503 guards do NOT audit.** A request rejected because a store's database never opened (`is_open()` gate, e.g. the `/api/v1/tokens` routes per #347 CH-3) is an *operational* event, not a principal action: the guard runs before any token/principal interaction, so there is no operation to evidence. The CC7.2 evidence for the outage is the boot-time `spdlog::error` plus the store's entry in the `/readyz` conjunction (and, once #1385 lands, the store-readiness gauge). This is the platform-wide convention for every store-down guard — do not add per-request audit rows to these paths.

## Event format (envelope)

All events — lifecycle, compliance, audit, system — follow a common envelope so downstream parsers can demultiplex by `event_type` without per-source schemas:

```json
{
  "event_type": "...",
  "timestamp": "...",
  "source": "server|agent|gateway",
  "payload": { ... }
}
```

## Response schemas

All instruction response data must be **typed** for downstream consumption (ClickHouse, Splunk, etc.). Permitted column types:

- `bool`, `int32`, `int64`, `string`, `datetime`, `guid`, `clob`

`clob` is reserved for large text fields with configurable truncation. See `docs/data-architecture.md` for the analytics-integration view.
