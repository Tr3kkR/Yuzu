- **Guardian/Spark rule ids and Spark keys are neutralised before they reach a log line, closing an operator-authored log-injection exposure (CWE-117, #4665).** A rule id containing a newline could previously forge a whole physical log line, and one containing a space or `=` could forge extra tokens on the same line, in log statements across the legacy file/registry/service guards, `SparkEngine`, the Guardian engine, and the server's Guardian push/event-store code — none of these sites validated or neutralised the value before printing it, unlike the existing `Guardian T_*` diagnostic lines. Every such print site now wraps its rule id, path, registry hive/key, value type, service/agent identifier or unit name through a shared neutraliser (`common/include/yuzu/log_token.hpp`) before it is written. **`POST /api/v1/guaranteed-state/rules` and MCP `create_guardian_rule` now reject a non-conforming `rule_id` at creation** (`400` on REST, a JSON-RPC error on MCP, both audited as `denied`) instead of accepting anything non-empty — a rule id must match `[A-Za-z0-9._-]+` and be at most 256 bytes; this was already the documented contract, now actually enforced. **Breaking — for a fleet with a pre-existing non-conforming `rule_id`:** validation is create-only and not retroactive, so an existing rule whose id predates this change is never torn down and its prior enforcement survives; the upgraded agent now additionally rejects a whole incoming push if any one rule in it fails validation (rather than silently dropping only the offending rule while still reporting itself caught up), so the server-side push builder excludes a non-conforming legacy row from every push it builds instead of sending one the agent is guaranteed to reject — that row itself stops receiving policy updates until removed (MCP `delete_guardian_rule`, REST `DELETE`, or a direct database delete, depending on which restriction the id trips — see `docs/user-manual/upgrading.md`'s Behaviour change entry), but every OTHER rule in scope keeps updating normally.
