- **Guardian/Spark rule ids and Spark keys are neutralised before they reach a log line, closing an operator-authored log-injection exposure (CWE-117, #4665).** A rule id containing a newline could previously forge a whole physical log line, and one containing a space or `=` could forge extra tokens on the same line, in log statements across the legacy file/registry/service guards, `SparkEngine`, the Guardian engine, and the server's Guardian push/event-store code — none of these sites validated or neutralised the value before printing it, unlike the existing `Guardian T_*` diagnostic lines. Every such print site now wraps its rule id, path, registry hive/key, service name or unit name through a shared neutraliser (`common/include/yuzu/log_token.hpp`) before it is written. **`POST /api/v1/guaranteed-state/rules` and MCP `create_guardian_rule` now reject a non-conforming `rule_id` at creation** (`400`, audited as `denied`) instead of accepting anything non-empty — a rule id must match `[A-Za-z0-9._-]+` and be at most 256 bytes; this was already the documented contract, now actually enforced. Validation is create-only and not retroactive: an existing rule whose id predates this change is unaffected and keeps working. A malformed full-sync push from the server is now rejected in its entirety rather than silently dropping only the offending rule while the agent still reports itself caught up.
