- **Wee Tam CI: per-job Postgres durability-off guard and four-cluster fingerprint (#2167 follow-up).** Fixed the Wee Tam (Windows) CI pool having no guard against durability-off drift on the native, pre-set-DSN Postgres clusters it uses (`scripts/ci/ensure-postgres.sh` path 1) — unlike the Docker path's tuning-label drift guard, and unlike agent 0, which was not even probed. Durability was previously applied only once, at provisioning (`deploy/windows/Provision-Windows-Runner.ps1`); a later drift on any of the four clusters surfaced only as a 700s `[pg]`-shard `TIMEOUT`. Every path-1 invocation (any pre-set `YUZU_TEST_POSTGRES_DSN`, on any OS — not only Wee Tam's Windows jobs) now reads `fsync`/`synchronous_commit`/`full_page_writes` from the cluster it is about to use before exporting the DSN and, only under GitHub Actions against a loopback host proven by a plain-URI DSN with a toolchain-manifest-vouched `psql` and no `PGHOST`-family override in the job environment, heals a drifted setting with `ALTER SYSTEM` + `pg_reload_conf()` (behind an in-session loopback/target identity check and a config-parse check) and a bounded re-read; elsewhere drift is only reported, never healed. `deploy/windows/Assert-Toolchain.ps1` now also prints a read-only, one-line durability-settings fingerprint for all four Wee Tam clusters on every run, so a drift is visible in seconds instead of as a shard timeout, and (opt-in, CI-only) exports the manifest-vouched `psql` path the new guard uses. A manifest-vouched per-agent (or agent-0/base) probe failure is retried briefly and then fails the job outright, rather than falling back onto the shared agent-0 cluster and reintroducing the cross-job contention the per-agent split exists to avoid. The guard also fails the job on an unreadable/unparseable settings read, a heal whose `ALTER SYSTEM`/`pg_reload_conf()` (or either in-session check) fails, a cluster that stays not-off after a heal, or a post-heal re-read that itself fails.
