- **MCP streamed POST (SSE-on-POST) lands, and ships OFF.** `execute_instruction` callers that supply a `_meta.progressToken` and send `Accept: text/event-stream` can receive progress on the POST response itself rather than the session's GET channel (ADR-1005 Decision 15, track 2f PR 3b). The machinery is complete and reviewed, but it landed with two bounds defects open against it and is therefore gated behind **`--mcp-enable-streamed-post` (default off)**. **Both are fixed in this same release** — see the #2739 and #2740 entries under Fixed — but the flag stays off by default; turning it on is a separate rung. The two, so an operator who opts in early knows what they own: **#2739**, the 120 s response cap is arbitrated only on a pass that finds neither progress nor a terminal, so a record whose progress mailbox is non-empty on every tick never reached it and the response stayed open for the whole execution. **Fixed in this release**; size shutdown grace against the enforced cap, per the server-admin manual, not against your longest execution; and **#2740**, a committed-but-undelivered streamed final holds one of the session's four streamed-POST admission slots, so four dropped connections locked that session out of streaming until it was deleted, the server restarted, a resume cursor passed the final, or the session was left idle long enough to expire. **Fixed in this release**. Neither affects plain JSON-RPC POST, the session lifecycle, or the GET channel. This is the same shape as Spark's `prefer_spark_`: land the machinery dormant, cut over where the invariants hold.
