- **MCP streamed POST (SSE-on-POST) lands, and ships OFF.** `execute_instruction` callers that supply a `_meta.progressToken` and send `Accept: text/event-stream` can receive progress on the POST response itself rather than the session's GET channel (ADR-1005 Decision 15, track 2f PR 3b). The machinery is complete and reviewed, but two bounds defects are open against it and it is therefore gated behind **`--mcp-enable-streamed-post` (default off)** — the follow-up PR carries both fixes and turns it on. The two, so an operator who opts in early knows what they own: **#2739**, the 120 s response cap is arbitrated only on a pass that finds neither progress nor a terminal, so a record whose progress mailbox is non-empty on every tick never reaches it and the response stays open for the whole execution (size shutdown grace against your longest execution, not against the cap); and **#2740**, a committed-but-undelivered streamed final holds one of the session's four streamed-POST admission slots, so four dropped connections lock that session out of streaming until it is deleted, the server restarts, a resume cursor passes the final, or the session is left idle long enough to expire. Neither affects plain JSON-RPC POST, the session lifecycle, or the GET channel. This is the same shape as Spark's `prefer_spark_`: land the machinery dormant, cut over where the invariants hold.
