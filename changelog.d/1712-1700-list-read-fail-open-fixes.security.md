- **Dashboard/workflow response readers and MCP `get_agent_details` close ADR-0017 list-read fail-open gaps (#1712, #1700).** The dashboard `/fragments/results` table and the workflow executions-drawer now apply the same per-agent management-group scope filter as the REST/MCP response readers (#1634/#1711) — a corrupt or unreachable RBAC store yields zero rows instead of the whole fleet's output. In the executions drawer the filter covers **both** per-agent sources: the response rows and the per-agent status fan-out that feeds the KPI counts, the agent grid and the per-agent table, so an out-of-scope agent's id, status, exit code and error text are withheld along with its output. The drawer's **live channel** (`GET /sse/executions/{id}`) is confined by the same predicate: per-agent transitions are admitted per event against the caller's management-group scope, so the stream can no longer re-disclose what the fragment withholds, and a corrupt RBAC store yields no per-agent events rather than the fleet. MCP `get_agent_details` now enforces management-group scope the same way `summarize_working_set kind=agent` does (#1653): an `agent_id` outside the caller's management group renders identically to "Agent not found," so that tool no longer confirms an out-of-scope agent's existence or discloses its hostname, os and tags. The dashboard results summary ("N results across M agents", and the Create Group affordance) and the drawer's targeted-agent total now count only in-scope agents, so a confined operator is no longer told how many agents outside their management group the command reached.
