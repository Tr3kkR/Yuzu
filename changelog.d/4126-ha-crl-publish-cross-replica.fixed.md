- **CRL publishing is safe across server replicas, and a missed CRL now republishes itself (HA WS-6 slice 6.1, #4126).** Every CRL publish (startup, an operator revoke, a subordinate-CA import, and the freshness re-publish) now runs as one Postgres transaction under a lock on the CRL table, so replicas sharing a database publish strictly increasing CRL numbers with no duplicates, and each CRL contains every revocation the previous one did. Previously two replicas publishing at the same moment could pick the same number, and one publish would fail. `GET /api/v1/ca/crl` is not blocked while a publish is in progress. A publish that waits more than 5 seconds for the lock fails and uses up no number: every trigger increments `yuzu_server_ca_crl_publish_failures_total`, and the operator-revoke paths also return `crl_republished:false` with a `ca.crl.published` failure audit. Previously a revoke whose own CRL publish failed stayed out of the public CRL for up to about 6 days; the leader's freshness pass now republishes on its next 15-second tick (up to about 5 minutes later if that attempt also fails) whenever the latest CRL does not cover every revocation. The `ca_store` schema migrates to v3 (a nullable `revoked_count` column, no backfill); rolling back to the previous release is safe.
