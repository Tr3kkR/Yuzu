- **`POST /api/v1/result-sets/{id}/re-eval` now rechecks its `instruction_result` fields against the same bounds enforced at creation time.** The `kInstructionResult` branch had no equivalent of the `kTarQuery` branch's existing 100 KiB `sql` cap: a caller holding ordinary `Execution:Execute` could mint a `Materialized` row via the unvalidated `POST /api/v1/result-sets` (no `source_kind` allowlist there) labeled `source_kind=instruction_result` with an oversized or over-keyed `params` object, or an oversized `instruction_id`, hand-crafted into `source_payload`, then call `re-eval` to dispatch it, fleet-wide if `parent_id` was omitted, fully bypassing any size bound. `re-eval` now re-applies the same `instruction_id` (256 bytes), `params` count (32 keys), key-length (256 bytes), and value-length (64 KiB) caps `create_result_set_from_instruction_result` already enforces at creation time, checked before the instruction-store availability gate so a malformed/oversized field is refused regardless of backend state. This mirrors the identical fix already shipped on the MCP twin, `reevaluate_result_set` (#4394). This IS a behavior change for a caller that was previously able to smuggle an oversized/over-keyed `params` object or `instruction_id` through this path and get it dispatched: that request now gets a clean `400` instead.
- Both branches also gained a type-confusion guard: `sp.value("sql", "")` / `sp.value("instruction_id", "")` threw `nlohmann::json::type_error` on a type-mismatched field (present but not a JSON string) rather than coercing it, an uncaught exception rather than a clean `400`. Both fields are now treated as absent when type-mismatched, matching the existing empty-field error path.
- **Not fixed here, tracked separately:** `POST /api/v1/result-sets` still has no `source_kind` allowlist, and REST's `from-tar-query`/`from-instruction-result` **create** routes still apply no per-field bound of their own beyond `from-tar-query`'s pre-existing `sql` cap (`docs/mcp-server.md`'s REST-twin-asymmetry note is narrowed accordingly, not resolved). Closing either is a separate, larger, deferred design question (adjacent note on #4353).
