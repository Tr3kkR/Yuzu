- **Guardian file guard's parent-directory watch is now retained across ordinary re-arms and torn down safely.** The watch that detects a rename or move of the guarded file's directory (added in the prior "file guard follows a renamed or moved watched directory" change) previously reopened on every single re-arm — including every ordinary content change to the guarded file — and blocked the re-arm on a full cancel-drain each time. It is now bound to the directory's resolved identity and only rebuilt when that identity actually changes, closing a source of needless per-event latency. Its teardown is a single drain-or-abandon step: a genuinely in-flight read is drained before its buffer is reused or freed; if a drain cannot be confirmed within the existing bound, the block is retained (never freed) so a delayed completion cannot write into memory that has since been reused, and after a small number of unconfirmed drains the watch is disabled for that guard, logged, rather than retried indefinitely. A rebuild that fails to open or arm no longer falls back to the guard's degraded polling cadence — it is retried for free on the next ordinary re-arm, matching the guard's normal event-driven design. Two watch-reconciliation call sites are corrected to match every other call site in the file's arm-before-check ordering: one that evaluated before re-arming (rather than after) is reordered, and one that re-armed without an evaluation following at all is given one — so a change landing in the gap is never missed.
