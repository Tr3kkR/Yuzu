- **MCP twins for human API-token rotation** (P2 #11, SOC 2 CC6.3): `rotate_api_token` and `confirm_api_token_rotation` mirror `POST /api/v1/tokens/{id}/rotate` and `/confirm` (ADR-1005 REST↔MCP twin obligation) over `ApiTokenStore::rotate_token`/`confirm_token_rotation`. Both gate on `ApiToken:Write`, reachable at the `operator` MCP tier and not approval-gated — self-service rotation of a token the caller owns, deliberately not the engine-credential arm's `Security:Write`/`supervised`-only/approval-gated posture, because the store itself confines a caller to their own token (`requesting_user` is always the authenticated session's username, never a tool argument). Owner-vs-nonexistent is indistinguishable (`kInvalidParams`, "token not found") — not an enumeration oracle. Audited on the `api_token.*` family (one row per reveal, mint, or replay, plus a `denied` row on the owner-mismatch path) and the confirm outcome increments `yuzu_api_token_confirm_total{surface="mcp",result=...}`, the sibling of the REST route's `surface="rest"` counter. **Known gap tracked for integration:** the rotate response currently reports the successor `token_id`/`expires_at`/`overlap_expires_at` unresolved (`successor_unresolved:true`) rather than re-deriving them via the engine arm's "first linked row" scan, which is unsound for a human principal that can have more than one rotation in flight at once (found mid-implementation; affects the REST twin identically; fix lands as one shared seam-level helper).
