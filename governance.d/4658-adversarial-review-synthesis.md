### Should fix

**1. The retry is not scheduled at its deadline when a later obligation exists** (Codex C2, Kimi K6; found by Codex; Kimi missed it in Phase 1, then verified the mechanism). `agents/core/src/spark_file.cpp:2514-2517`: `wake = any ? std::max(wake, pass_backoff_until_) : pass_backoff_until_`. Producers set `wake` with `std::min` (`:2449-2500`), so with a sole Deferred watch at +300 s (`kFileBackendRetryCap`) and a first-failure deadline at +50 ms, the result is +300 s. Codex's portable evaluation printed `later-deferred: wake=300000ms` vs `retry_deadline=50ms`; I confirmed by reading the producers and the max().
- Why it matters: the log says "retrying in 50 ms" but the retry runs at the later deadline; in a quiet worker the second and third failures (and so the `inert` flip) come on the later obligation's schedule (minutes) instead of the doubling schedule. That is the "dark worker reads healthy" case the issue exists to close. It self-corrects after one stretched interval because the later deadline becomes due-now and is then floored correctly.
- Comment `:2505-2506` claims "EVERY deadline computed above is clamped to the backoff deadline" and that the retry is an obligation; the code honours that only for earlier deadlines.
- Fix: while `pass_backoff_until_ > now`, `wake = pass_backoff_until_; any = true;` (the retry obligation IS the wake; later obligations are recomputed after the retry pass). Cost: at most one near-empty pass per backoff period (<= 30 s), already accepted for the idle case. Add a test: a Deferred watch with a much later deadline plus a transient control-wake pass failure; assert the retry pass runs near the backoff deadline. Mutation: revert to `max` and confirm that test goes red. Windows-only, so it needs a DGRHP run.
- Falsifier: a case where running the retry at `until` (instead of the later deadline) starves or breaks a real obligation. None found by either reviewer.

Registry has had the same shape since PR-B1; this change adds a runtime writer for File. Dormant while `prefer_spark_` is false and visible via the unsupported gauge/log. Recommendation: do not fix here (Guardian design change); add one sentence to R5.7 (g) stating the persistence, and file a follow-up issue for a recovery-edge re-reconcile plus a full-sync-during-failure test. Note it for the #4659 session (same consumer surface).
