## HEAD mechanism (read directly, this checkout)

- `io_detail::detached_trampoline` owns the worker closure in a `std::unique_ptr<DetachedPayload<Fn>>` (`agents/core/src/guardian_io_executor.hpp:256-269`). The payload, and with it the lambda and its captured `ticket` copy, is destroyed when that unique_ptr goes out of scope at the end of the trampoline: after `p->fn()` returns, before the trampoline returns, before the OS thread exits.
- `run()` worker captures `ticket` by value (`guardian_io_executor.hpp:497`); the caller drops its own copy under `wait_lk` right after launch (`:605`). `submit()` worker captures `ticket` (`:667`); the caller drops its copy unlocked after launch (`:744-749`).
- `alive_total` / `alive_by_class` are incremented only in `admit_locked` (`:979-980`) and decremented **only** in `~TicketCore` (`:902-905`), which runs when the last `shared_ptr<TicketCore>` holder dies. `active_worker_count()` reads `alive_total` (`:779-786`); `GuardianEngine::active_io_workers()` sums it (`agents/core/src/guardian_engine.cpp:1918-1936`).
- So at HEAD the alive decrement runs in `~TicketCore`, on the worker thread, at trampoline payload destruction: after the worker lambda has fully returned (including `on_complete`/`on_abandoned` and the callable resets), before the trampoline returns, before OS-thread exit. The post-decrement tail is: the rest of `~TicketCore` (`cv.notify_all`, `:909`), the remaining capture releases (the `State` shared_ptr), payload deallocation, the trampoline epilogue, CRT thread exit.
- The one range-added variation: for `submit()`, if the worker finishes before the caller's unlocked `ticket.reset()` (`:749`), the caller is the last holder and the decrement runs on the **caller** thread, after the worker already returned. The header documents this (`:133-135`, `:744-748`) and it moves the release **later**, never earlier - conservative for F3.

## Adjudication of the reviewer's finding

"The alive count reaches zero before the OS thread exits" is an accurate ordering description, but it describes a property that **already held at base `74090cf4a`** (and per the recorded history, since rung 7). This range did not move the physical release point one instruction earlier; its only new path moves it later (the `submit()` caller-thread case). The "opening the F3 teardown race" framing is also not supported by the tail's contents: the tail runs only process-lifetime runtime code (`notify_all`, `operator delete`, libstdc++/libc/pthread or CRT exit), never the Guardian/OpenSSL/libsystemd/Win32-RPC code F3 names as the hazard (`main.cpp:919-920`; design doc R5.1). A self-decremented count can never certify its own thread's exit; that residual is documented and accepted, not introduced. The finding is **pre-existing**, and its defect framing was correctly rejected in prior rounds.
