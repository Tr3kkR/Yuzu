| **`browser_inventory` plugin (Forensics, default-off, per-user browser data)** — reads per-user Chromium-family browser profile state (`browsers`/`profiles` actions; the per-profile `extensions` action follows as its own PR). CATASTROPHIC-IF-VIOLATED: it must never emit a browsing-account identifier, browsing history, cookies or bookmarks — no `gaia_id`, no e-mail address, no Chromium `info_cache` `user_name`/`gaia_name` field, in any row, on any OS leg. **Amended 2026-09-22 (Alex):** the LOCAL OS/home-directory account name (e.g. the `alice` in `/home/alice`) is explicitly PERMITTED on the `profiles` row — it disambiguates which of several local users on a shared machine a profile belongs to, is machine-local, and is not itself a personal/cloud identifier; it is NOT covered by the identifiers this clause forbids. `BrowserProfileRow` (the pure JSON row model in `browser_inventory_parsers.hpp`) still has no such field and never will — the local username is added only when the Linux leg formats the wire row (`browser_inventory_linux_parsers.hpp`'s `linux_profile_rows_at`), never inside the parser. **Second amendment 2026-09-22 (Alex, adversarial-review finding):** the `profiles` row's `display_name` (`BrowserProfileRow.display_name`, sourced from Chromium's `info_cache[dir].name`) is ALSO explicitly ACCEPTED as a residual-risk exception, not a struct field to strip — Chromium-family browsers commonly auto-populate a profile's display name from the signed-in account's real name, so this field CAN legitimately carry a personal name even though it is never a structured `gaia_id`/`user_name`/`gaia_name` JSON key; the README's "PRIVACY CONTRACT" and this row must both say so plainly rather than claim `display_name` is never an account/real-name field. A reviewer adding a NEW free-text field sourced from browser-controlled JSON must weigh this same risk explicitly, not assume `BrowserProfileRow`'s lack of a named identifier field is sufficient. A reviewer adding a `gaia_id`/`user_name`(browsing-account)/e-mail/history/cookie/bookmark field to `BrowserProfileRow` or any wire-row builder must re-verify this invariant, not just compile-check it. **Third amendment 2026-09-22 (Alex, adversarial-review finding):** the second amendment's residual-risk acceptance does NOT cover an e-mail-shaped value — an e-mail address is a browsing-account identifier under the headline clause above, unconditionally forbidden regardless of which field carries it. Both `profile_dir` (the `info_cache` key itself — some Chromium builds, notably a signed-in Edge profile, key it by the account e-mail) and `display_name` are free-text fields that can carry this shape, so `profiles_from_local_state` (`browser_inventory_parsers.hpp`) now redacts either field to the fixed literal `[redacted-email]` (`looks_like_email_address`/`kRedactedEmailPlaceholder`) BEFORE `BrowserProfileRow` is built — enforcement by value, not by the struct's field absence, since these two fields necessarily exist for the plugin to do its job. A reviewer relying on "the struct has no such field" as this row's whole enforcement story is exactly the gap that let the e-mail case reach the wire once already; the value-level filter is the closure, and it must survive any future refactor of `profiles_from_local_state`.
