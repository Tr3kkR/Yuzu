SPEC: GitHub issue #3692, 'OTA package upload/delete/rollout routes emit no audit-log event (CC7.2 evidence gap)'.

## Context

Found during the `/governance` run on PR 1 of the Postgres migration ladder's Wave 4 (`pg/update-registry`, UpdateRegistry migration, ADR-0061), by the `compliance-officer` reviewer. The underlying gap is entirely pre-existing — confirmed via `git diff --stat` that `settings_routes.cpp` is not touched anywhere in that migration PR, so this is not introduced or newly load-bearing by it. Filed per governance policy: an `I1` (security/audit-control-failure) finding cannot be silently parked even when it's out of scope for the diff that surfaced it.

## Evidence

`server/core/src/settings_routes.cpp:5265-5419` — the three OTA package management routes (`POST /api/settings/updates/upload`, `DELETE /api/settings/updates/{platform}/{arch}/{version}`, `POST .../rollout`) all gate correctly on `admin_fn_`, but none of them call `audit_fn_` — only `spdlog::info(...)` (app log, not the audit log). Sibling admin routes in the *same file* (`cert.upload`, `oidc.configure`, `plugin_signing.bundle.uploaded`, `user.create`) do call `audit_fn_` with a verb/result/entity triple. There is no compensating global mechanism — `server.cpp`'s pre/post-routing handlers cover auth/quota/metrics/security-headers only, not audit emission. `--ota-enabled` defaults **true** (`main.cpp:780-781`; the only flag is `--no-ota`, opt-out), so this is default-configuration behavior, not a niche opt-in.

## Scenario

An admin (or a compromised admin session/token) pushes an arbitrary binary to the entire agent fleet via the OTA upload route, or silently deletes/de-prioritizes a mandatory security patch via the delete/rollout routes — none of this is durably recorded anywhere an auditor or incident responder would look. "Who changed what OTA package when" is exactly the kind of change a SOC 2 auditor asks about for a capability with this blast radius.

## Acceptance criteria

- [ ] All three routes call `audit_fn_` (or the codebase's equivalent audit chokepoint) with the acting principal, the affected `(platform, arch, version)` key, and the action (`upload`/`delete`/`rollout_update`).
- [ ] Confirm no other admin-config route family in `settings_routes.cpp` has the same gap (a broader sweep may be warranted — this issue only names the OTA routes, found incidentally).
- [ ] A test asserting the audit row lands with the correct fields.
